## 一¾、三维到底踩不踩得到（小弟只查不改的报告，11-13 晚；探针 `test/probes/probe-autosave-resume-race.mjs`）

- **三维自己叠着发两次保存的那几种：踩不到。** 会话的保存排成一条队（`session.save` 的「正在存」旗）：自动保存撞上正在存的就这一拍不存；人按的、离开时的等前一次落地再存；刷新前先等正在存的。三维里没有别的路对开着的这份调保存。
- **「自动保存 + 回来续推」：踩得到。** 续推不走会话那条队（回线 / 登录落地之后的那一串、离线队列、图库卡片上的「处理…」）。前提：这份在这之前已经有一笔没传的（之前没网时存过）。探针在真的库 2.2.7 上三种排法是红的（云端是旧的、库的待传是 0）；小文件、本机写得快的那种 6 轮里 0 轮命中。
- **三维自己的那一层挡住了。** 会话另有一个「这份还没传完」的记号（`pushPending`），三种红的排法里它都还是真：回到前台心跳会补推；别的设备改了网盘、这台去核对时因为它不快进——探针实际跑了这一步，最后那一笔还在。
- **一条两层都会失效的窄路（读代码得出，探针没造出来）**：续推做完之后，会话按库报的「还剩几份」来放下自己的记号。要是这次自动保存正好在续推还没做完时落了本机，库的计数被错清成 0，会话的记号也跟着被清，两层都没了。收了 2.3.6 库的计数是对的，这条路不会再被错数触发。
- **结构上的事（统筹定，放进第二版）**：会话那一层的「放下」现在信的是库的计数，等于两层其实是一层。见第三节第 8 条。

## 三、第二、三版的规矩（原则先定，细则待补）

统筹先定的原则：

1. **已知云端有更新、内容没取下来** = 和 user 点「逃生」同一个状态：同一句话、同一个保护（改了存成「（分叉 时间）」，原来那份不碰）。不许等十来秒之后悄悄放行到旧版本。
2. **连问都没问成**（不知道云端有没有更新）= 照现在的离线路走，但要说一句「没连上云端，眼前是这台设备上的版本」。
3. **同一次故障、同一份文件**：后面的自动重试不整屏挡着；人主动点开的那一次照旧。「同一次故障」怎么算，待补。
4. **整屏的框一次只有一个主人**：后叫的不许盖掉先叫的，冲突框尤其（小黑屋用真的同步库跑出来过：盖掉冲突框 = 那一份之后的保存全落不了盘）。
5. **没人改过的文件不许被记成有改动或待传。** 小弟先只查不改（iPad 日志 18:20:34 那行 `gate check …: dirty`），结果出来再定要不要改、改哪里。
6. 冲突只在库的面里三选一，三维不替人回答、不绕面换字节（照旧）。
7. 调试日志导出时有没有该滤掉的东西，对一遍。

8. **会话那一层的「放下」不许只信库的计数**（瑞士奶酪：每一层自己承重）。续推开始时记下会话的保存序号；续推做完，只有「库说没有待传」**而且**「这段时间里没有新的保存落地」才放下记号，否则留着、让心跳再推一次。宁可多推一次。从库拿到「推完了 / 本来就干净」的那条路同理。

9. **三维的正确性不许靠同步库的超时。**（user 11-13 晚，原话：「我觉得这是一个非常严重的纪律问题，就是相当于你依靠这么一个本来不是用你做这个东西来保证你应用逻辑的正确，然后反而让别人去牺牲他们的安全要求去来迎合你，这是一个非常严重的纪律问题，非常严重的纪律问题。就是为什么你必须要依靠这个逻辑来保证你不卡死？我觉得这你可能本来就不应该有超时，关键是你依靠这个逻辑，你反而去改扩，反而把所有其他人都牵连了，这是一个非常严重的纪律问题。」「地理」「改扩」是语音，= 纪律、改库。）

## 三¾、细则（11-13 晚，统筹照小弟的报告定；报告 = `ai-docs/20261112-sync-session-facts-and-borrowed-safety.md`，查出九处「靠库的保命机制才成立」）

第二版拆成四小版，每版一件，diff 都发统筹。顺序按「先堵会整份藏起来或被盖掉的，再做最大的那件」。

**二之一：先存后数。**（报告第 5、6 处）
- 退出登录、还原出厂的护栏、离开文件夹家：先把开着的这份落盘（只落本机），再数「还有几份没传」。
- 数 = 库报的数，再并上开着的这份自己的状态（有没存的改动、还没传完）。数不出来按有。
- 探针：开着的有没存的改动、又没网 → 退出登录 → 下次开机库还挂着、这份看得见；还原出厂的护栏数到了它。

**二之二：会话自己的判断不借库的。**（报告第 3、4、7 处，顺带第 8 处）
- 不变量（三处其实是一件事）：
  1. 眼前的画布和它挂着的那份文件的本机副本，必须是同一条线上的。本机副本被换成了别的版本而画布没跟着换：画布没被动过 = 整份换成新版本并说一句；被动过 = 立刻改挂分叉名（不改不留，改了另存）。绝不让旧画布接着存进已经换新的那份文件里。
  2. 判断「换没换」看库的动作返回的结果（或者画布记着自己是从本机副本的哪一版读出来的，每次库的动作回来对一下），不从界面的回调里看人选了什么。
  3. 人点了「先离线用」= 闸自己的取消：那次核对回来的结果不许悄悄作用到画布上，照上面第 1 条处理。`localDirty` 只回答会话真的脏不脏，不再夹带「闸放弃了」。
  4. 「还没传完」的记号：续推开始时记下会话的保存序号；做完，只有库说没有待传而且这段时间没有新的保存落地才放下。从库拿到「推完了 / 本来就干净」的那条路同理。
- 心跳补推停不停（第 8 处）：会话自己记上一次推的结果，按结果定节奏。顺手能做就做，做不了记一笔。
- **「换没换」怎么判**（小弟查了 2.3.6 的返回值，11-13 晚）：`resolve()` 和 `pullIfClean` 的结果里明说了换没换，直接用；`open()` 只返回字节，看不出来（这就是原来只能从界面回调里猜的原因）。统筹定：在库给出正式字段之前，会话自己记一份摘要——画布是从哪一份字节读出来的、上一次落本机写的是哪一份字节（读进来和每次本机落盘成功时各记一次）；`open()` 回来的字节和它比，不一样 = 本机副本被换了，照上面第 1 条处理。条件：
  - 这是「字节变没变」的核对，不是身份：摘要只活在这一次会话的内存里，不写进文件、不拿去认文件、不跨设备比。（家规否决的是拿内容哈希当身份；库自己做回执自愈时也是比字节。）
  - 它靠的只有一条：`open()` 返回的就是本机副本的字节。加一条测试钉住：存进去、读出来，字节一模一样（明文和加密的各一种）。这条不成立就停下来报统筹。
  - 判错的方向必须是安全的那一侧：误报 = 多一次重开或多一份分叉，绝不能是漏报之后旧画布盖掉新文件。
  - 用到摘要的地方标出来，库给了正式字段就换掉。

**二之三：门口说实话。**（报告第 2 处；小黑屋交来的第 1 条）
- 下载失败不等于通过。已知云端有更新、内容没取下来 = 和 user 点逃生同一个状态：同一句话、同一个分叉保护。连问都没问成 = 「网盘没连上」那一面（已有）。
- 闸不靠库的下载到点才动：开始换字节之后等得久了（先定 15 秒，写成有名字的常数），罩子上加一句「网盘那头很慢，可以先离线用：眼前是这台设备上的旧版本，改了会另存一份」。只是多一句话，不自动替人点。
- 日志里的 `other` 拆成四个各自的词；闸被放弃时不再记成 `dirty`。
- 自动保存被跳过时，调试日志记一行（界面上的表示归二之四）。
- 探针：列目录通、下载内容失败（断开、超时、网关超时各一种）→ 界面说了什么、落在什么状态、改一笔之后落到哪个文件、云端那份有没有被碰。

**二之四：本机落盘不等网络。**（报告第 1 处；最大的一件，**动手前先交方案**）
- 要求：
  1. 「正在存」= 本机落盘在路上，落完就放下。推云单独一条线（同一时刻只有一趟），有自己的状态，不挡自动保存、切后台、离页、人按存。
  2. 要等推云结果的地方（离开前、刷新前）明着等推云那条线，带着人看得见的进度和「不等了」。
  3. 自动保存那一拍到了、上一次本机落盘还没回来（库的写队被上传占着）：不跳过，把这一刻的内容写进独立的影子库。加密的模型在里面必须是密文；口令忘了 = 不写并说一次（照现有的规矩）。之后本机落盘成了，清掉这份影子。
  4. 开机时影子里有图库文件的帧：打开那份文件，把帧当成没存的改动接上（算改过），照常自动保存。帧接不上（文件不在了、读不出、本机副本比它新）= 不丢帧，问人（另存成一份 / 丢掉），不替人定。
  5. 界面分得清三种：已存到本机并传完；已存到本机、正在传或等着传；这一段还没进图库、先放在应急备份里。
  6. 请求时限的开关原样不动，不改库。
  7. **先清点隐含的依赖，再拆。**（11-13 晚加；起因 = 小黑屋维修线设计同步库那一头时翻出来的：现在「保存和上传包在一起」的排法是有出处的，最早一次真实事故之后定的；而且加密、解密、换口令现在是靠「等在途的上传」才不会和明文的上传叠着——隐私红线。）三维的「正在存」拆成「本机落盘」和「推云」两条线之前，方案里先列出所有在看「正在存」、或者靠「等保存返回」的地方，逐处写它真正要的是哪一样：本机落完了 / 没有上传在飞 / 两样都要。重点查：加密、解除加密、换口令；改名、删除、移出本机；安家、搬家、另存；采纳云端那份、冲突面的两个选择；切换文件、退出登录、离页、刷新前。原来靠「正在存」顺带挡住的，拆完之后要明着去等对的那一条线，一处都不许因为拆开而放空。这张表交统筹，看过才动手。
- **验收就是「不靠超时」**：故障注入让上传挂住 10 分钟（时限设成很长），期间每 30 秒的改动都落了盘（库的本机副本或者影子）；这时候杀掉页面再开，一笔不丢。原来那个场景（时限 30 秒）照样过。
- 方案里要写：状态有哪几个、怎么转；切后台和离页那一下怎么办；恢复时界面长什么样；影子写不进去（空间不够）时说什么。

**第三版：同一次故障不反复整屏挡着；整屏的框一次只有一个主人。**（照第三节第 3、4 条，细则到时候补）
