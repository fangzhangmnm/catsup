## 一½、为什么第一版提到最前面（11-13 晚）

小黑屋维修线把同步库仓 11-10 的复现脚本（`test/repro/f188-dirty-cleared-before-bytes-land.repro.ts`，提交 dd5b2ba）拿到 v2.2.7 的导出副本上跑了，三维钉的正是这一版。它报的结果（统筹没有自己跑）：

- 五种时序里四种复现：自动保存和自动续推同一刻；隔一个微任务；存并推之后紧跟一次只落本机的保存；第一次保存的本机写入慢、这期间来了第二次保存。结果都是网盘 = 旧的、本机 = 新的、待传计数 = 0。
- 后果：别的设备改了网盘，这台去核对 = 干净快进，本机换成云端那版，备份箱 0 份。最后存的那一段没了，不留底。
- v2.3.5 上五种全过（2.3.2 修的，周账 F-238）。
- 它没查三维的会话层。三维要是自己把保存和上传排成了一条队，这几种时序可能踩不到——所以小弟先对着这四种时序读三维的会话层、尽量写出一个会红的探针，再收库。

user 是电脑和 iPad 换着用的，所以这是丢东西那一类，排在所有功能前面。

## 一¾、三维到底踩不踩得到（小弟只查不改的报告，11-13 晚；探针 `test/probes/probe-autosave-resume-race.mjs`）

- **三维自己叠着发两次保存的那几种：踩不到。** 会话的保存排成一条队（`session.save` 的「正在存」旗）：自动保存撞上正在存的就这一拍不存；人按的、离开时的等前一次落地再存；刷新前先等正在存的。三维里没有别的路对开着的这份调保存。
- **「自动保存 + 回来续推」：踩得到。** 续推不走会话那条队（回线 / 登录落地之后的那一串、离线队列、图库卡片上的「处理…」）。前提：这份在这之前已经有一笔没传的（之前没网时存过）。探针在真的库 2.2.7 上三种排法是红的（云端是旧的、库的待传是 0）；小文件、本机写得快的那种 6 轮里 0 轮命中。
- **三维自己的那一层挡住了。** 会话另有一个「这份还没传完」的记号（`pushPending`），三种红的排法里它都还是真：回到前台心跳会补推；别的设备改了网盘、这台去核对时因为它不快进——探针实际跑了这一步，最后那一笔还在。
- **一条两层都会失效的窄路（读代码得出，探针没造出来）**：续推做完之后，会话按库报的「还剩几份」来放下自己的记号。要是这次自动保存正好在续推还没做完时落了本机，库的计数被错清成 0，会话的记号也跟着被清，两层都没了。收了 2.3.6 库的计数是对的，这条路不会再被错数触发。
- **结构上的事（统筹定，放进第二版）**：会话那一层的「放下」现在信的是库的计数，等于两层其实是一层。见第三节第 8 条。

## 二、分三版，不混

**第一版：只收库，行为不变。** 同步库 2.2.7 → **2.3.6**（原来写 2.3.5；小黑屋维修线请我们等 11-12 晚出的 2.3.6，原因见下面「升级注意事项」第 3 条）。

- 走 `pwa-cloud-store` 的升级流程；动手前读 `20260601 MyPWAPatterns/docs/MASTER.md`（家规硬规则第 1 条）。库是唯一入口，缺接口不在三维这头绕，报统筹。
- 图库库（0.8.10）和加密库（0.2.2）这一版不升。2.3.5 要是要求更高的图库库 = 停下来报统筹（图库库 0.9 带着修改锁，那是另一轮迁移，不许顺手做）。
- 2.3.0 带来的两个开关（锁、记号）保持关。
- 好处是两样：下载失败的记录带上哪一步、哪台主机、哪个文件、等了多久；4 MB 以下一次传完的上传时限从 30 秒放宽到 120 秒。
- 代价：中间跨了 2.3.0 到 2.3.2（保存排在同名的队里、盘上账本）。要单独跑一遍端到端和红线那一组。
- **升级注意事项**（小黑屋维修线统筹 11-12 晚给的，它说是对着两版的接口清单和 18 个改过的源文件核的；统筹没有自己核）：
  1. **必须改的：没有。** 接口只有新增的可选项，没有删、没有改名、没有新的必填声明；三维建库时传的那些项全部照旧有效。两个新开关 `lockByDefault`、`fileMarks` 默认关，不传就是 2.2.7 的行为——这一轮别开（`fileMarks` 一开就会在网盘上建一份 `.catsup/store.file-marks.json`）。本机数据库没有迁移，退回 2.2.7 本机数据是兼容的（它是看改动的文件清单得出的，没有真的来回装过）。
  2. **可以只换同步库。** 图库库 0.8.10 的包里要求同步库 ≥ 2.1.2；加密库 0.2.2 对同步库没有要求。小黑屋当天上线的那一版跑的正是同步库 2.3.5 + 图库库 0.8.10 + 加密库 0.2.2，端到端 91 个场景它自己跑过。
  3. **一次传完的上传时限**：三维靠库的请求时限保证「正在存」不会永远是真（上传卡死 = 自动保存全被跳过 = 改动只在内存里，见 `src/app-store.ts` 里那段说明）。2.3.4 把 4 MB 以下一次传完的上传从 30 秒并进了 120 秒那一档。2.3.6 给它单独一个时限项 `upload`（写在请求时限那张表里：`timeouts: { ...DEFAULT_GRAPH_TIMEOUTS, upload: 30_000 }`）；不写 = 和 2.2.7 一样的 30 秒（小黑屋 2.3.6 出来时更正的，之前说的「不传 = 120 秒」作废）。~~统筹定：第一版写明 `upload: 30_000`~~ **撤回（同一晚，user 批评之后）：第一版不写这一项，请求时限那一行原样不动；三维不再对库的超时提任何要求**（见第三节第 9 条）。`src/app-store.ts` 那段说明只补一句「这是欠账」。**不要收 2.3.4 / 2.3.5**（那两版里一次传完的上传按 120 秒那档掐断，小黑屋自己说是裁定错了）。要不要放宽，等新的报错记录攒出「慢网上到底有多少次是卡在这 30 秒」的事实再定，单独一次改动。
  4. **行为变了、要拿测试对一遍的**：
     - 保存的 promise 现在要等同一份文件前面排着的动作（上传、加密转换、改名）做完才落盘、才返回。会话层里凡是「存一下应该很快回来」的地方看一眼。
     - 待传计数在保存叠着的时候会多留一会儿：以前错报 0 的地方现在是 1；叠着保存会多推一次；回执丢了之后又改过的，以前偶尔碰巧认成已同步，现在留着待传、之后撞冲突框问人。断言「此刻待传是 0」的测试可能要跟着改——这正是要的那个修，不许为了让测试过把它改回去。
     - 网络报错的字变了（带主机、文件、用时和一个固定词表里的类别，不再带浏览器的原话）；报错对象多了 `stage`、`host`；`cause` 换成只有名字和类别的替身。它搜过三维：按名字判 `CloudNetworkError` 的那处不受影响。要动的只可能是写死了报错原文的测试断言。
     - 同步收藏夹超时的那句从 `timeout` 变成带名字和毫秒数的一句。
     - `ui.resolveConflict` 的参数多一个可选的 `contentFailing`。不理它就和以前一样；第二版可以用它和 `stage`。
     - Graph 回非 2xx 时的错误正文截到 300 个字符。
  5. **所有版本都这样、不是这次带来的**：同一份文件有上传在飞的时候，库里后面的保存（包括只存本机的）都排在它后面。三维自己的崩溃影子是独立的一层，收库的时候不许把它动薄。
  6. **包和说明在哪**（2.3.6 已出）：包 = 同步库仓根目录 `internal-store-2.3.6.tgz`（tag v2.3.6）；收法 = 在三维仓根跑 `bash "../20260813 internal-store/scripts/pull-package.sh" 2.3.6`。说明 = 同步库仓 `ai-docs/20261112-host-upgrade-notes-2.2.x-to-2.3.6.md`（七节，每条写了是跑过的还是读代码得出的；别家踩过的坑在第五节，测试怎么照着做在第七节）。**开工前整份读。**
  7. **收了 2.3.6 也还在的**（说明第六节；统筹读了）：同一份文件的写队在等人、等网络时被占着（冲突面一直没人答 = 之后的保存落不了盘）——三维能做的是保证问人的面一定有人答得到，这归第二、三版；下载回来的字节不和文件大小对账，验内容靠三维自己的 `validateAdopt`（三维的文件有魔数，拦得住）；报错分不清「连不上」和「连上了但浏览器不让读」；调试日志导出要不要再过滤一遍各家自己定。

## 三、第二、三版的规矩（原则先定，细则待补）

统筹先定的原则：

1. **已知云端有更新、内容没取下来** = 和 user 点「逃生」同一个状态：同一句话、同一个保护（改了存成「（分叉 时间）」，原来那份不碰）。不许等十来秒之后悄悄放行到旧版本。
2. **连问都没问成**（不知道云端有没有更新）= 照现在的离线路走，但要说一句「没连上云端，眼前是这台设备上的版本」。
3. **同一次故障、同一份文件**：后面的自动重试不整屏挡着；人主动点开的那一次照旧。「同一次故障」怎么算，待补。
4. **整屏的框一次只有一个主人**：后叫的不许盖掉先叫的，冲突框尤其（小黑屋用真的同步库跑出来过：盖掉冲突框 = 那一份之后的保存全落不了盘）。
5. **没人改过的文件不许被记成有改动或待传。** 小弟先只查不改（iPad 日志 18:20:34 那行 `gate check …: dirty`），结果出来再定要不要改、改哪里。
6. 冲突只在库的面里三选一，三维不替人回答、不绕面换字节（照旧）。
7. 调试日志导出时有没有该滤掉的东西，对一遍。

8. **会话那一层的「放下」不许只信库的计数**（瑞士奶酪：每一层自己承重）。续推开始时记下会话的保存序号；续推做完，只有「库说没有待传」**而且**「这段时间里没有新的保存落地」才放下记号，否则留着、让心跳再推一次。宁可多推一次。从库拿到「推完了 / 本来就干净」的那条路同理。

9. **三维的正确性不许靠同步库的超时。**（user 11-13 晚，原话：「我觉得这是一个非常严重的纪律问题，就是相当于你依靠这么一个本来不是用你做这个东西来保证你应用逻辑的正确，然后反而让别人去牺牲他们的安全要求去来迎合你，这是一个非常严重的纪律问题，非常严重的纪律问题。就是为什么你必须要依靠这个逻辑来保证你不卡死？我觉得这你可能本来就不应该有超时，关键是你依靠这个逻辑，你反而去改扩，反而把所有其他人都牵连了，这是一个非常严重的纪律问题。」「地理」「改扩」是语音，= 纪律、改库。）
   - 现状（统筹读的代码）：会话把「正在存」的旗挂在 `await` 库的保存上，推云是内联在那次保存里的；推云挂住 = 旗一直是真 = 30 秒一拍的自动保存全被跳过。当初是用「给每个请求开时限」糊上的（`src/app-store.ts` 42–43 行自己写着）。图库里的文件，崩溃影子就是「自动保存到库的本机副本」，没有独立的一层（`session.ts` 开头的说明）——所以上传挂住的那段时间，改动确实只在内存里。
   - 牵连：小黑屋维修线读到这个依赖之后，在 2.3.6 里把「一次传完的上传」的默认时限从 120 秒退回了 30 秒。统筹当晚还定过「三维写明 30 秒」，是在加固这个依赖，已撤回，并告诉了小黑屋：默认值请按库自己的道理定，不用照顾三维。
   - **要做成的样子**：不管网络那一头等多久、挂不挂，本机落盘都不受影响。「正在存」只管本机落盘；推云在后台，不占着它。
   - 库那一头的根（周账 F-268：同一份文件有上传在飞时，后面的保存都排在它后面）归小黑屋维修线和 user；三维的做法要跟着它走。在它修好之前，三维这一层自己承重：自动保存撞上正在存时不再跳过，写进独立的那个影子库。这一条是统筹的提议，**要 user 点头才做**。
   - 细则等小弟查实四件事实（图库家有没有独立影子、旗等的是哪一步、上传在飞时再发只落本机的保存会怎样、被跳过时界面上有没有表示）。

待补（等报告）：门口现在有哪几种结局、各自显示什么；「other」是哪几种情况合在一起的；第 3 条的边界。

## 四、验收

- 故障注入的探针：列目录通、下载内容失败（断开、超时、网关超时各一种）。每一种：界面上说了什么、放行到了什么状态、改一笔之后落到哪个文件、云端那份有没有被碰。
- 同一份文件连着失败三次：整屏的框只出现一次（人主动点的除外）。
- 冲突框开着时再触发别的整屏的框：冲突框还在，保存照常落盘。
- 没人动过的文件，经过开机恢复、点离线、登录过期、下载失败之后，不在待传名单里。
- 红线那一组在要发的那个提交上全绿。
