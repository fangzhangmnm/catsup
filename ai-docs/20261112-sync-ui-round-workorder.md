## 三、第二、三版的规矩（原则先定，细则待补）

统筹先定的原则：

1. **已知云端有更新、内容没取下来** = 和 user 点「逃生」同一个状态：同一句话、同一个保护（改了存成「（分叉 时间）」，原来那份不碰）。不许等十来秒之后悄悄放行到旧版本。
2. **连问都没问成**（不知道云端有没有更新）= 照现在的离线路走，但要说一句「没连上云端，眼前是这台设备上的版本」。
3. **同一次故障、同一份文件**：后面的自动重试不整屏挡着；人主动点开的那一次照旧。「同一次故障」怎么算，待补。
4. **整屏的框一次只有一个主人**：后叫的不许盖掉先叫的，冲突框尤其（小黑屋用真的同步库跑出来过：盖掉冲突框 = 那一份之后的保存全落不了盘）。
5. **没人改过的文件不许被记成有改动或待传。** 小弟先只查不改（iPad 日志 18:20:34 那行 `gate check …: dirty`），结果出来再定要不要改、改哪里。
6. 冲突只在库的面里三选一，三维不替人回答、不绕面换字节（照旧）。
7. 调试日志导出时有没有该滤掉的东西，对一遍。

待补（等报告）：门口现在有哪几种结局、各自显示什么；「other」是哪几种情况合在一起的；第 3 条的边界。

## 四、验收

- 故障注入的探针：列目录通、下载内容失败（断开、超时、网关超时各一种）。每一种：界面上说了什么、放行到了什么状态、改一笔之后落到哪个文件、云端那份有没有被碰。
- 同一份文件连着失败三次：整屏的框只出现一次（人主动点的除外）。
- 冲突框开着时再触发别的整屏的框：冲突框还在，保存照常落盘。
- 没人动过的文件，经过开机恢复、点离线、登录过期、下载失败之后，不在待传名单里。
- 红线那一组在要发的那个提交上全绿。
