## 一、四件事实

**1. 图库家有没有独立的崩溃影子：没有。**（读代码）
- `session.ts` 头注释第 5–7 行：图库家 = 30 秒空闲自动保存到库的本机副本，这就是它的崩溃影子；独立的影子库（`crash-store`，盲快照、行李牌）只给磁盘上的单个文件和还没有家的模型。
- 代码对得上：`localHomeKind()` 对图库家返回 null（`session.ts:265`），`snapshotOnce` 第一行看见 null 就退（`:354`）；`tick` 里图库家走 `save({ implicit: true })`（`:325`）。

**2. 「正在存」从竖起到放下，中间等的是什么。**（读代码）
- `save()` 竖 `saving` → `writeHome`：① 等参考卡编码完（`refs.settled`）② 冻结 + 编码（含画的合成）③ `docFile(path).save(bytes, { tryPush })`：库里先落本机，`tryPush` 为真就接着推云（取元数据 + 上传，带 If-Match），推完 / 失败 / 超时才返回；2.3.2 起还要先等同一份文件前面排着的动作（上传、加密转换、改名）④ 选了「云端覆盖本地」的还要整份重开 → `finally` 放下。
- 推的保存 = 等到推云结束；不推的 = 等到本机落盘。
- 自动保存那一拍的 `tryPush` = 已登录 ∧ 在线 ∧ 没被压住（`pushHeld`：回来那一串前半段、从没传过人没答应的）。**平常在线登录着的自动保存 = 一直等到推云结束。** 只落本机的几种：没网 / 没登录 / 被压住时的自动保存；离页（pagehide）；刷新前（flushBeforeReload）第一步；门口核对里那一下。
- 人按的保存：在线时同样等推云；撞上冲突会弹面 → 等人答，这段时间 `saving` 一直真（同步库说明第六节第 1 条「写队在等人时被占着」在三维这一层的样子）。

**3. 库里有上传在飞时，三维再发一次只落本机的保存，会怎样。**
- 库这一层：排在那次上传后面等（同名串行段；同步库说明说所有版本都这样，2.3.2 起封装也进了队）。（读库的说明）
- 三维这一层根本不发：`saving` 竖着时，自动的直接 `return false`、这一拍不存；人按的 / 离开时的等前一次落地再存；离页看见 `saving` 就不存；刷新前先等 `saving` 放下，最多等 `RELOAD_PUSH_WAIT_MS`，过了时限再发的那一下只落本机也被 `saving` 挡回（implicit → false）。**所以实际表现 = 推云没结束之前，之后的改动不落盘，只在内存。**（读代码）

**4. 自动保存撞上「正在存」被跳过时，界面上有没有表示：没有专门的。**（读代码）
- `tick` 的 `idle` 含 `!this.saving`（`session.ts:323`），不满足就这一拍什么都不做：不记日志、不出字。
- 保存钮的状态 `saveState()` 在 `saving` 时返 `"saving"`（`:271`），不区分「那一次还在推」和「之后的改动还没落盘」。
- 图库家的崩溃影子就是自动保存，同一个开关挡着：这段时间本机副本停在上一次。

## 二、门口（开机 / 醒来的「核对网盘」）有哪几种结局

闸 = `src/app/cloud-gate.ts`，核对那一步 = `session.checkCloudOnce` → `refreshOpenDoc`。（读代码；④ 有日志佐证）

| 结局 | 什么时候 | 界面 | 日志 |
|---|---|---|---|
| 不出闸 | 没挂库 / 这台没账号 / 醒来时离上次通过不久 | 无 | `no account … → no gate` 等 |
| 照旧离线 | 之前选过离线 | 不出闸；后台静默试连一次 | `while offline chosen → no gate` |
| 通过 | 续签成了，核对在 8 秒硬时限内做完；或者核对进了「换字节」（硬时限暂停）后等它结束 | 罩子「正在核对网盘上的版本…」，换字节时「正在从网盘更新…」，按钮「先离线用」；通过后收起，跑「回来那一串」 | `gate: boot/wake pass Nms` |
| 先离线用 | 罩子上点了逃生 | 罩子收起；条「离线 · 还有 N 份没传上去」 | `gate: escape clicked` / `offline chosen (escape)` |
| 没连上 | 续签失败 / 8 秒没回 / 核对抛错 / 没网 | 面「网盘没连上」+ 原因（登录过期了 / 现在没有网络 / 网盘没有回应）+「重新登录」「离线继续」 | `gate: blocked reason=…` |

「通过」里面那一步，日志 `gate check <名>: <结果>` 的几种（`refreshOpenDoc` 的回执）：
- `skipped`：不是图库家 / 空白新稿 / 正在存 / 正在安家 / 现在推不了 → 不查。
- `dirty`：会话脏 ∨ pushPending；**或者库回了 dirty-skip——库问的 `localDirty` 是「会话脏 ∨ 闸已经放弃」**（`session.ts:838`）。没放弃 → 会话脏的先只落本机 → 走库的 open（回执丢失自愈，真分叉才弹面）。放弃了 → 直接返回，什么都不做。
- `in-sync`：云端没变。
- `fast-forwarded`：云端更新、本机干净 → 拉下来整份重开，状态行「已从云端更新「名」」。
- `escaped`：换字节时点了逃生，分叉在罩子的按钮里做了。
- **`other` 合了四种**：① 库回的别的状态（前一行日志 `refresh <名>: <状态> <原因>` 里有原文）；② 快进之后发现换了家 / 期间落了笔（画布留人的）；③ 快进后重开读不出字节（状态行「云端已更新，但重开失败」）；④ 抛错——下载失败、超时……只进调试日志（`refreshOpenDoc failed: …`），**界面上什么都不说，闸照样「通过」**。user 11-12 18:20:21 那次就是 ④：下载内容 `Load failed`，闸等了 14.8 秒才「通过」，眼前是本机旧的那份，没人告诉他没取到。

## 三、没改过的文件会不会被记成有改动 / 待传：不会。（读代码 + 日志佐证；没跑专门的探针）

- 「有改动」= 会话 `dirty()`（文档改动号 ≠ 存盘时的号）；「待传」= 会话 `pushPending`（只在一次保存的结果里设成真：`= !r.pushed`）+ 库的待传（只有保存进了库才会记）。
- 开机恢复、从图库打开、快进：`adopt` 把存盘号对齐、`pushPending` 清掉 → 干净。
- 点「先离线用」、登录过期选离线、下载失败：这几条路都不碰文档改动号、不调保存 → 不会记。只有真改过（或上次保存没推成）才会进保存、才会记待传。小黑屋 v3.0.21 修的「离线 / 登录过期时把没人改过的稿无条件记成欠推」那条路，三维没有。
- 日志里那行 `dirty` 的来历：18:20:31 开机恢复 a12b → 18:20:32.173 点「先离线用」→ 18:20:34.192 `gate check 20261111-a12b: dirty`。后台那次核对没停，库换字节之前问 `localDirty`，「闸已放弃」让它答了真 → 库回 dirty-skip → 会话记成 `dirty` → `checkCloudOnce` 看见放弃了就返回。**这行 dirty 的意思是「闸被放弃了」，不是「文件改过」，字面误导。** 佐证：18:21:04 退出登录时记的 `unpushed left in this browser: 0`。
- 已知会多算的（偏安全，`ai-docs/20261112-save-faithfulness-audit.md` 第九节）：空操作照样提交、撤回到存盘时的样子仍算改过、设置来回改——都要人动过手。

## 四、干净的本机副本会不会被清（读代码）

- 库：没有自动清（没有 LRU、没有容量上限；三维开着 `autoCacheOpenedFile`，打开过的都留本机）。删本机副本只有 `offload()`，库只在「干净 ∧ 在线 ∧ 同步过 ∧ 云端有完整一份」时删，否则抛错。
- 三维：只有一个入口——图库卡片上「移出本机」（`gallery-host.ts:65` → `session.offloadDoc`）。人点的，不自动。
- **2.2.7 那个毛病下的后果**：没传上去的那份在账上是「干净 + 同步过」→ `offload` 合法 → 人在那张卡上点「移出本机」= 把唯一一份新字节删了，云端是旧的。收 2.3.6 后账是对的，这条路跟着关上。
- 浏览器层：存储紧张时可以把整个源清掉，不分干净脏（MASTER §A 修订 1）；三维在打开图库 / 挂库的手势里请求 `persist()`（`main.ts:1886`、`:1916`）。
- 退出登录不删本机字节；还原出厂会删（护栏里的「N 份没传」来自库的计数，见下面第 6 条）。

## 五、三维里「靠库的保命机制才成立」的地方

每条：靠的是库的哪个机制 → 它不触发 / 换数 / 换时机时三维会怎样 → 三维这一层该凭什么成立。只列，不改。

1. **「正在存」靠请求时限才放得下**（`app-store.ts` 那段说明，已标欠账；`session.ts:945` 竖、`:1003` 放）
   - 靠：库的 Graph 请求时限（一次传完的上传 = meta 那档 30 秒，分块每块 120 秒）。推云挂住时只有它到点抛错，`save` 才返回。
   - 不触发（时限关掉、设得很长、浏览器的请求挂在时限管不到的地方）：`saving` 一直真 → 自动保存全跳、切后台 / 离页不存（都看 `!saving`）、人按存一直「上一次保存还在路上」、刷新前等 5 秒后连只落本机那一下也被挡 → 改动只在内存。同步库说明里「这个数两头都有人要」正是这一处：一个参数被两个目的共用。
   - 该凭：本机落盘是会话自己的一步，落完就放下「正在存」；推云另走一条线，不占着本机落盘。
2. **门口靠下载失败才放行**（`cloud-gate.ts:183` 硬时限 8 秒；`checkCloudOnce` 的 `onLongWait` → `pauseHardTimer`）
   - 靠：库的下载失败 / 下载时限。库一开始换字节，闸的 8 秒就停了，之后只等库的下载结束：成了 = 快进；失败 = `refreshOpenDoc` 吞成 `other` → 闸当「通过」。
   - 不触发：下载挂着不失败 → 闸一直罩着「正在从网盘更新…」，直到整文件那档时限（15 分钟）或人点「先离线用」。触发了也不对：「取不到」被当成「通过」，界面不说（第二节 ④）。11-12 那次 14.8 秒是浏览器的 `Load failed` 先来了。
   - 该凭：闸自己定「等多久就不等」（自己的钟，和库的请求时限无关）；到点或下载失败都如实说「没取到云端新版本，眼前是本机这份」，失败不等于通过。
3. **会话的 pushPending 靠库的待传计数才放下**（`main.ts` `offerPushLocalOnly` → `session.noteCaughtUp(left === 0)`；`session.resolveActive` 拿到 pushed / clean）
   - 靠：库的待传计数（`files.dirty.count()`）和 `resolve()` 的结果。
   - 计数错成 0（2.2.7 那个毛病）→ 会话这一层跟着清掉 → 心跳不补推、回前台核对可以快进 → 两层其实是一层（报告 a 第四节）。
   - 该凭：会话自己记「哪一次保存的字节推上去了」（统筹已定第二版：续推开始时记保存序号，做完只有库说没有待传 ∧ 这段时间没有新的保存落地才放下）。
4. **（新）「闸被放弃」借库的「本机有改动就不快进」那道检查来传**（`session.ts:838` `localDirty: () => this.dirty() || !!this.refreshGuard?.abandoned()`）
   - 靠：库在换字节之前问一次 `localDirty`（这是库保护「本机没传的改动不被云端盖掉」的检查）。人点了「先离线用」，后台那次核对并没有停，全靠库换字节前问这一下才不换。
   - 库要是换了问的时机（比如只在开始下载前问、换字节前不再问）：放弃之后这份照样被换成云端那份——人已经在离线用了，还没动手的那几秒里眼前的东西被换掉。副作用：日志写成 `dirty`，把查问题的人带歪（第三节）。
   - 该凭：放弃 = 闸自己的取消（真的停掉那次核对，或者回来的结果一律丢弃），不借「本机脏」这个保命判断来传。
5. **（新）退出登录时「下次开机还挂不挂这个库」只看库的计数，而且先数后落盘**（`main.ts` `cloudSignOut`：`left = files.dirty.count()` 在 `session.flushLocal()` 之前；`deviceKvSet(KV_ATTACHED, left > 0 ? "1" : null)`）
   - 开着的这份有没存的改动、又刚好推不成（没网）：数的时候是 0 → 不挂 → 落盘后这份成了待传，下次开机库不挂，它「藏」起来（字节在、看不见，直到重新登录）——和那段注释里的「不让它们藏起来」相反。2.2.7 的错计数同样会让它不挂。
   - 这一条主要是顺序错，顺带信了库的计数。该凭：先落盘再数；开着的这份三维自己知道有没有没传的（`dirty` / `pushPending`），并进去。
6. **（新）给人看的「还有 N 份没传」都只信库的计数**
   - 还原出厂的护栏（`factory-reset.ts:51`）、离开文件夹家的确认（`main.ts:1955`，同样先数后落盘）、回来那一串的问话和结果（`offerPushLocalOnly`）。`settleNoHome`（`main.ts:2170`）数不出来按 1 算，方向对。
   - 计数少了 = 护栏说少了：人以为都传了才点还原出厂 → 删掉没传的。
   - 该凭：「哪些没传」的账本按家规就是库（这一条该信它），但开着的这份三维自己知道，至少并进去；数之前先把开着的这份落盘。
7. **（新）门口从冲突面的回调里偷看人选了什么**（`session.ts:592–596` `conflictGate.lastOpenChoice === "takeCloud"`；回调在 `store-ui.ts:110` 记下）
   - 靠：库在 open 时弹冲突面、经 `ui.resolveConflict` 回调告诉三维人选了什么。三维据此决定要不要把眼前整份换成 open 返回的字节，而不是看 open 本身的结果。
   - 库要是不弹面就换了本机字节（它认为本机干净直接快进——2.2.7 错计数时可能这样；或者以后加了别的自愈路），`lastOpenChoice` 是空的 → 三维不重开：眼前是内存里的旧画布，库的本机副本已经是另一份；下次存会把眼前这份推上去盖掉（库认为谱系对，If-Match 能过）。**这一条是读代码的推断，没跑。**
   - 该凭：看 open 返回的结果（库给的字段，或者和本机原来那份比字节），不从界面回调里猜。
8. **（新，轻）心跳补推停不停，靠库的冲突回调竖起 attention**（`push-retry.ts:26` 看 `attention`；`attention` 只在 `main.ts:2362` `conflictGate.onDeferred` 里、库为自动保存调冲突回调时竖起）
   - 库换了冲突的处理方式（比如自愈了、或改成抛别的错）→ attention 不竖 → 心跳按节奏一直重推。后果是多推、多请求，不丢东西。
   - 该凭：会话自己记上一次推的结果（被拒 / 网络 / 成功），按结果定节奏。
9. **（新，轻）门口分辨「登录过期了 / 网盘没有回应」靠读库的诊断日志原文**（`cloud-gate.ts:31` `parseRenewFailure` 解析库写进 `ui.reportError` 的 `[auth] silent token renewal failed (…): name=… code=…` 那一行）
   - 不是保命机制，是拿库的诊断文字当接口。库改了这行的字样 → 原因码读不出来 → 一律当「网盘没有回应」，人看不到「重新登录」这条该走的路（钮还在）。`test/cloud-gate.test.ts` 对着库的 dist 核这一行，库改了会红。
   - 该凭：库给一个正式的结果字段（续签失败的原因码），三维不读日志。这要改库的接口，归统筹 / user。

## 六、顺带

- 报告 a 里说的「三维自己叠着发两次保存那几种踩不到」，第一节第 3 条是同一个原因：`saving` 旗让会话在三维这一层就不发第二次。代价就是第一节第 4 条：撞上时什么都不存、也不说。
- 第五节第 1、2、4 条在 user 11-12 那段日志里能看到同一件事的两面：门口等了 14.8 秒是第 2 条；之后那行 `dirty` 是第 4 条。
