- **I10 / I11 · 组件定义会被炸开顺手删（user 10-30）**：原话「为什么删实例会有删组件定义的风险？这个风险就不应该有。你看一下这是什么系统性的问题。一共有几层瑞士奶酪？」「为什么炸开会删除组件。我们没有一个中心化的按引用计数的东西吗？学blender……然后到时候也有这种引用和孤儿管理面板……你先非常认真小心地做。到时候fable审核」「这样，我们先写一个。然后高中时代让fable重写一个」「无人使用的材质会悄悄残留。这个现在小学时代能修复吗。」「反正就是要么被引用要么被素材库引用。和blender的逻辑一样」「能改成guid吗 然后物体之类的同理，定成家规」「不要用序号」。
  - 查到的（Opus 5.5）：删实例本身不删定义；**炸开**把一个组件的最后一份炸掉时会删定义（`ops.ts` 同种硬表面一处、跨种类一处）；**合并**恰好不删。同一件事三条路两种结局 = 定义的生死没有统一的主人，各个动词自己写。测试 `object-ops-kinds` 还把「定义没了」当对的钉着。孤儿森林（UX26，10-28）只钉了存读那一层。
  - 瑞士奶酪（「定义只在用户点清理时才死」这件事有几层）：① 场景模型 = 平表、实例只记定义编号 ✓；② 指令层 ✗（炸开两处删）；③ 存盘写 ✓；④ 读盘 ✓（③④ 同一条往返测试）；⑤ 撤销能找回 ✓（这是补救，不算防线）；⑥ 结构守卫 ✗（没有）；⑦ 指令层测试 ✗（反而钉着删）；⑧ 披露 ✗（炸开不说定义没了，孤儿哪都看不见）。
  - v0.18.3 补：② 炸开不删；⑥ 守卫 = 源码里不许出现删定义的写法；⑦ 炸开（两种身体）/ 删实例 / 合并之后定义一个不少；⑧ 炸开最后一份时提示「定义照样留在文件里」+ 资源清点（I10）。
