## 1. Opus 的评论（供 Fable 参考，不是结论）

- **方向对**。CatsUp 要的「画」和 WeebPaint 的「画」核心数据不是一个东西：
  - WeebPaint = 一张画布上的一摞图层；
  - CatsUp = 贴在网格上、每层有自己的 UV 和分辨率的贴图（§3 user「每个layer有独立的分辨率和uv」）。
  - 两边真正一样的是无状态的东西：笔刷怎么栅格化、颜色混合、重采样、选区 / 变换的数学。
  - 硬做一个两边共用的「画的东西（workpiece）」，就是那种「错误的抽象」：两个消费者谁改都要照顾对方，越改越歪。user 说的「两个 workpiece 打架」就是它。
- **Kokoro 只有 CatsUp 一个消费者**：做成 CatsUp 里的一个内部模块（目录）就够，不必出 `@internal/*` 包。包的意义在于多个消费者共享版本，这里没有第二个。
- **拿 WeebPaint 的东西 = 拷（vendor）进来，不是 import**：每次拷记下「从 WeebPaint 哪个版本的哪个文件」，反哺时同理。拷的单位是无状态的算法文件（笔刷栅格、混合、重采样），不拷 WeebPaint 的文档 / 图层 / 存储。
- **代价要说清**：两份同样的算法会各自修 bug、慢慢漂开。
  - 缓解：只拷无状态的、给每份拷贝记上游出处。
  - 等两边都稳定、同一个算法被第三处需要时，再把它抽成真正的共享模块（「先抄三次再抽象」）。
- **WeebPaint 不用 Kokoro 的代码**：符合 user 一贯的「可拔性」，Kokoro 冷落了也不拖累 WeebPaint。

## 2. 科普：「不结婚直接生小孩」在软件工程里有没有先例

先说清楚：下面是我（Opus）凭训练知识说的业界情况，没逐条上网核对年份细节，Fable 写稿前可以再核。

- **有名字的原则**：
  - 「宁可重复，也别要错误的抽象」：Sandi Metz 的说法，「重复比错误的抽象便宜得多」。
  - 「先抄三次再抽象」（rule of three）。
  - 共享代码的代价是耦合：两个消费者的需求一分叉，共享层就得兼顾两头。所以「拷一份、各自长」在两边模型不同的时候常常是对的；两边模型相同时，共享才划算。
- **图像 / 3D 赛道的例子**：
  - **Photoshop 和 3D 画**：Photoshop 曾经把 3D 功能塞进本体（「结婚」），后来把 3D 功能撤掉了，3D 画交给独立产品 Substance 3D Painter。这是最贴近 user 问题的先例：在 2D 软件里硬塞 3D 画，最后分家。
  - **Procreate**：两种都试过。3D 画是直接加进 Procreate 本体（2021 年前后，5.2 版），动画则单独出了 Procreate Dreams 这个新 app。
  - **Lightroom 和 Photoshop**：两个产品共用同一个 Camera Raw 引擎。是「共享一个无状态的引擎、各自的产品各管各的文档」，和 §1 说的「只共享算法、不共享 workpiece」同构。
  - **Blender 的 Cycles 渲染器**：既在 Blender 仓里，也有独立仓，别的软件也能用。是「孩子长大了能单独过」的例子。
  - **GIMP 和 GEGL**：GIMP 把图像处理核心抽成独立库 GEGL。走的是「抽共享库」那条路，是两边模型一致时的做法。
  - **Krita**：从办公套件里分家出来独立长大，分开以后发展反而更好。
- **结论**：两边模型不同、早期快速变化时，「生小孩 + 只拷无状态算法」是业界常见且被推荐的；等算法稳定了，再考虑抽共享引擎（Lightroom / Camera Raw 那种）。

WeebPaint 6-28 设计稿 `20260628-bodypaint-texture-space.md` 的结论（AI 写的，摘要）：

- 屏幕上画到一张笔画缓冲；落层时在 UV 空间把模型画一遍，每个贴图像素算出自己投到屏幕的位置，去笔画缓冲里取，即「贴图像素去屏幕上取」（gather）。
- 用深度测试防画穿。
- 和 2D 自由变换的 GPU 扭曲是同一个骨架。
- 比 Procreate 不漂移的原因：每个贴图像素按真实插值出的世界坐标投影，不用每个四边形的线性近似，所以位置保证对。
- 掠射面会糊，那是信息极限，转视角解决。

## 4. 给 Fable 的问题（出设计稿时回答）

1. **贴图的尺寸和采样方式归谁**。
   - 现状：文档里材质带 `sizeM`（贴图一张代表多少米）。
   - Opus 倾向：跟材质。同一张图可以在两个材质里按不同尺寸、不同采样用：像素风用最近邻，照片用平滑。
   - 材质窗口长什么样，是 user 点名要设计的。
2. **每层独立 UV + 分辨率**（§3.4 user 的设计）和 glTF 导出怎么接：导出时烘成一张，还是多套 UV / 多张图；「固定管线和 drawcall 肯定不接」那句的边界在哪。
3. **自动 UV 的存法**：user「autouv的时候也许不保存uv」。如果不存，读盘要重新展，结果必须确定，否则贴图会错位。这条和「派生数据只在内存不进文件」怎么对上。
4. **像素精确的保证范围**：画的位置保证对（6-28 稿 A 层）；掠射面糊是物理极限。CatsUp 的像素风风格（像素描边、1-bit）和贴图的最近邻采样怎么叠。
5. **Kokoro 的边界**：哪些文件从 WeebPaint 拷、拷到 CatsUp 哪个目录、上游出处怎么记、反哺怎么记；套索和变换（user「刚需」）先拷还是先自己写。

## 5. 显存 / 贴图池（user 10-30 追问）

user 原话：「texture pool那一系列肯定要，但是也得和我们自己的内存管理合并，而不是各管各的。不过也许反而是我们用weebpaint的架构我们迁移过去？以及渲染用的buffer也许可以另算？weebpaint的只管贴图，那么临时的呢？也归它？还是都weebpaint。以及如果我们都是小贴图怎么办，weebpaint是比最小还小就浪费了吗？」

事实（Opus 10-30 读代码）：
- WeebPaint：图层按 256×256 一块存（`common/tile-geometry.ts TILE_SIZE = 256`，一块显存 256 KB）。CPU 池是真本，GPU 池（`backend/gl/gpu-tile-pool.ts`）只是缓存，随时可扔、扔了从 CPU 重传。块装在一张贴图数组里，有钉住两档 + 最近最少用淘汰，容量按需翻倍。块尺寸是建池时注入的参数（`app-tile-pool.ts`），不是池子里写死的。临时的帧缓冲走 Port 的 `PooledFBO`。
- CatsUp：材质贴图每张一个纹理，各管各；渲染用的临时画面（像素风小图、辉光、遮蔽图集）也各管各；小栗鼠只事后估一个总显存数（`minccino/budget.ts vramMb`），没有统一的池。

Opus 的看法（给 Fable 定）：
1. **一本账、几个分配器**，不是一个分配器管一切。三类东西性质不同：
   - 能画的贴图层：CPU 是真本、显存是可扔的缓存 → 用 WeebPaint 那套块池，这部分迁过去，它是被验证过的。
   - 只读的材质贴图（从文件来的图）：可以扔了从文件字节重建，或者只降几级 mip。
   - 渲染用的临时画面：跟屏幕大小走，这一帧要用的不能扔，按尺寸租借复用（WeebPaint `PooledFBO` 同款）。
   - 三类都往同一本显存账上记（小栗鼠的预算已经有显存这一轴）。显存紧时按「临时画面不扔 → 能画的层扔 GPU 缓存 → 只读贴图降级」的顺序让路。
2. **不是整个 CatsUp 迁到 WeebPaint 架构**：渲染器、场景、编辑器都不一样；迁过去的只是「能画的贴图层怎么存」这一块。
3. **小贴图会浪费**：一张 32×32 的 GBA 式贴图放进 256×256 的块，块里 98% 是空的（64×64 是 94%）。CatsUp 偏爱复古小贴图，这事躲不掉。两条路：
   - 按尺寸分档：64 / 128 / 256 各一个池，块尺寸本来就是参数，开几个池就行。推荐。
   - 小图拼进共享大块：省显存，但改一张要重排，更复杂。
   - 另外，没在画的小贴图可以直接当普通纹理，不进块池。
4. **临时缓冲归谁**：笔画缓冲、预演、撤销差量这些临时的，归画的那一层（Kokoro / 块池那边）租借。渲染的临时画面归渲染器。两边都记同一本账。
5. **user 10-30 补「关键是我们会有3d texture，vao vbo 一大堆乱七八糟的，而且贴图大小也不规整」→ 账按字节记、按类别管，块池只是其中一类**：
   - 显存里的东西形状千奇百怪：体积贴图、网格的顶点 / 索引缓冲、大小不规整的材质贴图（非 2 的幂、长条）、渲染临时画面。只有「能画的贴图层」适合切成固定块。
   - 所以统一的是那本账，不是分配方式：每个显存资源登记「类别 · 字节数 · 能不能扔 · 扔了怎么重建（从 CPU 真本 / 从文件字节 / 这一帧现画）· 谁钉着它」。
   - 预算按类别看总数（小栗鼠预算的显存轴从「事后估」变成「这本账加总」）。紧的时候按类别的让路顺序扔。
   - 分配各管各：块池管能画的层；网格缓冲跟池网格走（现在就是每个池一份几何）；不规整贴图按原尺寸建；临时画面按尺寸租。
   - 和 three 的关系：现在 three 自己建、自己删这些东西，账要从 `providers/three` 那一层拿真实字节数（three 有内存统计，但不分类别、不知道能不能扔），这一步是渲染器契约的事，归 Fable。
6. **user 10-30「也许不能直接用」**：同意。WeebPaint 的块池默认「一张画布、固定 256 块、2D」；这边是很多张大小不一的贴图，还有体积贴图。大小不能被 256 整除的贴图边缘块会浪费，小图更浪费（第 3 点）。借的先是思路：CPU 真本 + 显存可扔缓存、钉住两档 + 最近最少用淘汰、批量分配、只在帧首扩容。代码能不能原样 vendor，Fable 出稿时逐个文件判。
