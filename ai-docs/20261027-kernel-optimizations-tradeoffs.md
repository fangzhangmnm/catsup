## O1 拖动预演每帧整份拷内核

**现状**：拖一个点 / 一张面时，每帧从真内核拷一份、在拷贝上跑动词、画出来（预演 = 看到的就是松手后的真结果）。全合并坦克（3.2 万面）每帧拷贝 95–166 ms；分件坦克最大零件 25–47 ms；iPad 上拖大物体 ≈ 每秒 6–10 帧。渲染那半（只重建改过的面）v0.14.52 已做，≈ 1 ms。

| 路 | 做法 | 代价 | 能省多少 |
|---|---|---|---|
| ❶ 拷一次 + 每帧退回 | 拖动开始拷一次；每帧先把上一帧在拷贝上做的改动按改动日志（已有的 Int32Array）逐条退回，再做这一帧 | 要证明「退回 = 没动过」，**含各表的遍历顺序**（Map 插入序：删了再插会挪到表尾 → 下一帧结算的追踪起点变 → 平手时预演和提交分叉）；改动日志要覆盖内核全部可变表（现在只记了面 / 边 / 顶点三张？要核）| 每帧 95 ms → 退回量级 = 上一帧改动量（拖一个点 ≈ 几十条）≈ 1 ms |
| ❷ 只拷会被碰到的池 | 已经部分做了（DT93：预演只克隆活动池）；再细 = 只拷活动池里影响域附近的部分 | 要定义「部分内核」并让结算机在它上面跑：结算机已经是 O(影响域)，但克隆 / 认领 / 平面登记是整池的；拆开 = 另一套边界契约 | 不确定；全合并坦克单池时省不到 |
| ❸ 摊平成数组（= O3） | 内核改列式类型数组，拷贝 = 一块内存 memcpy | 见 O3 | 78 MB 堆 → 拷贝几 ms，但整池仍每帧拷 |
| ❹ 可持久化结构（user 提的） | 像 WeebPaint 分 tile：没动过的分区共享，拷贝只复制路径上的节点 | 内核全部表换实现（Map → 持久化树），所有算法照旧；写得好是干净的，但工程量 = 把内核的数据层整个换掉 | 拷贝 O(log n)，每帧几乎免费 |

**推荐 ❶**，理由：改动日志已经存在（DT96 时铺的底），证明的形状和 T2 一样是「局部 = 全局」的差分对拍（预演一串帧后的拷贝 vs 每帧新拷），可以今天的测试框架直接钉；工程量一两天。❹ 更漂亮但要换数据层，和 O3 撞车——**等 mesh 内核落了再看 brep 值不值得换底**（SU 工作台拖大物体的场景比想象的少：硬表面大多是分件的）。❷ 不推荐（边界契约不值）。

**user 拍**：做 ❶（推荐）/ 先不做（现在的 6–10 帧凑合，先做 mesh）/ 直接上 ❹。

## O2 结算里还随整个模型涨的两步

**现状**（v0.14.58 实测，全合并坦克 3.2 万面 / 1.35 万平面）：①「含任一脏边的平面」每步 1–3 ms（包围盒先筛后逐边查，仍 O(平面数)）；② 推拉的影响域计算（被碰平面上的面）20–33 ms——不是扫全图，但最贵。

| 路 | 做法 | 代价 |
|---|---|---|
| ①a 给平面加空间索引 | 每张平面记它上面的面的包围盒并集（只长不缩 = 超集），脏边先查索引再逐边 | 多一张要维护的表；1–3 ms → < 1 ms |
| ①b 不做 | 1–3 ms 在每步 20–50 ms 里不显眼 | 零 |
| ②a 先量再切 | 20–33 ms 是「被碰平面上的面」逐张算包围盒相交 + 代表点测试；先 profile 哪一半贵 | 一小时的量 |

**推荐**：① 不做（①b）；② 先量（②a），量完再定——没有数字不动刀（家规「先量后优」）。都不值得现在排。

**user 拍**：同意 / 还是把 ① 做了。

## O3 内核改成按属性分列的数组 + 纯函数（WASM 纪元的正事）

**现状**：3.2 万面内核 JS 堆 78 MB（≈ 2.4 KB / 面）；Metasequoia 开同一只坦克约 +91 MB（口径不同）。已经按这个写的先例：渲染缓存（大数组、法线 16 位、颜色 8 位）、改动日志（Int32Array）。user 目标：「ecs级别的少存元数据和json overhead……能在水杉这种十几年前电脑上跑」。

| 路 | 做法 | 代价 |
|---|---|---|
| A 现在动 brep 内核 | 顶点 / 边 / 面 / 环 / 平面全换列式数组，算法改成不碰对象的纯函数 | **动红线区核心**；要先有「新内核 vs 旧内核」逐动词对拍网（user 自己说的）；工程量 = 重写内核数据层，周级；和 O1 ❹ 二选一 |
| B 先在 mesh 内核上这么写 | mesh 内核是新写的，从第一天就列式 + 纯函数（点坐标 Float64Array、环用 Int32Array 偏移表、边层用位图）；brep 以后照抄 | 零额外代价（本来就要写）；brep 的 78 MB 先放着 |
| C 只给 brep 做「只读列式镜像」 | 渲染 / 拾取 / 碰撞读列式镜像（已经部分是：渲染缓存），编辑态照旧对象 | 内存不降（两份），只是读路径快——已经做了的就是这个 |

**推荐 B**：mesh 内核第一天就按列式 + 纯函数写（这是 mesh 内核提案 .h 的一条硬要求），把对拍网、WASM 编译路线都在 mesh 上先跑通；brep 的改写等它证明了这条路再排，到时候 brep 的大物体问题（O1）顺便一起解。**不排 A**。

**user 拍**：B（推荐）/ A 现在就动 brep。

## O4 圆规 / 球规的求解器（v0.14.62 Opus 先做的三处取舍）

| 取舍 | 现状 | 另一条路 | 判 |
|---|---|---|---|
| ① 弯的轨迹不进一维合成器，只在光标附近产几个 0-D 点 | 圆 × 轴线 / 对齐线不会合成交点 | 把圆当「一维候选」进合成器：要给合成器加曲线 × 直线 / 曲线 × 曲线求交 | **接受现状**：尺规作图里「圆和轴的交点」确实会要（圆心在轴上画圆、找圆和轴的交点 = 常见），但现有的「圆上最近点」+ 轴吸附可以两步到位；真缺再加，不预支 |
| ② 秩：圆上 = 参考线档（3.5 px）；球面只比画图平面高一点 | 圆比边低、比轴高 | 圆当边一样高 | **接受现状**：参考几何不该压过实边（F-85 边 > 轴 > 栅格同一精神） |
| ③ 组件被非等比缩放时圆 / 球半径取平均（不退成椭圆） | 近似 | 真算椭圆 / 椭球 | **接受现状，但要披露**：非等比缩放的组件里用圆规时提示一句「这个组件被不等比缩放过，圆规按平均半径算」；真椭圆等有人要 |
| ④ 格式可选键 `circles` / `spheres`（空就不写，老文件和定稿指纹不变） | 对 | — | **对** |

**user 拍**：三处都接受（推荐）/ 哪一处要改。
