## 1. 现状哪里错了（对着代码说，不辩解）

`src/editor/xr-pointer-frame.ts`（v0.4.0）把手柄射线当「眼」、射线周围 80° 当一张 800 px 的虚拟屏，然后**原样复用桌面的平面投影数学**：

1. **1/z 奇点是真的，钳位只是遮羞布**。`angularPx` 是透视投影 `(x/z, y/z)`；`z = max(dot(rel, dir), 0.01)` 把 z ≤ 0（点在手的后半球）的整个 branch 压到「近乎无穷远」，而 z 在 0 附近（与射线夹角接近 90°）的点被投到几百万像素外。手在臂长处，几何常常就在手的侧面甚至身后——这些点的「屏距」没有单调性，求解器按屏距排序候选就会**吸到别的地方**（#4「画到别的地方」）。
2. **输入只有一样东西：手的 pose = 一条射线 (origin, dir)**（user 纠正：本稿初版把「可见性」交给头，错了——那正是 FPS 移植 VR「子弹从眼睛 raycast、玩家没法瞄准」的 bug）。遮挡/可见性与命中必须**同源于射线原点**：射线打得到的才算看得见，头只管渲染，不进任何求解数学。现状 `viewDir(p) = p→手` 这一点本来是对的；错的是把「射线周围」当成一张**平面视口**去量距离。
3. **ε 是角度，抖动被距离放大**。10 px @ 800 高 = 80°/80 = 1°。手柄姿态抖动量级 0.5–2°，在 3 m 外就是 3–10 cm 的横向摆动；桌面的 ε 是「手腕撑着的鼠标 + 屏幕像素」标定的，直接换算成手柄角度 = 把 2-DOF 的假设硬套到 6-DOF 输入上（#3「手抖难拾取」）。
4. **轴向动词在近平行处退化**。推拉/轴锁的第二点 = 射线与轴的最近点（`closestOnAxis`，分母 1−(a·r)²）。站在柱子旁边往上推、射线越来越接近竖直轴，最近点越来越病态；同时手要「指到 10 m 高处」= 仰到几乎竖直（#4「造不出高柱子」）。这是几何退化与「手要动 10 m」两个问题的交汇处。
5. **框选/marquee** 在 VR 里根本没有屏幕——现状只是没炸而已。
6. **v0.4.2 止血（已落，不是正解）**：① `xr-pointer-frame.ts` 对 z ≤ 0（手后半球）的点直接返回远点——镜像 branch 掐掉，脚下的地板顶点不再投到屏心被吸；② `editor.ts` 推拉自由拖 / 拖动阶段线工具 / 磁滞三处把 canvas 尺寸喂给了 800×800 虚拟屏的 (400,400) 光标（`vp()` 该是 `fvp()`），VR 里射线整个斜掉（A2 漏网，golden 没抓到因为桌面 vp≡fvp）。通天柱「只到腰间」= 这两条叠加的产物之一；真机复验归 user。

结论与 user 一致：**在 VR 里假设一张视口平面就是不鲁棒**。A2 把接口改名成「射线语义」只改了名字，数学还是投影。

## 2. 无奇点的射线几何（#4 的正解方向）

**把「角度尺」从平面换成球面。** 输入只有 (o, dir)，以射线原点 o 为球心（能 cope：求解器本来就是「射线 + 角距」，崩的只是把角距当平面投影算的那层）：

- 点 p 的距离 = 夹角 θ = ∠(dir, p − o) ∈ [0, π]。全球面单值，没有 branch，身后的点就是 θ > 90°，自然落选。
- 线段 [a, b] 的距离 = 球面上大圆弧 â b̂ 到点 d̂ 的球面距离。闭式：n = â × b̂ 归一化；若 d̂ 落在弧的扇区内（用 (â × d̂)·n 与 (d̂ × b̂)·n 同号判），距离 = asin(|d̂·n|)；否则取到两端点的角。参数 t 用 d̂ 在弧上的投影回推（沿射线的最近点仍是 3D 两线公垂，与现在一样）。
- 面 = 射线求交（现状已经是射线，没问题）。
- ε 的量纲改成**弧度**：桌面 10 px @ 800 高、50° fov ≈ 0.0109 rad；VR 直接用弧度（或按手速/距离自适应，见 §3）。同一个数在桌面就是 px / 像素焦距——**这才是「不维护两套」的真正落地：接口是度量（distance），不是坐标（chart）**。

接口形状（提案，pin 在这里等拍板；实现时回写）——**只有一条射线，没有头**：

```ts
interface PointerFrame {
  ray(): Ray;                        // (origin, dir)：命中、遮挡、角距全从它来
  angTo(p: Pt3): number;             // 点的角距（rad）= ∠(dir, p − origin)
  angToSeg(a: Pt3, b: Pt3): { ang: number; t: number };   // 线段角距 + 最近参数
  forward(): Pt3;                    // = dir；平面「面向度」用
}
```

桌面实现：`angTo` = atan(px 距 / 像素焦距)（小角下 ≈ 现值，golden 数值会微变——改动时重钉，属 A2 第二刀）；桌面的「眼」= 正交/透视相机的射线源，同一个接口。`marqueeScreen` 保留为桌面特例（VR 无框选）。`occludedBy` / `occludedSpansOnLine` 从 `ray().origin` 判（现状已是手，保持）。

**通天柱的几何**（user 案例）：推拉沿法向 n 的高度 = 射线与法向轴的公垂点 = `h_hand + D·tan α`（D = 手到柱轴的水平距、α = 仰角）——手抬到 89° 就是上百米，抬到 90° 平行无解（现状 `ppStuck`）。所以「手一挥通天」在纯射线模型里是**有的**（v0.4 到腰间是 §1.6 两个 bug），但 90° 附近灵敏度 ∝ 1/cos²α，抖一下就是几十米——这正是 §3「拖动期切手位移驱动」要接管的区间：射线定方向与起点，之后 h 随手的竖直位移 × 增益走，平行也不退化。

## 3. 6-DOF 输入模式（#3 / #5）

VR 手柄给的是位置 + 姿态，我们只用了姿态的射线。文献里的标准件（别重新发明）：

| 模式 | 出处 | 适用 | 对 CatsUp 的意义 |
|---|---|---|---|
| 直接抓（near-field direct manipulation） | 通用 | 臂长内 | 手的位置就是光标：零射线、零抖动放大，近处画线/推拉最自然 |
| HOMER（射线选、手动） | Bowman & Hodges 1997 | 远处 | 射线选中目标后光标贴到目标上，之后 **Δ光标 = G·Δ手，G = 目标距离 / 手距离**：10 m 外的东西手动 30 cm 就够——正面回答「不该拉 10 m 手也动 10 m」 |
| Go-Go | Poupyrev et al. 1996 | 中远 | 手伸出超过半径后非线性延伸；与 HOMER 二选一 |
| PRISM（速度增益） | Frees & Kessler 2005 | 精细 | 手慢 → 增益 < 1（精细），手快 → 1:1；抖动是高频小幅，自然被压 |

**与 SU 动词模型的结合**：每个动词的「第二点」= 一个「光标点 + 约束」的求解，求解器不关心光标点从哪来。所以：

- **第一点（拾取）**：远处用射线（球面度量，§2）；臂长内用直接抓（手的位置直接当点，ε 用米不用角）。两者按「手到最近命中的距离」自动切换或 grip 显式切换。
- **拖动期间（第二点）切到手位移驱动**：Δ光标 = G · Δ手（HOMER 增益，钳在 [1, G_max]），叠 PRISM 速度增益；光标不再是射线与几何的交点，而是一个跟手走的 3D 点，求解器对它做正常的轴/面/点吸附。**这一步同时解决 §1 的第 3、4 条**：抖动只进拾取（粗），不进拖动（细）；推拉沿法向的位移来自手的位移在法向上的投影，与射线夹角无关，没有近平行退化，柱子想多高手就往上带（乘 G）。
- **grip = 锁**（user 提议，我同意）：SU 的 Shift 锁推断 / 方向键锁轴在 VR 的对应物——拖动中按住 grip = 锁定当前推断（轴线 / 面上 / 点上，状态行显示锁的是什么），松开解锁；「悬在某条轴提示线上按 grip」= 显式轴锁（对应 #3「忘了 axis lock 的按钮」——不用记按钮，锁就是握紧）。
  - 竞争语义：grip 也常被当「离合器」（clutch：按住时手动不驱动光标，用来重新摆手）。两者冲突，要拍板一个。我建议 grip = 锁；离合器给摇杆按下或不做（HOMER 增益已经让手不用大幅移动）。
- **稳定化三件**（与上面正交，都便宜）：① 射线锚点改肩/肘（shoulder-anchored ray：从估计的肩点过手柄，杠杆 0.5 m，手柄姿态抖动不进射线；Quest 的 `targetRay` 是系统给的，改锚 = 自己算）；② 1€ filter（Casiez et al. 2012）滤射线方向；③ ε 磁滞已有（1.5×），可加按距离自适应。
- **尺度旋钮的统一**：rig 缩放（缩小帽 / 巨人，A13 phase 2）= 全局增益，HOMER = 局部增益，同一个旋钮的两面，可共存；缩小帽下 ε（米）也随 rig 缩。

**gizmo（#3 后半）**：move gizmo 本质是「约束 + 柄」，TRS 一体 gizmo（Blender/Unity 式）在 VR 可行，但它是一个 **mode 切换**（user 自己也说「这确实是不同的工具模式」），与 SU「move 一个动词吃掉 TRS、靠推断 + 锁」的哲学相左。我的判断：**先做 §3 的「射线拾取 + 手位移拖动 + grip 锁」**——不改动词模型、不加 UI；gizmo 留到 rotate/scale 立项（A13 phase 2）再评估，那时「轴锁柄」和「gizmo 柄」很可能是同一个东西。shear 不做。

## 3.5 激光笔 vs 平移手：如何权衡（user 追问，提案未拍板）

user：「平移手确实好用，不会有 2 投 3 的歧义。不过转动手腕的激光笔更爽。如何权衡」。两者是**同一个手 pose 的两个分量**（姿态 → 角度、位置 → 米），不是两套输入：

- 激光笔（角度）：增益大、快、爽；歧义只在**没有约束**时（自由空间的 2→3），而 SU 的答案本来就是推断（画图平面/轴/面锁）——激光 + 推断 = 现在的 SU 模型，别丢。退化处 = 射线与约束轴近平行（通天柱 90°）。
- 平移手（位置）：无歧义、无退化，但臂长有限、幅度小、远处要增益。
- **权衡 = 按阶段自动分工（HOMER 的形状）**：**取点用激光**（第一点 / 选面 / 选约束——远、快、爽），**拖量用平移**（第二点：锚定约束后 Δ光标 = G·Δ手 沿约束投影，G = 目标距离 / 臂长，钳 [1, G_max]）。扳机按下那一刻切换，激光仍显示但不再驱动；grip = 锁推断。不做两者混合（两路信号打架 = 抖）。playtest 若「拖也想用激光」，做成设置项 `pointerDrive: auto | laser | hand`，默认 auto。

**grip = 增量平移的离合器（user 同日深夜追加，提案未拍板）**：「grip 按住的时候可以切换成增量平移？但是松 grip 的时候增量是否保留？顺便一提无 grip 的时候你的 ray origin delta 也是无增量的平移，之前的手感不行就是 viewport 模式 disrespect 了 ray origin change」。我的看法：把 §3.5 的「按阶段自动切换」改成 **grip 手动切换**更可控——不按 grip = 激光（绝对：光标 = 射线∩约束，手的平移通过射线原点**绝对地**移动命中点，这就是「无 grip 时 origin delta 也是平移」）；按住 grip = 增量（光标 += G·Δ手，射线方向不再参与）。**松 grip 的增量保留到本次手势结束（扳机松开）**：手势中光标绝不许跳（跳 = 几何毁掉）；手势之间光标本来就是绝对激光，偏移自然清零。这样 grip 同时是「离合」和「精修」，与 §4 第 2 问的「grip = 锁」竞争——三选一仍待拍板。「viewport 模式 disrespect ray origin change」= 对的：平面视口把一切当成绕固定原点的角度，手一平移（原点变）近处候选的角位置剧变 → 抖；增量模式里光标直接吃 Δ原点（米），才是手真正做的事。

## 3.6 架构：同一路径还是两条路径（user：「现在的主要决策就是 vr 和桌面是用同一路径还是不同路径，如何尽量的保证 ssot 和不出错」；提案未拍板）

**语义一条路径，物理指针 N 个适配器。** 不变量：从「候选点 / 约束 / ε」往下（solver、pick、tools、editor 状态机）只认 `PointerFrame` = **射线 + 度量**，永远不认「图」（px 坐标）。桌面/VR 的差别只在把物理设备翻译成这个接口：

| 层 | 桌面 | VR | 契约（SSoT） |
|---|---|---|---|
| 物理 → 射线+度量 | OrbitCamera（px 度量 = 角度度量的伪装：tanθ·f） | 手柄射线（球面度量） | `PointerFrame`（§2）；ε 一个数（角度量纲，`solver.EPS`），适配器各自换算 |
| 第二点驱动 | 鼠标就是激光 | 激光取点、平移拖量（§3.5） | **平移驱动也做成一个 `PointerFrame` 实例**（`OffsetPointerFrame`：ray = 从被驱动点沿约束、angTo = 米距/ε_m）；editor 已有 `setPointerFrame`，适配器按阶段换帧 |
| 移动/碰撞 | 键鼠 → `InputFrame` | 手柄 → `InputFrame` | `src/player/` 已是 |
| UI | DOM | 手腕面板 / 字幕 toast | `HudModel` / `NoticeOpts` 已是 |

即：**「两条路径」只允许存在于适配器层**（`src/app/{gestures,vr}.ts`、`src/player/{flat,xr}-input.ts`、`ui/{dom,wrist,vr-toast}`），求解器/工具零分支。这和 render3（一个场景，相机由 XR 或轨道写）、HudModel（一模型两渲染器）是同一个形状——**模型一份，每设备一个适配器**。

**不出错的机械保证（不是靠自觉）**：
1. lint（v0.4.2 已落 `scripts/build.sh` 0.65）：editor 的 `frame().*` 必配 `fvp()`；指针数学禁直连 `this.cam`；solver/pick/tools/指针帧零 DOM/屏幕/相机；player 零 DOM/three/editor。
2. **等价套件（待做，A2 第二刀一起）**：每条求解器 golden 同时跑两个帧——桌面帧 + 一个射线与之相同的 `XRPointerFrame`——吸附结果必须一致（角度 ε 内）。这是「一条路径」的物理证明；现在的 golden 只跑 OrbitCamera，所以 vp/fvp 错配没被抓到。
3. 探针对偶：probe-hover/pen 的场景在 probe-xr-fake 里各有一份。
4. 适配器不许私藏容差：ε 只住 `solver.EPS`；适配器只做设备级判定（tap 阈值 `travelPx`、长按时长）。
5. 残留的桌面味搬回适配器：`canArm = pointerType === "mouse"`（点两下）应变成适配器给的 `armable` 标志；`marquee` 只由桌面适配器发起（VR 无框选）。

## 3.7 推断的多层 cue（user 同日晚追加，已含两条吃书；提案未拍板）

user 原话：「抱歉吃书：判断对齐哪个面的时候 (xy yz zx) 用头的方向」「画面的时候还是容易想画水平的会画成竖直的，然后在有几何的时候有时候一个水平面莫名其妙画到 z<0，虽然我几何都是贴着 z=0 摆的」「move 还是很难 snap to axis 的根因：在 vr/minecraft 里面，你会不由自主地对准正北正南。这样的话 z 和 y 重合，所以总会 snap to y。也许这时候虽然我还是希望激光笔的体验，但是手势可以作为一个 cue？然后这样的话也许头判断对齐平面也不一定要有。用手势来 cue 就行了。激光笔用来 raycast，手势来 cue。所以也许我们的推理引擎就是有好几层 cue，摄像机是一层，手势（flatscreen 没有）是一层，origin+dir 是最终精确定位的」

- **v0.4.3 已落**：`XRPointerFrame.forward()` = 头向（只喂 `pickByFacing` 选 xy/yz/zx；命中/角距/遮挡仍全从手）。「想画水平画成竖直」的机制 = `pickByFacing` 的 |fwd.z| ≥ 0.34（≈20°）门：站着看 5 m 外的地面只有 19° → 落到「最面向」的竖直面；头向比手向稳，但门槛本身仍是桌面口径，待 cue 层接手。「z<0」候选 = 竖直平面被选中后射线打到地面以下（同一机制的副产物），头向后应减少；真机复验。
- **正北的 Z/Y 重合**：从手的射线看，锚点出发的 Z 轴线与 Y 轴线在角度尺上重合（Y 的消失点在地平线中心），任何单射线度量都分不开——等秩候选取第一个 = 永远 Y。这不是 ε 的问题，是信息不够：**需要第二个信号**。
- **cue 分层（user 的框架，我同意）**：① 相机/头一层（选平面的面向度；桌面也有）；② 手势一层（VR 才有：手的**位移方向**——往上抬 = Z、往前送 = Y，与 §3「拖动期切手位移驱动」是同一件事：位移既是 cue 也是量）；③ origin+dir 最终精确定位（激光 raycast）。在求解器里 = 候选排序多一个「与 cue 方向的夹角」项（rank 相同时用 cue 破平局；cue 明确时可压过 rank 一档），位置/命中仍由射线定。桌面无②，退化为现状 = 一条路径两种 cue 集，符合 §3.6。
- **待 user**：手势 cue 的判定阈（位移多少算「明确」，臂长内 5 cm？）；cue 只破平局还是能压 rank。
- **v0.4.4 转折（user 桌面复测 + SU 实测）**：「不是顶面吸附，而是 z 轴的容差比较小…SU 的 move effectively 就是三个轴三选一…也许这样我们能做的纯激光笔，不需要手势，那就超级舒服了」→ **已落**：move 自由拖 = 宽锥三轴三选一（`inferAxisByDirection`，六个 60° 锥，方向来自光标相对锚点的角度尺位移——这就是「相机/射线一层」的 cue 用足了；锥外 = 屏幕平面；擦射线不甩）。正北 Z/Y 重合的问题在这个模型里变成：Y 与 Z 在角度尺上投影方向相同时（消失点在屏心）两锥重叠 → 取夹角最小者仍是并列 → 需要打破平局：现状取排序第一（x,y,z 顺序 → y 赢）。**手势位移 cue 的必要性从「必需」降为「破平局」**——等真机说话。
