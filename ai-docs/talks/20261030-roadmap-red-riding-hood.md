- **Opus 核过的现状**：代码里还没有 UV 展开、骨头、蒙皮、关键帧（搜不到）；参考窗（第五个宿主）、两套建模、渲染器骨架、数据引擎都在；结婚有两份稿（10-24 方向稿、10-30 素材稿），「贴图像素去屏幕上取颜色」那套像素对齐的思路六月 WeebPaint 时就定了；动画已拍的：化身 = 骨架 + 蒙皮 + 一串 clip、只编辑每个 clip 自己的时间轴、编排是另一种身体、摆姿势走全身 IK（物品栏稿 §6）。
- **Opus 的看法：大体同意，但不全是手柄。** 这次贵，是因为几何内核是「手感数学 + 拓扑必须对」，边做边冒边角（推断、焊、镜像中缝……），Fable 一轮轮重想。后面的大部分是教科书算法，加上大量界面和手柄（Opus 便宜但量大）。真正难缠的剩这几块：
  1. **自动展 UV**（人和怪物这种有机形状：切缝 + 摊平）：成熟算法，要解一个大的稀疏方程组。要下功夫，但不是科研。
  2. **每层自己的 UV 跟着面的身份走**（user「加了手臂在新层画……每次topology change只是以前的layer部分坏了」）：这是设计 / 身份问题，不是数学问题，和 GUID 那批是同一个地基，归 Fable 定。
  3. **在模型上画**：思路已定，是 GPU 上的一遍渲染，难度中等（接缝渗色、掠射角糊是已知的坑）。**笔刷手感的钱 WeebPaint 已经付过了**，拷过来就行。这是贴图比看上去便宜的主要原因。
  4. **自动蒙皮权重**：常用做法是在网格上解热扩散方程。数学不难写，难在脏网格（断开的零件、没封口的洞、叠穿的衣服）。Blender 有名的「Bone Heat Weighting: failed to find solution」就出在这里。
  5. **自动摆骨（user 说的科研）**：任意模型自动找关节是真科研；限定「人形 + 一套模板骨架 + 人拖几个点对齐」就退化成好做的拟合 + 手柄。
  6. **全身 IK 的手感**：两节骨头的手脚有现成公式；MMD 自己用的是简单的逐节逼近加角度限制。但「抓手一拖、身子自然跟着走」是手感数学，和 SketchUp 推断同一类。Opus 猜这是后面最可能再烧 Fable 的一块。
  7. **（user 没提，列出来让你知道）MMD 的头发 / 裙子物理**：要的话最省事的是 vendor 一个现成物理引擎，自己写是大坑。
  8. **时间轴、clip、动画资源管理**：插值曲线、四元数转动都是教科书内容；主要是界面量 + 数据格式（动作 = 可复用的资源、按 GUID 指骨头）。格式归 Fable 定一次，其余归 Opus。
- **两块共同的依赖**：1 和 4 都怕脏网格。从自由建模做出来的人物网格干不干净（闭合、没有叠面），Opus 没核过；第一次全流程跑小红帽，最可能在各段之间的接缝上冒出没计划的活（导入小红帽 glb 时平滑组那次就是一例）。
- **吃 token 的粗估（猜的，没算）**：Fable 会比这次少，因为剩下的手感数学主要是全身 IK 一块，笔刷手感已有；Opus 的量不一定少，因为界面和手柄多。
