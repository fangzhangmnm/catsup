  - 「新的一周开始了，我总算下定决心来挑战这个事情。我的建议是，比起先做贴图材质，我们得把整个结婚纪元给规划好。还记得我后来拍的吗？就是不结婚直接生小孩。这就代表着说，我们实际上是要抄。那个画画库里面的代码，并且保证可移植性。当然，我们肯定也是要一步一步来，对吧？」
  - 「所以说，可能我们最一开始也是贴图， 和材质， 然后这一轮非常痛苦，我跟你打赌会非常痛苦，而且可能一个礼拜痛苦不完。的毕业条件就是我能进行最基本的手感不差的在模型上的贴图绘制，可能有些功能能慢慢的加。」
  - 「所以现在当务之急是从非常高软件工程，就你想象你是一个软件的高管……去一开始规划好我们整个的这个结婚的途径，要求很简单，就是。当我们在慢慢的，可能我们一开始只支持最普通的画和橡皮，对吧？但等我们的慢慢加功能的时候，每次增加一个新的功能的复杂度，不会随着我们已有功能的复杂度增加，而是甚至最好是越后面的新功能抄起来加起来越方便。」
  - 「然后我同时也授权你。对 v i b Paint 的核心进行 fork，然后改，或者说，甚至你可以直接拿到授权，直接推新的这个画画软件的版本，对它进行重构。就是说，相当于我们在生小孩的时候，我们同时也会让父母跟小孩对齐。但关键就是说，我希望我们在这个施工的过程中不会越后面越难，就相当于，比如说从你的立场、你的感受来说，就是相当于在后面不会，你每加一个新功能，你需要阅读的代码量越多，我们需要这么一个很好的规划」

- **这轮 user 定了的**（原话里直接有的）：
  - 先规划整个结婚纪元，再动手。
  - 路子 = 不结婚直接生小孩 = 抄画画那边的代码，并且保证可移植。
  - 这一轮的毕业条件 = 能在模型上画贴图，最基本的，手感不差。
  - 要求 = 加新功能的复杂度不随已有功能涨，最好越后面越方便；衡量办法之一 = 加一个功能要读的代码量不越来越多。
  - 授权：可以改画画的核心、可以推画画的新版本做重构，让两边对齐。（Fable 读法：推的是开发版；正式版照家规另问。）
- **Fable 读了两边代码之后的看法**（详见设计稿）：
  - 画画的后端已经自成一体（约 1.7 万行，只依赖自己和四个 vendor 库，几乎零界面接口）；工具引擎约四千行也零界面，只是文件还在界面那一层。
  - 成本不涨靠一条规矩：工具只认识一块平面（笔画台），三维只写「推」「拉」两个口。
  - 两边用逐字节同一份内核（正本在画画仓，三维机械拷贝）。这条改了 10-30「独立的小孩、可以冷落」的说法 → 要 user 拍。
  - 两条路不是二选一：角色当考卷，白模阶段冒出来的操作问题小版修，和内核整理并行。架构对只保证不返工，不保证好用。
- **等 user 拍的五件**：同一份内核还是各自长；画属于物件还是材质；用 ORA 存；第一笔排在材质窗口前面；两个正式版要不要先推。
- **Fable 先按默认走的三件**（没拍，user 不同意就改）：浮着的图转视角时贴屏幕；一笔只画进当前站在里面的那个物件；笔的大小按屏幕算。
