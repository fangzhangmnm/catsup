## 11-10 · 开题
- **user 原话**（语音转的字，照抄；「v i b Paint」= WeebPaint）：
  - 「新的一周开始了，我总算下定决心来挑战这个事情。我的建议是，比起先做贴图材质，我们得把整个结婚纪元给规划好。还记得我后来拍的吗？就是不结婚直接生小孩。这就代表着说，我们实际上是要抄。那个画画库里面的代码，并且保证可移植性。当然，我们肯定也是要一步一步来，对吧？」
  - 「所以说，可能我们最一开始也是贴图， 和材质， 然后这一轮非常痛苦，我跟你打赌会非常痛苦，而且可能一个礼拜痛苦不完。的毕业条件就是我能进行最基本的手感不差的在模型上的贴图绘制，可能有些功能能慢慢的加。」
  - 「所以现在当务之急是从非常高软件工程，就你想象你是一个软件的高管……去一开始规划好我们整个的这个结婚的途径，要求很简单，就是。当我们在慢慢的，可能我们一开始只支持最普通的画和橡皮，对吧？但等我们的慢慢加功能的时候，每次增加一个新的功能的复杂度，不会随着我们已有功能的复杂度增加，而是甚至最好是越后面的新功能抄起来加起来越方便。」
  - 「然后我同时也授权你。对 v i b Paint 的核心进行 fork，然后改，或者说，甚至你可以直接拿到授权，直接推新的这个画画软件的版本，对它进行重构。就是说，相当于我们在生小孩的时候，我们同时也会让父母跟小孩对齐。但关键就是说，我希望我们在这个施工的过程中不会越后面越难，就相当于，比如说从你的立场、你的感受来说，就是相当于在后面不会，你每加一个新功能，你需要阅读的代码量越多，我们需要这么一个很好的规划」
  - 「实际上那个写歌软件、写作软件和画画软件，我都是用他们有这些比较专业的产出的。但是建模软件一直都没有。我上次是 Game Jam 做一个小房子的时候就出事了，就发现我平时测试玩的时候很方便，但我真正用到 Production 里面的时候，发现有些东西非常不方便或者做不了。所以我会觉得说，如果我们不做贴图纪元，还有一个选项是，我就老老实实的去做一个二次元动漫角色人物。看能不能跑通，然后在做这个的过程中，我能慢慢的把很多操作上面的问题给暴露出来。」
  - 「实际上，我觉得我们这些软件比起那些纯用 AI 写的软件，最有价值的是我是个艺术家，就是说我在边用边做。这个时候我提的反馈是非常重要的……只有我在创作的时候，反而是开发的高峰期。」
  - 「我开始创作，但是我创作的话，我最后肯定会卡死在白膜那一面，没法做贴图，对吧？……如果是创作的话，反而是 UX 方面就。虽然会卡住人类，但是可能从软件工程角度来说，只是改一下接线，就是说这个是不是要放在后面，甚至是可以在施工的过程中一起做。但还有个问题就是说，如果我们一直没有实际的创作实践去 grounding 的话，会不会飘得太远？还是说，其实只要我们这个架构对、数据结构对的话，就不会有太大的事情？」
- **这轮 user 定了的**（原话里直接有的）：
  - 先规划整个结婚纪元，再动手。
  - 路子 = 不结婚直接生小孩 = 抄画画那边的代码，并且保证可移植。
  - 这一轮的毕业条件 = 能在模型上画贴图，最基本的，手感不差。
  - 要求 = 加新功能的复杂度不随已有功能涨，最好越后面越方便；衡量办法之一 = 加一个功能要读的代码量不越来越多。
  - 授权：可以改画画的核心、可以推画画的新版本做重构，让两边对齐。（Fable 读法：推的是开发版；正式版照家规另问。）
- **Fable 读了两边代码之后的看法**（详见设计稿）：
  - 画画的后端已经自成一体（约 1.7 万行，只依赖自己和四个 vendor 库，几乎零界面接口）；工具引擎约四千行也零界面，只是文件还在界面那一层。
  - 成本不涨靠一条规矩：工具只认识一块平面（笔画台），三维只写「推」「拉」两个口。
  - 两边用逐字节同一份内核（正本在画画仓，三维机械拷贝）。这条改了 10-30「独立的小孩、可以冷落」的说法 → 要 user 拍。
  - 两条路不是二选一：角色当考卷，白模阶段冒出来的操作问题小版修，和内核整理并行。架构对只保证不返工，不保证好用。
- **等 user 拍的五件**：同一份内核还是各自长；画属于物件还是材质；用 ORA 存；第一笔排在材质窗口前面；两个正式版要不要先推。
- **Fable 先按默认走的三件**（没拍，user 不同意就改）：浮着的图转视角时贴屏幕；一笔只画进当前站在里面的那个物件；笔的大小按屏幕算。

## 11-10 晚 · 第二轮：草稿和套索是创世纪；不只是界面和容器，是数学
- **user 原话**（语音转的字，照抄；「v i b p a n t」= WeebPaint，「液画」= 液化）：
  - 「把这个角色的脸在模型上画出来 / 我跟你说件鼓舞士气的话，这个东西 Blender、Procreate 都接不住。」
  - 「对，我们现在就是需要有 v i b p a n t 级别的手感，但是我们要知道，就是我们这个画画软件，实际上本质上我们要画对联，我们实际上是要磨草稿，我们需要有套索。液画其实没套索好用，就是你看液画我后来加的，但其实是套索上线之后我就基本能画了，液画反而对调整形体没有想的那么有意义。但关键一个是套索，一个是草稿图层。」
  - 「还有一个说明题是草稿会不会跑到我们这个模型的投影外面，对吧？但是我们可以想一下，三次元里面我们手办师他们是怎么画的，对吧？可能我们不一定需要有一个很好的二维的 grease pencil 的支持，而只是说在三维上。」
  - 「但是我们草稿笔和套索，这个是我们这个画画软件一开始活下来创世纪的第一个东西。就你要我真正的画，而不是说先想好，先在二维上画好，只是一个施工，只是一个坡，而是说我真正的一个绘画水平不好的人，他能在上面很细致的调你这个眉毛，调你这个眼睛，草稿笔和套索。」
  - 「为什么你会觉得只是界面和容器，而不是数学？你看一下我当时说的像素变换和逆变换的那个讨论，然后还有就是我们说的自动贴图、自动 Atlas。 我们当时是有好多设计的，我们这些也要考虑上了。就当时我设计了好几个方案，是用户不用手动管理 UV，而且在更改了模型之后，还可以接着画，就是画好贴图之后，你可以更改模型，不会造成毁灭性的打击。你看一下当时我的思路是什么样的。」
- **这轮 user 定了的**：
  - 毕业条件 = 「把这个角色的脸在模型上画出来」。
  - 草稿笔（草稿图层）和套索是第一批，和笔一起；液化没有套索有用。
  - 要的是能在模型上真的画、磨草稿、细调眉毛眼睛，不是把二维画好的东西贴上去施工。
  - 草稿不一定要二维的支持，在三维上就行（Fable 读法：倾向画在表面上；user 说的是「可能」）。
  - 三维这边是数学，不只是界面和容器；以前讨论过的像素变换和逆变换、自动铺、自动打包、改了模型接着画，都要编进设计。
- **Fable 找到的「当时的讨论」**（三处；如果 user 指的是别的一次，待补）：画画仓六月稿 `20260628-bodypaint-texture-space.md`（贴图像素反算屏幕、同一个逆映射骨架）；10-28 视口设计笔记 2.6 节（屏幕有变形时鼠标的逆变换）；10-30 `20261030-pixel-uv-straighten.md` 十二轮 + `20261030-bodypaint-kernel-uv.md` 八轮（自动铺、只平移打包、像素不变、Ptex 兜底、硬边当线稿、带子按面积比例拉直）。
- **Fable 承认第 1 版错在哪**：把「拉」写成了「把一层画成平面图再投回去」，套索每抬一次放一次就糊一次；套索排在第三段、图层排在最后；UV 那批只写了「照旧有效」，没编进架构；整体把三维这边写成了接头。
- **第 2 版改了什么**（设计稿第四½节，Fable 的设计，没拍，两条标了没验证）：
  - 内核只会「照一张坐标表取样」，是它现有浮层变换的推广；相机、深度、矩阵全在三维这边，算成表（落点表、回读表、邻面表、换铺表）。
  - 看不看得见 = 来回一趟回到自己，代替调深度容差（没验证）。
  - 套索三档：原地放下一个字节不变；沿贴图格挪无损（画画软件的套索原样跑在贴图上）；屏幕上自由变换只取一次样。
  - 补边里放缝对面那张面的颜色（按邻面展开），任何工具写完统一补（没验证）。
  - 改模型的七条规则；面的来历由建模操作当场交代（全仓 45 处新建面），不靠猜；镜像两半共用像素。
  - 加一个「从现在的视角铺」（小红帽的脸的铺法），排第一批。
  - 草稿 = 这份画里的一层，画在表面上，落在模型外的不留。
  - 路线改成：整理内核 → 第一笔 → 能磨草稿（毕业）→ 铺得好 → 接住现成的 → 往后。
- **还等 user 拍的**：第一轮那五件没变（同一份内核 / 画属于物件 / 用 ORA 存 / 第一笔和磨草稿先于材质窗口和导入 / 两个正式版要不要先推）。
