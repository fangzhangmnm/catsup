# 讨论日记：物体上的数据——属性列和数据块（2026-11-13 夜）

> created 2026-11-13 by Claude Fable 5.2（Catsup统筹）。原话是语音转写，照录；统筹的读法另标。结论落在 [物体上的数据：制度和登记册](../20261113-object-data-registry.md)。

## 经过

1. **起因**：第 1 版做「把画拿掉」。统筹先同意小弟的做法（只换材质），接着发现拿掉之后物体仍被当成带着画、转不了硬表面，于是改定成「拿掉时把贴图坐标也交出去」。
2. **user 纠正**：「代价：脱钩之后要把画放回去只能撤销，提示行会照实说。你没抓住重点，这个本质是脱钩的时候需要丢uv吧。我们的纪律，根据我们的纪律应该是这样的，就我们前面说的那些 attribute，就是说在转换的时候会丢 UV。我觉得是这样，首先是我们这个 UV，我们在脱钩的时候是可以不用丢的，然后转换的时候，如果我们转换的时候已经写好了。对脚点数据的处理的时候，这个 UV 也是不用偷的，就是原则上现在不用丢 UV，就是原则上，即使我们没有做这个 BRAP 的贴图功能的话，我们转一千再回去，它 UV 实际上还是拿得到的。你重新查一下，我觉得你这里思路可能有问题。」
   - 统筹认的错：物体被一道拦挡着，统筹去删数据迁就那道拦，没去改那道拦。
   - 重查的事实：自由建模之间搬面，列本来就跟着走；转硬表面时角上的列全丢，因为硬表面内核没有属性表、没有地方放角上的数据。
3. **user 问坐标架**：「画图用的坐标架，改成三个种类都能存。 解释一下画图用的坐标架是什么？这个概念是干什么用的？我觉得它是你发明的，你没有跟我说过」。统筹答：就是尺规里「坐标架」工具摆的那一套原点和三根轴，叫法是统筹照代码名字硬翻的。user：「同意，转换坐标架的时候不丢，坐标架不是原点，而且以前我也说过自由建模也应该有坐标架。」
4. **user 说老版本开新文件**：「你不要再在老版本程序打开新版本文件会出 bug 这面这上面浪费太多时间行吗？我们发正式版都是在考虑，平时不要考虑这个问题。」统筹把那两件从要处理的事里拿掉。
5. **user 问哲学**：「我们现在有个设计决定，就是我们挂拿掉画的时候，要不要自动清相应的属性列，还是让用户清？这是一个很有意思的 UX 决定。你帮我想一下哲学。」又问：「你跟我解释一下为什么不能转？然后现在是能把硬表面建模的 UV 支持也给做掉吗？我真的不理解为什么硬表面现在还不支持。」
   - 统筹的看法：不自动清——拿掉是收起来，清理才是扔掉，自动只做收不做扔；列的生死跟着引用走。硬表面带不了贴图坐标是三处没做（没地方放、改的时候跟不上、转过去会并面），原理上可以。
6. **user 提出制度**（原话在登记册第零节）：物体上挂的是一块一块的数据，换种类时不认识的原样留着、变灰、能手动删；属性一个面板、数据块一个面板；「我们先把这个 attribute 和 property 给设计一下」；自由建模的坐标架工具「我建议是也做，但我们可以把它给推一下之后再设计」。
7. **user 定优先级和硬规矩**：「我们现在优先做印表面接 attribute 系统。我的要求是以后这些物体所有的属性，要么是 attribute，要么是 property，没有别的地方可以存，就所有的东西我们都要记录在册。你写一下数据文档」「我建议是优先做 attribute 和 property，我们现在优先做，这个是筑基」。额度：「相当于我 Fable 可以相对多用点，OP 是可以省点。就这个东西，我说你要不要多出点力？」

8. **user 看了第一稿**：「「不认识的就无脑原样保留」对数据块成立，对属性列不成立。同意同意」。生死按引用、不自动删：同意，并要一个清理的功能和一个共用的清理窗口（原话在登记册第零节；设计在第六½节）。
9. **user 的新想法**：种类本身也只是一个数据块，像 Unity 那样挂上去就变；让统筹批判。统筹：对一半——种类降成「物体带着哪一块几何」之后，空物体和以后的灯、相机、角色都自然落位；不行的一半——几何不能灰着留着、只能有一块、它就是元素本身，所以只能是规矩单列的特殊一块。建议做成特殊的几何块，等 user 定。

10. **名字**：user「其实我比较想叫 property，就一个叫 attribute，一个叫 property。」「正好两个中文名字都叫属姓，你可以想下分别怎么分」。统筹提：元素属性 / 物体属性，按「是谁的属性」分。
11. **user 纠正统筹对第 9 条的读法**：「你理解错我意思了，或者说你的反驳反而是我想表达的意思。就像 Unity 里面 transform 是每个物体必带的」——几何是必带的那一个、是基类，元素属性挂在基类上，基类派生出各个种类。统筹认：说的是同一件事，user 的说法更准。
12. **user 要设计时考虑以后的几何**：高度图地形、方块世界的 chunk、Marching Cubes 的光滑体素；「chunk 的话反而不能走 attribute……是每个 chunk 是一个物体吗？」统筹：chunk 不是物体，是几何内部的储存单位（像画布的瓦片）；道理上还是元素属性，要改的是容器（分块存）；契约里预留「属性表不许写死成一整个数组」。细的在登记册第五½节。

13. **图元**：user「元素容易让人想到魔法，我还是想争取一下图元。但是我们也有非显示的attribute」。统筹支持：图 = 图形不是显示；和像素、体素同一种造词法；SketchUp 中文版的边和面就叫图元。attribute = 图元属性，property = 物体属性。
14. **一项只管一件事**：user 提每张表各是一项 property、不要一项里塞很多、没有就是默认、复杂的聚合也支持但最好是字典。统筹同意，并指出它让「对照表」成为一个共用模块（合并、重新对号、清理没人用的行只写一份）；提醒别拆过头（必须一起变的字段留在同一项）。写进登记册第五节。

15. **chunk 和无穷大的地形**：user 确认 chunk 是里面怎么存、对外不透明；要无穷大的地形，画的时候不用先想好多大（没经验的人会填一千、两千然后刷死）。统筹：没有的块 = 默认值，摸到哪长到哪，和「没有那一项物体属性 = 默认」是同一条规矩。
16. **文件格式**：user「我们在把这个做完之前，不要做任何后向兼容。做完之后，我们的文件格式升一个大版本，然后专门做一个移植的小小程序。」「在我说可以了之前，你不用假设我有产生新的文件」。统筹同意，补三处做法（冻一份现在的读法当转换程序的前半段；转换做成软件里明着的动作；中间版本默认不推开发版）。写进登记册第六¾节。

17. **往远了想**（user 要统筹仔细想、批判）：图元属性那本字典挂在物体上还是挂在某个部件上；chunk 是另一种数据结构怎么办；粒子系统、实例系统、volume 各是什么。统筹：字典是几何的一部分（几何是必带的那一个，不是物体属性）；图元属性 = 从图元到值的对应，存法分列表型和格子型两家，人眼里是同一个概念；粒子系统不是几何（设置是物体属性，粒子是算出来的）；成批的实例是一种列表型的几何；判断法 = 有没有各自的身份；三处要防（别做成游戏引擎、一个物体一份几何、整个物体一个值的只归物体属性）。写进登记册第五½节。

18. **user 回「往远了想」**（原话两条，照抄在登记册第零节）：
   - 同意的：属性跟着几何走；图元属性 = 从图元到值的对应、按名字分列、怎么存归几何；判断法「有没有各自的身份」（user 的例子：全面战争里一个 unit 是物体，里面的兵是图元）。
   - **硬规矩**（user：「这个是硬规矩，进设计文档」）：整个物体一个值的一律是物体属性，图元属性严格每个图元一个值。
   - **纠正统筹**：「别做成游戏引擎」是错的。目标一开始就是游戏引擎，专做数据驱动的场景编辑器；引擎长成那样是为了图形和物理的性能。统筹认错：以前定的边界划在规则上（规则不写死进核心），不在数据上；统筹把两件事混成了一句。换成 user 的那条：同一样东西只做一份。
   - **物体属性这一层的 ECS**（user 提）：不定长的各放各的，小而整齐的做成跨物体的大数组；排布细节等超大场景再做；同一样东西绝不做两份。统筹同意，提四个今天留的口子（声明里一栏「形状」、定长的只放数、一个入口、一个意思登记一次），写在登记册第五¼节。
   - **算法只经物体属性和图元属性访问数据**（user，像 Blender 的 Python 接口；性能要保证）。坐标架、硬表面里的组都得是其中一种。统筹对组的读法：一列代号 + 一张对照表，各组各用一个池子是存法。
   - **格子型第一天就按块**（user）。统筹读作「格子型的第一天」，不是现在就写。
   - **「一个物体只有一份几何」**：user 说这个想法很特殊，要统筹想好处和代价。统筹：它是 Blender 物体和 USD 节点的做法做得更严，建议守住；真正的代价是不同种类之间不能共用点和边，别的都有办法；代价表在登记册第五½节。统筹同时更正自己上一轮对 Blender 的说法。user 还没表态。

19. **user 回四个口子、组、施工单的默认**（原话照抄在登记册第零节）：
   - 四个口子：可以；定长的记录就是 C 的 struct。
   - 组：装着所有组的容器是一项物体属性，不是每个组各算一项定长的属性。
   - **新要求，筑基阶段就做到：没有隐藏数据。** 程序里读到的 = 文件里写的；不认识的东西交给用户处理；物体属性和图元属性就是文档的数据结构，以后可以慢慢不靠 glTF；这一版做完，几何里所有上盘的数据都看得见有哪些（不用逐个能改）；图片和音频以后做。问能不能做、现在图元属性是不是存在 glTF 的数组和 blob 里。
   - 统筹答：能做。现状 = 文件是 .glb，标准的一半是烤出来的三角形，真正的数据在我们自己的扩展里、数组借 glb 的二进制块放；隐藏数据三类（口袋、认识但不列、文件里另一副样子）。落法 = 文件照登记表写（守卫）、面板照同一张表列三块、不认识的变成看得见的条目、口袋退役；完全读不懂的打开时让人选。范围先做物体这一层。写在登记册第六¾节第 6–13 条。user 开头那个「不」统筹读作「版本不同不用当成专门对付的问题」，没确认。

20. **user 纠正代价表里的树**（原话在登记册第零节）：一棵树真做的时候是一个带着几何的树干物体、上面粘贴叶子、最后并成一个物体；带着几何的父物体是常态，空物体只是容器；内容创作是第一公民，创作时打散和重组非常频繁（做 Klee 时把帽子提出来、拷回去、又提出来）。统筹认：那一行问错了问题，改成「提出来和并回去必须随手、不丢东西」，记成筑基的验收。
21. **LOD 归谁**：user 倾向归渲染引擎、用户看不见（引擎会合批、重新切片）。统筹同意：人写的进文档，算出来的归引擎；手做的简化版和碰撞体才是带「用途」的子物体。

22. **范围**：user 同意「没有隐藏数据」这一版只做物体这一层；文档层和图片、音频那一半「进wishlist」。

## 统筹对 user 方案补的一处

「不认识就无脑原样保留」对数据块成立，对属性列不成立：属性列按元素排，几何一换算元素就变，原样留着会挂错地方，它得跟着几何走。所以是两套东西、同一个哲学——不懂它意思的那一层也必须把它带着。为了让「原样留」安全，数据块不许按序号指着元素。user 同一晚同意了。
