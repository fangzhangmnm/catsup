## 10-30 · 材质色是线性还是 sRGB；glb 里存错了
- **user 原话**：「然后我们现在是linear还是srgb？（其实我比较喜欢srgb）」「glb 规定材质色要存线性值，我们写进去的是 sRGB 值……给方案和pro con」
- **现状（代码核过）**：app 里材质色按 sRGB 存；线稿 / 像素 / 1-bit / 剪纸直接在 sRGB 里算；写实 / 铸铜先转线性算光、再转回。glb 规定 baseColorFactor 是线性值，我们写 / 读都按 sRGB 值 → 自己往返没事，Blender 打开偏浅、从别的软件导进来偏深。
- **方案**：
  - A 文件边界换算（推荐）：app 里照旧 sRGB，写 glb 时换成线性、读时换回。好 = 别的软件颜色对、app 里一切不变、只改读写两处、浮点换算往返不丢色；坏 = 老文件（按 sRGB 存的）得认出来——材质那块格式拍子 +1，老文件按老读法（颜色是作者挑的值，这里建议念旧，和 UV 不同）。
  - B 两份都存（glTF 字段写线性、自家扩展再存一份 sRGB）：好 = 自家往返一字不差；坏 = 同一个颜色两份，别的软件改了我们读不到，违反「一个事实一个地方」。
  - C app 内部全改线性：好 = 和物理渲染一致；坏 = 你喜欢的 sRGB 手感没了，线稿 / 像素那些画风的明暗会变，调色板取色器全要换算。
  - D 不改、写说明：零成本，互通一直偏色。
- **状态**：**拍了 A**（user「文件边界换算 同意」「老文件我们现在真的不用念旧」）→ **落地 v0.18.16**；老文件那三行 user 同日「好，不走特殊，合规来，三行没关系」= 留着。

## 10-30 · 第二轮：UV 是材质的属性、画皮 / triplanar；顶点色；色卡；素材架只收主动送的；颜色空间科普
- **user 原话**：「没懂，你是说着色器自己算uv吗。这个我同意，也符合数据契约。所以自动uv是材质的属性？合理，这样小红帽也能接别的材质而留着自己的uv。然后画皮的uv还是少数，涂到砖墙上也会报错找不到uv，而不是变成一张张皮。然后这样的话triplanar也可以顺手做，什么适合triplanar，也许不急」「要不要我们也用linear，只是ux的时候srgb？先帮我全量科普一下到底影响什么。我做retro game是要调srgb的 精确小数为什么round trip没有浮点误差」「然后我也不明白为什么uv会担心老文件，因为我们现在改的是shader的行为，老文件里面存的语义是什么」「然后问你，油漆桶里面那么多色卡是材质还是啥。顶点色和材质我们必须先理清楚逻辑设计清楚」「其实这样干净，赞，不会屎山……顶点色是另外一回事，可以wishlist，但是我觉得面对应材质，然后顶点色是另外一个通道比较好」「然后材质也能进asset store哦，但是还是临时的dummy材质不进，只有mark as asset的才会进」「这样就是你导入一个猫娘不会asset store里面一大堆散的皮。asset store里面只有你要assign别人的。所以烘培的贴图什么各种单例都不进。除非你主动放行。就是看用户说的send to asset store. 这个设计理念怎么样」
- **Opus**：
  - UV 现在不是着色器算的，是画之前在 CPU 上现算（效果一样：不存、现算）；「怎么铺」做成材质的属性 = 平面投影（默认）/ 三向投影 / 用模型自己的 UV（画皮，模型没有就报错）。三向投影适合：地形、石头、悬崖、雕刻出来的没有 UV 的网格体、程序生成的材质（像素方块、噪声）、弯曲的光滑表面（平面投影每个小面各贴一块、接缝乱）。
  - 为什么 UV 要问老文件：文件里只存「这面刷哪个材质 + 材质一块多大」，「怎么铺」的意思写在代码和契约那句话里——改代码 = 同一个老文件打开长得不一样；文件里没东西要迁移，只是要不要让老文件保持原样。你说不念旧，已经改了。
  - 色卡：每张色卡第一次刷的时候在文件里新建一个材质（名字 + 颜色），之后同名同色复用；没有顶点色。
  - 素材架只收主动送进去的：赞成，这就是 Blender 的「标为素材」。好处：架子是你挑过的工具箱、导入一个角色不会冲进几十张散皮；没上架的东西按「有没有人用」活着（没人用 = 孤儿，资源页清理）。要留意：① 找得到——资源页 / 层级的右键都要有「放进素材架」；② 架子上是一份拷贝（按值），原模型后来改了，架子上的不跟着变（要更新 = 再送一次 / 以后做「从原处更新」）。
  - 颜色空间科普（对话里讲全）：影响的是「混」——渐变、平均、半透明叠加、贴图缩小时的取平均、光照乘法、抖动阈值；单个颜色存什么数不影响看到的颜色（换算是可逆的）。线性里混 = 物理上对（光真的这样叠）；sRGB 里混 = 画家和老游戏机的手感（中间调偏暗、对比强，PS1 / SNES 那代都这样算）。所以真正要选的不是「app 内部存什么」，是「每个画风在哪个空间里算」：线稿 / 像素 / 1-bit / 剪纸在 sRGB 里算（你要的 retro 手感），写实 / 铸铜在线性里算——现在已经是这样；以后可以把「在哪个空间混」做成渲染窗里画风的一项。往返为什么不丢：双精度浮点的误差在 1e-15 量级，一档色阶是 1/255 ≈ 0.004，差十几个数量级，回到 8 位取整一定是原来的色号（单测把 256 个色号逐个跑过）。
- **状态**：顶点色另开通道 = wishlist；素材架只收主动送的 = user 提的、Opus 赞成（拍了）；「怎么铺」做成材质属性 = 方向拍了、没做。

## 10-30 · 第三轮：每个画风在哪个空间里算；图片为什么存 sRGB；和 WeebPaint 对齐；色卡要 sunset；材质纪元
- **user 原话**：「每个画风在哪个空间里算 对，渲染里面可以调。只是我们图片格式默认srgb存，是不是这样其实比linear在低精度省内存的时候精度高？然后颜色因为我们的语义是颜色，html css也是srgb对吧，weebpaint也是，weebpaint混色也是吗？可以和weebpaint对齐。但是我们的写实引擎可以走linear，复古走srgb，可以吗」「色卡：每张色卡第一次刷的时候，在文件里建一个材质，之后同名同色就复用 这个之后马上要sunset」「材质编辑转bump一个minor，然后linear vs srgb也归这个minor」
- **Opus**：
  - 对：8 位存图时 sRGB 更省——sRGB 把更多的档位分给暗部（人眼对暗部差别更敏感），同样 8 位，线性存会在暗处出色带。所以图片、贴图、颜色值存 sRGB 是对的；只在要「按物理算光」的那一步临时转线性。
  - 网页（CSS）的颜色默认就是 sRGB，渐变默认也在 sRGB 里插值（新的 color-mix 才能选别的空间）。
  - WeebPaint（代码核过）：手指混色默认 sRGB，可选 oklab（感知均匀）和 spectral（像颜料）——user 08-30 拍的默认；色带插值默认也是 sRGB。CatsUp 对齐它：颜色语义 = sRGB；写实走线性、复古走 sRGB；以后「在哪个空间混」做成渲染窗里画风的一项，选项照 WeebPaint（sRGB / oklab / spectral，再加写实用的线性）。
  - 「一个色卡 = 一个材质（同名同色复用）」：user 说马上要 sunset——记账，材质纪元里换掉（怎么换下一轮聊）。
  - 材质编辑器 = bump minor 开「材质纪元」；「在哪个空间算」也归这个纪元。
- **状态**：写实线性 / 复古 sRGB = 拍了（user「可以吗」+ Opus 同意，已是现状）；渲染窗里可调 = 材质纪元做；色卡 sunset = 材质纪元。
