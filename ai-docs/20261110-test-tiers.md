## 一、现状（2026-11-10）

- （工具做好之前）`npm test` = 一个进程把 197 个测试文件全跑一遍，再跑红线守卫，再跑画画内核自己的那一套。约 45–55 秒，机器忙时 79 秒。没有「只跑一部分」的入口。这个串跑留作 `npm run test:serial`。

## 二、四档

| 档 | 跑什么 | 多久 | 什么时候跑 |
|---|---|---|---|
| **快门** | `npm run typecheck`，加上点名跑正在改的那一两个测试文件 | 几秒 | 每改一下 |
| **被动过的** | `npm run test:changed`：看 git 里改了哪些文件，只跑会走到它们的测试，加上便宜的守卫 | 实测：改网格内核一个文件 = 135 个文件、约 6 秒；只改文档 = 36 个便宜守卫、1 秒左右 | 一块改完、提交之前。反证（换回旧代码看它红）也只在这一档做 |
| **全套** | `npm test` | 并行约 12 秒（串跑 `npm run test:serial` 约 50 秒） | **一张工单最多两次**：交审或者自己合之前一次；合进 main 之后、推开发版之前一次。第二次在「合并是快进、交审之后没再改代码」时省掉 |
| **探针和截图基线** | 点名的那几个 | 每个不超过一分钟 | 只在改到它管的那一块时。每张工单动手前，在施工细则里列出「这一张要跑哪几个」 |

| **整跑** | `node scripts/probe-sweep.mjs`：全部守卫探针一个一个跑，和底账比 | 约半小时（11-12 量：33 分钟，带真模型 43 分钟） | **它不属于任何一个版本：发版之前不跑它，发了版也不等它。** 什么时候跑看这中间改了什么（user 11-12：「可以改下一步的时候后台跑。不过确实一般是全量测一次就能发现的，再测不一定还会有新东西，不过也不一定」）：① 合进去的东西碰了很多探针都会走到的公共层（编辑器换工具 / 换工作台、输入闸、键表、会话和存盘、工作台的声明、重拉内核、升共享库）→ 推完开发版、开下一步的时候后台跑一次；② 只改了一小块、那一块点名的探针已经跑过，或者只改了文档和探针 → 不跑；③ 上一次整跑之后代码没变 → 不跑；④ 同时只跑一份；下一次改完、推了新版本时上一轮还没跑完 = 先杀掉（user 11-12：「如果下一次改完了后台还没跑完可以先杀」；它测的已经是旧代码），已经跑完的那部分结果留着记一笔，新版本够得上 ① 再开新的一轮；⑤ 一天下来有改动而一次都没跑过 → 收工时跑一次。纪元收尾再跑一次。出了新红，手上这一步做到能停的地方先查它 |
| **性能** | 底账里 `role: perf` 的那几个（规模、基准、量拷了多大） | 几分钟 | 施工单碰到画画那条路（落笔、每帧、合成、内核、渲染器贴图）时，收尾跑一次，放后台；纪元收尾跑一次 |

**发版只看前四档（user 11-12：「我还是没法接受每个小版本要白等21分钟」「必须得分级」；家规 10-14 早就有「先推开发版再跑慢的」）。** 一个版本从改完到推开发版，要跑的只有：被动过的（几秒）、全套（十几秒，照上表的次数）、这一张点名的那几个探针（每个不超过一分钟）。整跑和性能档永远排在推开发版之后，没有人等它们。

**红线那一小组（user 11-12：「但确实dev可以先发版再跑。关键是核心安全红线护住了，其他的不好行为相对可以容忍」）。** 守丢数据那几类的探针固定成一小组，不靠人挑：修改锁每层都拦、存盘前后一致、撤销逐位还原、文件格式来回、崩溃快照。底账里给这几行标上 `redline: true`；合计不超过两分钟，超了就留最综合的几个、其余归整跑。**每个改了 `src/` 的版本都跑这一组**：推完开发版马上放后台跑，不管这次改的是什么；红了 = 手上的停下，先修。别的探针红了可以排队修。唯一的例外不是等待、是审查：改到锁、存盘、撤销、文件格式这四类时，合之前把那一块点名的探针跑完（它们本来就在「这一张要跑哪几个」里）。

画画内核自己的那一套（`run-kernel.mjs`）只在重拉内核、或者改了 `src/paint/` 时跑。

## 三、怎么跑（不许机械地等）

1. **不许「改一行就跑全套」。** 平时只跑快门和被动过的。
2. **全套和探针放后台跑，同时接着做别的**（写施工记录、更新流程图、重新生成接口签名）。不空等，不隔一会儿去看一眼；跑完会有通知。
3. **同一份代码不跑第二遍。** 全套绿过之后只改了文档、注释、施工记录：不重跑。
4. **红了**：只重跑红的那一个文件，修好后跑被动过的。全套留到交审前那一次。
5. **偶发的红**（忽快忽慢的、和时钟有关的；这台机器的钟会被往回拨）：单独重跑那一个，记进施工记录。不为它重跑全套。
6. **审查的人不重跑**施工的人跑过的，除非有具体的怀疑。
7. **速度对比**只在工单明说要量的时候跑，而且用小规模：一万面左右、单次几秒、改之前改之后各三遍取中间的，全部加起来不超过一分钟。这台机器上别的线也在跑东西，一成的差别量不准；慢三成以上才算退步。能直接证明「没多做事」（多出来的分配和拷贝是零）的，计时只是旁证。
   - 11-10 夜的教训：施工单（三）要求量十万面的环切、细分、倒角，改前改后各跑几遍，一遍就是好几分钟，user 看到小弟等一个测试等了十五分钟。门是 Fable 定重的，当晚改小。
8. **任何一条命令估计要跑一分钟以上**：先缩小规模再跑。缩不了的放后台，手上接着做别的，不停下来等。Fable 写施工单的门时，先想这道门跑一遍要多久。
9. **不砍测试、不放宽断言来换时间。** 慢的测试挪档或者拆开，不删。
10. 报告里说清这一次跑了哪一档、没跑哪一档。没跑的不说成跑过。

在画画仓做内核的工单时同样：平时只跑改到的那一块；逐像素基线和显卡冒烟在交审前跑一次。画画仓自己有分档的照它的；没有的，小弟侦察之后在那张工单的施工细则里列一张「改了哪里跑哪些」的小表。

## 四、给小弟的工单：把工具补上（你自己测完自己合）

排在 1-2 交审之后、W-8 之前。小，一个末位版本。细则你自己定，下面是要达到的：

1. **量一遍**：197 个测试文件各花多久，最慢的十五个列进本页第一节；内核那一套花多久；截图基线花多久。
2. **`npm run test:changed`**：
   - 改了哪些文件 = 和 main 分叉以来的提交，加上没提交的、没跟踪的。可以用参数指定从哪个提交算起。
   - 一个测试该不该跑 = 它沿着 import 能走到改过的文件。
   - 靠读源码文本来查的守卫（扫 `src/` 的那些）沿 import 找不到它们。这类便宜的每次都跑；贵的在脚本里明着列出它管哪些文件夹。
   - 跑之前打印选中了哪些、各因为哪个文件；一个都没选中时说清楚，不当成绿。
   - 改到了 `test/run.mjs`、`package.json`、`tsconfig.json`、测试的公共工具：直接说「这次得跑全套」。
3. **改了哪里 → 跑哪些探针**：一张表（一个文件，脚本和人都读它），按文件夹粗分就行。`npm run test:changed` 末尾按这张表提醒「这次改动建议跑这几个探针」，不自动跑。
4. **全套变快**（做得动就做，做不动把原因写进记录）：照 MoonSinger 的并行运行器，把 197 个文件分给几个进程。目标 20 秒以内。随机的测试种子是固定的，并行不许改变结果。
5. **守卫**：每个 `test/*.test.ts` 都在 `test/run.mjs` 里（不许有写了却没人跑的测试）；探针的那张表里每个脚本名都存在。
6. 做完把第二节里带「目标」的数换成量出来的，`CLAUDE.md` 的「自测入口」那一行跟着改。

碰到这些停下来说：沿 import 选出来的几乎每次都是全部（说明有个公共文件被所有测试引用，要先说怎么拆）；并行之后有测试互相影响。

### 施工细则（小弟，11-10 深夜；Claude Opus 5.5）

侦察：`test/run.mjs` 静态 import 全部测试文件（它就是登记处，不另起一份名单）；`test/runner.mjs` 一个全局数组，先全部登记、再全部跑；40 个测试读文件，其中 23 个扫目录（读源码的守卫）；探针 179 个（含 `lib/`、`fake-cloud/`、几个 bench，不是探针）；机器 16 核。

改哪：
1. `test/runner.mjs`：`run()` 照旧；多一个给工人用的「跑完这一批、清空、交回计数」。
2. 新 `test/par.mjs`（并行运行器）：从 `run.mjs` 的 import 行读名单；开 N 个工人进程（默认 min(8, 核数 − 2)，`--jobs=N`），每个工人一份一份 import → 跑 → 清空 → 报耗时和计数；按上一次量的耗时从慢到快派活；绿的文件只打一行汇总，红的打全文；并行红的文件最后单独串跑一遍，单跑绿在总结里明说「并行红、单跑绿」（照 MoonSinger），单跑也红 = 真红。红线守卫和画画内核那一套作为另外两个工人同时跑。`npm test` 换成它；原来的串跑留成 `npm run test:serial`。
3. `npm run test:changed`（同一个脚本 `--changed [--since=提交]`）：改过的 = 和 main 分叉以来 + 没提交的 + 没跟踪的；扫 `src/`、`test/` 的 import 文本建图，测试沿 import 走到改过的文件才选；读源码的守卫按耗时分：便宜的每次跑，贵的在脚本里一张表写明管哪些文件夹；打印选中了哪些、各因为哪个文件；一个都没选中说清楚；改到登记处 / 运行器 / `package.json` / `tsconfig.json` / 测试公共工具 → 说「这次得跑全套」并跑全套；改到 `src/paint/` 加跑画画内核那一套。
4. 探针表 `test/probes/probe-map.json`：按文件夹粗分；`test:changed` 末尾按它提醒建议跑哪几个，不自动跑。
5. 守卫 `test/test-tiers-guard.test.ts`：每个 `test/*.test.ts` 都登记了；探针表里每个脚本名都存在、每个文件夹都存在；贵守卫表里的文件都存在。

这一张跑哪些：串跑一次、并行一次，两边通过 / 失败 / 待办的数和失败名单逐条相同（不同就停下来报「并行之后有测试互相影响」）；`test:changed` 用几种假改动看选中和理由（改网格内核一个文件、只改文档、改运行器）；不跑探针（这张不碰 app 代码）。

### 施工记录（小弟，11-10 深夜；v0.19.7，自己测完自己合）

做了：
- `test/par.mjs`（并行运行器 + `--changed` + `--files` + `--dry` / `--verbose` / `--times` / `--jobs` / `--no-retry`）、`test/par-worker.mjs`（工人：一份一份 import → 跑 → 清空 → 交回）、`test/runner.mjs` 多一个 `runBatch`（`run()` 改成调它，串跑行为不变）。`npm test` = 并行；`npm run test:changed`；`npm run test:serial` = 原来的串跑。
- 「只跑被改到的」：扫 `src/`、`test/` 的 import 文本建图；读文件的测试（直接用 fs 的，或经工具模块读 `test/fixtures/` 的）便宜的每次跑，贵的（> 0.5 秒）在 `par.mjs` 的 `EXPENSIVE_FILE_READERS` 里写明管哪些地方——现在 7 个（scale-ref、change-log、identity-merge、identity-guard、cloud-gate、textures-table、format）。全套跑完时，读文件的测试超过 1 秒又没进表 → 点名提醒。
- 探针表 `test/probes/probe-map.json`：18 条，按文件夹粗分，每条挑 3–6 个代表。
- 守卫 `test/test-tiers-guard.test.ts`：没登记的测试（原来在 `run.mjs` 末尾那一段，挪进来当一条测试）、测试文件之间互相 import、探针表的探针和路径、`par.mjs` 两张表指的东西。

量的和对的：
- 串跑 `npm run test:serial`：1833 过 / 0 红 / 4 待办 + 画画内核 549 过、零泄漏，54.5 秒。并行 `npm test`：同样 1833 / 0 / 4 + 549，11.3–12.5 秒。两边每条测试的名字和结果逐条比过：2387 行一样（只差画画内核两条的耗时后缀）。
- 第一次并行多出 2 条：`kernel-fuzz.test.ts` 里有个公共检查函数，另外 3 个测试文件 import 它，工人先碰到这 3 个之一就把 kernel-fuzz 的两条（各 4.5 秒）又登记、跑了一遍。改法 = 公共函数挪进 `test/kernel-invariants.ts`，测试文件之间不再互相 import，守卫钉住。（这正是第四节说的「并行之后有测试互相影响」那一类；根在测试互相 import，已拆，不是并行改变了结果。）
- `test:changed`：改网格内核一个文件 → 选中 135 个（119 个沿 import + 16 个便宜守卫）、1447 条全过、约 6 秒，提醒 5 个探针；只改文档 → 37 个便宜守卫、明说「这不等于测过」；改运行器 → 全套；改冻结样本 → 读样本的 2 个。
- 反证：临时让一个测试 import 另一个测试 → 守卫红、点名；临时放一个没登记的测试文件 → 运行器拒跑、点名。
- 这一张跑全套的次数超过了「最多两次」：工具本身就是要量全套（并行四次、串跑一次），按施工细则说的「串跑一次、并行一次」做对照，多出来的是查那 2 条和量耗时。合进 main 时只有文档从 main 那边进来，不再跑。

不放心的：
- 改 B-rep 内核一个文件会走到 148 / 198 个测试，改网格内核 119 个：import 图是粗的（编辑器引用了几乎全部），没到「几乎每次都是全部」那条线（八成），但偏多。
- 截图基线 19 个场景要 1 分 36 秒，超过一分钟的线；可以点名几个场景跑，要不要拆成几份并行没做。（11-11 W-9 做了：4 个浏览器并行，28 个场景 47 秒。）
- 「贵的」表要人维护：新写的读文件测试变贵了，全套会提醒，但不会自己进表。
- 并行红、单跑绿的文件会单独再跑一遍、算过、但在总结里点名（照 MoonSinger）；这次没遇到。

## 五、探针整跑和底账（统筹 11-11 定；小弟施工，2026-11-11 Claude Opus 5.5）
> as-of v0.19.48 + reds 分支 / 2026-11-11

起因：流畅第一批收尾整跑出 19 个红，全是 v0.19.45 以前就红的老账（有的红了十几版没人知道）。规矩：
- **底账 `test/probes/probe-ledger.json`**：每个探针一行，状态四种——`green`；`known-red`（`reason` 为什么红、`since` 从哪一版、`fixBy` 谁什么时候修）；`flaky`（`symptom`、`seen` = 几次里红几次、`fixBy`）；`helper`（不是探针，整跑不跑，如 `fake-cloud.mjs`）。新探针加一行，跑绿了写 `green`。守卫 = `test/test-tiers-guard.test.ts` 第 ⑥ 条（每个探针文件一行、每行都有文件、每种状态该写的字段都写了）。
- **整跑 `node scripts/probe-sweep.mjs`**（先 `bash scripts/build.sh`）：脚本自己在仓根起服务、串行跑全部（不并行：软件显卡抢核会跑出假红），和底账比，只报三样——**新红**（底账说绿的、或者底账里没有的）、**新绿**（底账说已知红的跑绿了 → 改底账）、**还红着**；偶发的这次红了单列。红的每一个用 `scripts/probe-why-red.mjs` 打出红在判据的哪一条（`const ok = …` 按顶层 `&&` 拆开逐条算；✓ / ✗ 风格的打 ✗ 那几行），不靠人眼在输出里找 false。退出码 1 = 有新红。
- **一条都没查 = 红，或者明说没跑，不许是绿**（统筹 11-12；同一类口子第二次出现）：截图基线、`probe-update-conflict` 在所有整跑里都是假绿过——整跑按惯例传网址，一个被当成场景名、一个被当成用法，一条都没查就报 ok / 退出码 0。修了：截图基线比了 0 个场景 = 红；`probe-update-conflict` 不给参数或给网址 = 跑验收那一档、不认识的用法 = 退出码 2。整跑脚本末尾另报「可疑的绿」：绿了、但比开一次 app 的固定开销（1.4 秒）还快的，单列出来看日志。新写的探针：点名对不上、什么都没做 = 红。
- **整跑什么时候跑：见第二节表里「整跑」那一行**（统筹 11-12 改。11-11 定的是「每一批收尾整跑一次」，实际跑成了差不多每个小版本一次，v0.19.49 还是等它跑完才发的；user 11-11「为什么要测试35分钟，批判性地想一下合理吗」、11-12「我还是没法接受每个小版本要白等21分钟」「必须得分级」）。不属于任何版本，按「这中间改了什么」触发、后台跑（细则在第二节那一行；11-12 稍后 user 又说可以在改下一步的时候后台跑，所以不死守一天一次）。改探针本身（比如把写死的等待换成等条件）之后不为了「对一下底账」专门整跑，等当天那一次。
- **底账另一栏 `role`**：`guard` = 整跑要跑的；`scaffold` = 做某张单时对着看的细探针，不进整跑（`--only` 点名照跑）；没写 = `guard`。现有的碰到哪个分哪个。每张单收尾时，把那张单里的细探针收成一两条综合的（user 11-11：一块做完收成几条综合的对抗性测试，守卫不许变薄）。
- **性能档 `role: perf`**（统筹 11-12，分档本身）：量时间、量规模的探针不算守卫、也不是脚手架，单列一档。现在 = `bench-scene`、`bench-pools`、`bench-bake-paths`、`probe-paint-scale`（这几条「不随画布 / 模型 / 笔画长度涨」是流畅那一批的成果，靠它守着）；守卫档文件里量的那一半用 `perfArgs`（现在 `probe-live-region` 量拷多大、`probe-paint-workbench`「切进来 < 半秒」，都是 `--perf` 开关：不带只打数、带了才判）。命令 `node scripts/probe-sweep.mjs --tier=perf`。**什么时候必须跑**：施工单碰到画画那条路（落笔、每帧、合成、内核、渲染器贴图）的，收尾跑一次（后台）；每个纪元收尾跑一次。施工单十九第 3 刀、十八、搬画那几张收尾都跑。守卫档里只留和时间无关的判据：绝对时间的判据（「< 半秒」这类）一律进性能档，这台机器别的会话一忙它就红、红了说明不了什么。
- **红线那一小组 `redline: true`**（统筹 11-12：「核心安全红线护住了，其他的不好行为相对可以容忍」）：守丢数据的那几类固定成一小组——修改锁每层都拦（`probe-lock-matrix`、`probe-present-lock`）、撤销逐位还原（`probe-undo-fuzz`、`probe-paint-undo`）、存盘前后一致和崩溃快照（`probe-paint-save`、`probe-mid-stroke-save`）、文件格式来回（`probe-export`；格式的冻结样本在 node 全套里每版都跑）。合计约 100 秒（11-12 量的，负载低时）。**每个改了 `src/` 的版本推完开发版马上后台跑**，不管这次改的是什么；红了 = 手上的停下先修，别的探针红了可以排队。命令 `node scripts/probe-sweep.mjs --redline [--at=<提交>]`：`--at` 对着那个提交干净构建（临时 worktree + build）跑；每次跑完记一笔到仓的 `.git/catsup-redline-runs.jsonl`（哪个提交、哪个版本、工作区干不干净、哪天、全绿没有、红的是哪几个）——推正式版前查的就是它：要推的那个提交上红线组和快档是绿的。守卫：redline 那几行必须是守卫档、现在是绿的，至少五个。
- **这台机器的两个事实（统筹 11-11 补，user 提醒）**：① WSL 的墙上钟约每 32 秒往回拨 1.8 秒（11-08 量过）→ 量时长、判超时一律 `performance.now()`，不用 `Date.now()` 相减；`test/`、`scripts/` 里用墙上钟的每一行都要在同一行写 `// 墙上钟：为什么`（守卫 `test-tiers-guard` ⑦；跨刷新的到期时刻、文件夹名后缀、跟 app 同一个钟的这几种留着）。② 别的会话也在这台机器上跑（16 核，11-11 夜负载 6–10）→ 整跑整个低优先级（`os.setPriority(10)`，子进程跟着）；每个探针记开跑时的负载；新红先单独重跑一次，重跑还红才算新红、才停，重跑绿 = 「偶发这次红」照实报。并行最后才考虑（一个探针的软件显卡就吃三四个核，并多了把别的会话挤出假红）：先省固定开销，真要并按当时空着的核算、机器忙就退回串行。
