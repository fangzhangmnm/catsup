# 画这一块的数据结构清单（实测）

> as-of v0.19.80（main bfbd20ae）/ 2026-11-13 · created by Claude Opus 5.5（施工单十八：第 1 刀推完之后、第 2 刀之前，统筹点的清单）
> 只读：这一页什么都没改。字节数是测试页里给 WebGL 建图 / 删图 / 建缓冲记账量的（和 `test/probes/probe-paint-open-memory.mjs` 同一个钩子），和显卡无关；毫秒数是软件显卡上的，只能同一次里互相比。

**怎么量的**：无头 Chrome，显卡 = `ANGLE (Google, Vulkan 1.3.0 (SwiftShader Device (Subzero)), SwiftShader driver)`（软件显卡）。基准 = 一个盒子细分 4 次（1536 张面、6144 个角），整个物件一张 2048 × 2048 的画（新开的画两层，再加一层 = 三层）；也量了 256 × 256。内存里的像素用 `__catsup.paint.tiles()`；撤销记录读 `editor.history` 最上面那一步；文件用 `session.encodeNow()` 拆开数。量的脚本是一次性的，没进仓。MB = 2²⁰ 字节。

## 一、一张画在显卡上

2048 见方、三层、1536 张面，在绘制工作台里画过两笔：

| 东西 | 2048 时 | 怎么算 | 什么时候在 |
|---|---|---|---|
| 给渲染器的显示图（连缩小图） | 21.3 MB | n²·4·4/3 | 一直在（歇着也在，这份是要的） |
| 内核的合成目标 + 预借的帧缓冲 + 池里留的两张 | 4 × 16 MB = 64 MB | 4·n²·4 | 第一笔之后一直在，**歇着也不还** |
| 内核的图块池（一份文件一个，2D 图组） | 64 MB（256 片） | 起步 64 片 16 MB；画的时候长到两层画布那么多图块，睡前那次整张合成长到三层那么多；**只长不缩** | 第一张画开的时候建，换文件才退 |
| 每格的表（RGBA16UI） | 32 MB | n²·8 | 只在绘制工作台里 |
| 一笔正在画时的两张薄层（定型层 + 当帧那张） | 32 MB | 2·n²·4 | 只在一笔当中，抬笔就还（实测 33 554 432 字节） |
| 每层一张索引小图（R32F） | 8 × 8 × 4 B，每层一张 | (n/256)²·4 | 醒着 |
| 面表 + 三角形表（R32F，2048 宽） | 16 KB + 188 KB | 2 个数 / 面 + 15 个数 / 三角形 | 只在绘制工作台里，跟物件走、不跟画布走 |
| 一笔里每帧的数据表（R32F，2048 宽） | 0.4 – 7.3 MB | 跟着画过的最大那一帧长 | 第一笔之后**一直留着** |

- 合计：三层醒着 **182.0 MB**（除了最后一行的每帧数据表，其余逐项和 `src/paint/open-memory.ts` 的公式对得上；那张表不在公式里）；256 见方 18.1 MB。
- **歇着**（离开绘制工作台以后）：一层涂满的 2048 画 = **156.6 MB**，其中显示要用的只有 21.3 MB。还掉的只有每格的表和面表。睡前那一次整张合成反而把图块池从 128 片撑到 256 片。
- **两张画**（同一个物件各占一半，都 2048，各涂过两道，都歇着）= **256.5 MB**：显示图 2 × 21.3 MB、帧缓冲 5 × 16 MB、图块池 512 片 128 MB（**用户 0 个**）、每帧数据表两张共 5.9 MB。

## 二、内存里的像素（内核图块）

- 稀疏：没画过的格子没有图块，空画 0 片。
- 每片 256 × 256 × 4 = 256 KB，原样存；压缩在后台慢慢做（`src/paint/tile-jobs.ts`）。
- 实测（2048，一层）：横扫一道 = 58 片 14.3 MB；再涂满 = 122 片 30 MB（现在的约 64 片，加上撤销拉着的上一笔的旧片）。一秒多以后压完的只有一两片（12 KB）。
- 额度：原样的图块共用内核的一个 128 MB 额度；压缩过的才按大小摊进撤销那边。

## 三、撤销

- 三维撤销栈里，一笔 = 一条「画」记录：64 字节，外加每碰一层 64 字节（实测 64 和 512 + 64）。
- 旧像素不在这条记录里算：它是记录拉着的旧图块（上一节）。涂满一层 2048 = 最多拉住 64 片 16 MB 原样的，压缩以后才变小。压完要多久没量。

## 四、每格的表（建的时候）

- 内存：
  - `owner` Int32，每格 4 B（2048 = 16 MB，建完留着）。
  - 建表时临时的 `best` Float64 每格 8 B、`inside` Uint8 每格 1 B（2048 = 36 MB，建完就丢）。
  - 每张面的环、三角形、公式约 870 B（1536 张面 1.3 MB，跟画布大小无关）。
- 显卡：每格 8 B（上表第四行）。
- 离开绘制工作台：缓存只留这次要用的目标，内存和显卡两份一起放（实测显卡那 32 MB 还了）。
- 建表耗时（软件显卡）：2048 = 几何 345 ms + 每格 364 ms + 表 16 ms；256 = 158 + 23 + 15 ms。

## 五、每格的三维位置

- 只在一笔当中：两张薄层，2·n²·4 字节，就是第一节表里那 32 MB；抬笔就还。没有常驻的。

## 六、网格体上的贴图坐标

- **v0.19.80**：每套排法一列，每个角两个 Float32 = 每个角槽 8 B。
  - 角槽按容量长：6144 个角占 8184 个槽（75%），1536 张面一套 = 64 KB。
  - 每多一套排法，整列再来一份，不在这套上的角也占着。
- **第 1½ 刀以后**：一列坐标（每个角槽 8 B）+ 面上一列代号（每张面一个整数），不跟套数涨。

## 七、文件

- 贴图那一行存两份像素：
  - `content.ora` = 分层；
  - `composite` = 整张合成的 PNG，冷的时候拿来显示。
- ora 里面有 `mimetype`、`stack.xml`、每层一张 PNG（空的层不写）、`Thumbnails/thumbnail.png`（116 B），还有 `mergedimage.png`——它**只有 617 B，是个占位**。别的软件打开这个 ora、看它的合成预览，看到的是空的（这一条是格式上的事，不是占地方的事）。
- 实测 2048，一层涂满：ora 338 KB（那一层 336 KB）+ 合成图 272 KB；整个文件 828 KB，其中模型和别的约 220 KB。几乎空的画：ora 66 KB。
- glTF 本体的 `images` 里只有一张 6 KB 的 JPEG，没核它是哪张。

## 八、freed（第 2 刀才加）

- 每张失去位置的面一个包围盒 `[x0, y0, x1, y1]`（四个整数，单位是格），记在那套排法的那一行里。
- 补面时当它占着，重排的时候收回。大小跟丢了位置的面数涨，不跟画布涨。

## 九、绘制调用和顶点

- 主渲染：**固定 3 次 + 每摆一份物件（它用到几种材质 + 1 次边线）**。摆好几份不合批。实测（都站在最外层、什么都没选）：

| | 摆 1 份 | 摆 3 份 |
|---|---|---|
| 没有画 | 5 | 9 |
| 一张画盖满整个物件 | 5 | 9 |
| 两张画各占一半 | 6 | 12 |

- 一张画盖满时，底色那一组是空的，所以和没画一样多。
- 顶点：三角形之间不共用顶点。每个顶点 = 位置 f32×3 + 法线 i16×3 + 颜色 i8×3 + 贴图坐标 f32×2 = 29 B，每个三角形 87 B。几何每个内核一份，摆几份都共用；按 1.5 倍扩容。

## 明显浪费的（只标出来，没改）

1. **歇着的画板不还内核的池子**。图块池只长不缩、帧缓冲池也留着，要到换文件才还。一张 2048 涂满后离开工作台，白挂 135 MB；两张 2048 白挂约 214 MB；睡前那次整张合成还把池子撑大一倍。
   - 以后会长成什么：画越多、画布越大越糟，iPad 上显存紧的时候第一个撞上的就是它。
   - 反映的结构问题：池子只有高水位、没有退潮。「谁该在没人用的时候把它缩回去」现在没人管。
2. **一笔里每帧的数据表画完留着**，跟着画过的最大一帧长（实测最大 7.3 MB）。和上一条是同一类：只长不缩。
3. **v0.19.80 的贴图坐标每套排法一整列**：第 1½ 刀就在改。
4. 建表时临时的 `best` 用 Float64（2048 = 32 MB 临时）。Float32 够不够没核，影响小。

不算浪费、但该知道的：
- ora 里的合成预览是占位（第七节）。
- 撤销拉着的旧图块要等后台压缩，压之前按原样算（第二、三节）。
