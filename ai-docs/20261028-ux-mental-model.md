## 0. 一句话

控制器 = MVC 的 C = 一个**无头骑士**：它只看得见三样东西——①从设备抽象出来的手势、②模型的只读视图 + 一组带类型的动词、③给窗口 / 画面的显示模型。它的「智能」（捕获优先级、默认布尔、轴向、吸附立场）**全是表里的一行**，不是散落的 if。设备（鼠标 / 笔 / 手指 / VR）只差一个适配器和表里「默认值」那一列。

## 1. 你在抱怨什么（10-28 下午已确认「对」）

1. Blender 的属性编辑器 / Unity 的 Inspector：「对每个当前的东西，显示它全部的上下文」——全局、物体、网格数据、修改器、材质、贴图叠在一根柱子里，不同逻辑层级混在一个窗口，字段不知道属于谁，窗口形状还随选中物变。
2. Opus 下午的「物体设置选项窗」同一个病：修复 / 转换 / 镜像 / 细分 / 默认平滑 / 组件的进入炸开锁藏改原点，塞成一张菜单——几何层动词、物体层属性、工作台层设置三种东西混在一起。右键菜单也一样，编辑几何时被物体级的东西污染。
3. 你要的：**一个窗口只盯一个指针，窗口按类型分**（文件 / 视口 / 物体 / 材质 / 贴图各一个，`类型 → 当前`）。窗口只显示自己那一类的属性；「物体 → 它的材质」是跳转（换材质窗口的当前指针），不是在物体窗口里展开。
4. 顺带要理的：Blender 和 SketchUp 两套肌肉记忆焊在一起（周账 F-117）、各工具各一套选择逻辑、把手大小 / 画在哪、镜像硬表面一套网格体一套。你自己的要求前后也可能不一致——所以这份稿不是抄话，是把话摆到一张图上，把打架的地方挑出来。

## 2. 模型（五张图）

### 2.1 窗口 = 类型 → 当前（一个窗口只看一个指针）

| 窗口（类型） | 它的「当前」指针 | 住哪（iPad 竖屏优先，版图文档 `20261024-ui-layout.md`） | 里面只放 | 现在的代码 |
|---|---|---|---|---|
| **文件** | 当前文档 | 左上 ☰ | 打开 / 保存 / 另存 / 导出 / 云 / 设置 / 帮助 | ☰ 分区菜单（已是） |
| **视口** | 当前视口 | 右上 ☰ + 导航把手 | 透视 / 线稿粗细 / 栅格 / 单位 / 参考窗 / 步行 / VR / 渲染方案（以后）/ **工作台下拉框**（user FM161「工具下拉框是视图」——它是「怎么看、怎么编这份东西」，归视口） | 视图 ☰ 分页（已是） |
| **工具** | 当前工具 | 左柱 + 底部选项条 | 这把工具自己的选项（工具配置表 `tool-config.ts`）+ 它的动作钮 | 已是 |
| **指令** | 当前指令（马前炮 = 正要做的；马后炮 = 刚做完的那一步） | 右下参数小窗 + **画面里的指令把手** | 这条指令的参数、应用 / 取消、说明行 | 参数小窗 + 平面把手（已是；把手只有镜像有） |
| **物体** | 当前物体：默认 = 你所在的这一层（最外层 / 进着的组件）；子组件的物体菜单里点「物体设置…」= 换成它 | 右边一颗钮（自由建模 / 硬表面都有）；**分页**（user 10-28「物体窗口的一个tab」）：属性 / 修复 / … | **这一个物体的**：名字、种类（硬表面体 / 网格体）、几份实例、锁 / 藏 / 层；编辑属性：**镜像面 + 模式**、默认平滑；对它的一次性动词：转换种类、细分、修复…、应用缩放、改原点、炸开、进入 | **没有**（Opus WIP 停在分支，形状不对） |
| **材质** | 当前材质 | 油漆桶再点一下 / 以后右缘 | 这一个材质的：颜色、贴图尺寸、（以后）贴图指针 → 跳到贴图窗口 | 材质面板（已是，雏形） |
| **贴图** | 当前贴图 | 以后 | 这一张图的 | 没有 |
| **系统** | — | 右下血槽 / 底部通知 / 调试日志 | 状态、版本、报错 | 已是 |

规矩（这就是和 Blender 的区别）：

- **窗口只显示自己类型的当前那一个的属性和动词**。「相关的别的东西」= 一行跳转，点了换那个窗口的当前指针。永远不内联另一类型的属性。
- **窗口第一行写清当前是谁**（user「选窗要说明选择的是哪个object」）：「物体：组件「块」（网格体）」「物体：最外层（硬表面体）」。
- **指针是显式状态**，不是选区的影子：物体窗口的当前 = 上次设的那个（默认这一层），换选区不自动换；右键子组件才换。关掉窗口不动选区。
- 每个窗口有**固定的家**（左上 / 右上 / 左柱 / 右下 / 右边钮）。小屏（手机）上家变成底部抽屉（sheet），但身份不变——还是「文件 / 视口 / 物体 / …」五个抽屉，不是一个大 Inspector。
- 导航把手上的小灯（吸附锁、镜像状态）= **状态灯 + 快捷键**（user 10-28「对，或者说快捷键吧，就是也可以操作，只是快捷键」）：灯可以跨窗口、可以点（点 = 快捷键：开 / 关、切模式），但**正主在它自己的窗口**（镜像的正主 = 物体窗口；吸附的正主 = 视口窗口栅格页）。灯上做不了的（挪镜像面、选轴）去正主那里。

### 2.2 菜单 = 对着什么点，就只给那一层的动词

右键 / 笔长按 / 触屏浮条是同一张表的三个渲染器（已是）。按「点在哪」分三层：

| 点在哪 | 给什么 | 现在的代码 |
|---|---|---|
| **空处** | 新建 ›（立方体 / 圆柱 / …）、回上一层 | 右键菜单里混着（v0.15.46）；user「先做空白就剩下新建，回上一层」 |
| **几何（选区 / 点中的点线面）** | 几何层动词：删除、建组 / 建组件、焊接、炸开曲线、软化 / 硬化、选连通体、选成环 / 洞、反选、取消选择；自由建模的环切 / 连线 / 插入 / 倒角 / 合并到中心 / 对称对齐 / 手标；选中的**组**的进入 / 炸开 / 锁 / 藏（组不是物体，它的动词留在这里） | 右键菜单（已是，但混着物体级的） |
| **子组件（选中的只有组件、点中的是组件）** | **物体菜单**：对这个物体的动词——删除、炸开、进入、锁 / 解锁、藏、应用缩放、以后的 make unique / make prefab…；**「物体设置…」只是其中一项**，点了开物体窗口、当前 = 它（user 10-28「不是，而是物体的菜单，因为也有删除，explode之类的……物体选项只是其中一项」） | 右键菜单里混着（v0.15.46） |
| 物体钮（右边） | 物体窗口、当前 = 这一层（这一层的属性 + 对这一层的动词：转换 / 细分 / 修复 / 默认平滑 / 镜像） | 没有 |

「xx 指令放在 yy」的集中处 = **放置表**（Fable 10-27 指令注册表提案的那张；代码 `src/editor/commands/action.ts` Placement，`placementsAt(面, 工作台)` 查）。现在它只管注册表里的指令（修复九条 / 转换 / 网格体十几条）；右键菜单里写死的二十几项（删除 / 建组 / …）和快捷键、左柱还在 `main.ts` 里。**整理 = 把这三样都搬进放置表**：面 = `空处右键 / 几何右键 / 物体窗口 / 左柱 / 快捷键 / 手腕面板 / 搜索 / api`，每行 = 动作 × 面 × 工作台 × 顺序 × 键。菜单 / 窗口 / 左柱 / 键盘都是「按面查表」的渲染器。以后你「再抖动」= 改这张表的一行。

### 2.3 工具的立场表（「直乘」怎么变成「立场」而不屎山）

你说的「直乘」：老软件把 工具 × 捕获优先级 × 布尔模式 × 轴向 × 吸附 全暴露给用户配置（Blender 的 preferences / 顶栏那一排下拉），因为它不敢替用户决定。套路固化了以后我们敢：**每把工具一行立场**，引擎读行，用户不配置。不屎山的办法只有一个：**立场是数据，不是代码里的 if**——一张表、一个解释器、一条守卫（每把工具必须有一行、每一格的值必须在枚举里）。

列（哪些已经有、散在哪）：

| 列 | 意思 | 现在散在 |
|---|---|---|
| 抓什么（grab）= **捕捉优先级 + 半径** | 没选区时按下作用在谁上：点 > 边 > 面 / 只认面 / 只认点和边 / 取点 / 刮 / 不抓；半径按工具（自由建模点 14 px、边 6 px，常量；FM162 / FM163「按工具分 vs 按大小比例」收口：**按工具 × 工作台分，写在表里**，user 10-28「点线面的捕捉逻辑也乱，不同的工作流和工具下面也有不同的最优解」） | `tools/selecting.ts pressTarget`（v0.15.46 刚收）、`pick.ts` 常量、各工具 down |
| 点一下 | = 选 / = 放第一个点（SketchUp 点 → 挪 → 点）/ = 落点（刀）/ 没意思 | `ToolHandler.tap` / `armable` / `repeatTap` |
| 空处拖 | = 框 / 套索 / 什么都不做 / 相机 | `BoxDrag`（刚收）、手势路由 |
| 布尔默认 | 替换 / 加 / 切换 / 减——**按手势 × 设备**（§3-7 拍了）：鼠标 点 = 替换 / 框 = 替换 / 套索 = 加；笔 点 = 切换 / 框 = 加 / 套索 = 加（笔没有 Shift，框错了清掉重来就行，user「触屏框错了可以clear all selections」）；手指以后、先照笔 | `selecting.ts selModeOf` + 工具配置「选区」两档 |
| 方向默认（frame） | 这把工具沿什么动：视线平面 / 推断 / 法向 / 面内 / 视线轴 / 均匀；把手旁「世界 / 物体 / 法向」按钮改它，**每把工具自己记**（user 10-26「是工具自己记住的选项。而且每个工具单独记」） | 各工具 solve 里写死 |
| 吸附立场 | 默认推断（SketchUp）/ 默认不吸（Blender）/ 无 | 各工具；Shift 的意思从它推出来（修饰键稿 §2） |
| Shift / Ctrl / Alt | Shift = 把吸附立场反过来；Ctrl = 这把工具的另一种做法；Alt = 换目标（环 / 洞、沿法线） | 修饰键稿 + 各工具 |
| 锁的种类 | 轴 / 面 / 无（方向键、X Y Z） | `ToolHandler.lock` |
| 轴心 | 包围盒中心 / 平均 / 最后选的 / 抓的那个点 | `ctx.pivotOf` + 各工具 |
| 语法 | steps（按下 = 起点，再按 = 落定）/ direct（按住拖，松手提交） | `ToolHandler.grammar` |
| 键 / 图标 / 名字 / 在哪个工作台的左柱第几格 | | `main.ts TOOL_SPEC` / `MODE_RAIL` / `MODE_TOOL_LABEL` |
| 工具选项 | 段数、油漆桶模式… | `tool-config.ts`（已是表）|

**同一把工具在两个工作台立场不同 = 表里两行**（硬表面那行 = SketchUp，自由建模那行 = Blender），差异一眼看得见——这就是周账 F-117「两套肌肉记忆焊在一起」的解法：不是抹平，是**把焊缝画出来**，每一格你拍。工具模块（`tools/*.ts`）只剩「拿到目标以后做什么」（挤面还是挤边、插入还是倒角）——那一半是和几何核绑的。

### 2.4 把手（gizmos）：三种，各是某个窗口在画面里的那一半

| 把手 | 是谁的 | 管什么 | 现在 |
|---|---|---|---|
| **导航把手**（右上坐标球 + 手 / 放大镜） | 视口窗口 | 转视角、平移、缩放、切正视图；**状态灯**：吸附锁、镜像（§3-9） | 已是 |
| **指令把手**（镜像面的方块、变换的三轴） | 指令窗口（马前炮）——参数的画面版 | 拖它 = 改参数；和参数小窗同生同灭 | 镜像面有（大小已修成只看屏幕像素）；变换有 |
| **选区把手**（点一下弹出的箭头 / 环 / 方头 + 「世界 / 物体 / 法向」小按钮） | 工具的方向列 | 约束方向；按钮改这把工具记住的方向 | 没做（把手稿 `20261027-gizmo-design.md`） |

规矩：把手**按屏幕像素定大小**（不随缩放、不随视角）；**模型上不画装饰**（user「自由建模模型上的干扰需要少一点」）——模型上只许：选区、中缝点、吸附标记、预演影子；别的状态去导航把手的灯或窗口里。

### 2.5 设备：鼠标 / 笔 / 手指 / VR（**词定死**：鼠标 = 键鼠；笔 = iPad 上的 Apple Pencil（现在只做这个，手指只管相机）；手指 = 没有笔的触屏（手机、笔丢了；以后）。不再说「触屏」，user 10-28「停，分手指触屏和笔。现在我们先只做笔。terminology说清楚不要歧义」）

控制器看见的手势（已经抽象出来的部分）：指针帧（射线 + 度量，`pointer-frame.ts`；VR 帧 = 手柄射线 + 角距，没有虚拟屏）、按下 / 跟随 / 松手 + 指针种类、修饰键 {Shift, Ctrl 类, Alt}、「要菜单」意图、点按族（几下）、**和工具分开的相机通道**。设备只做两件事：适配器把物理输入翻成这些；立场表里「默认值」那一列按设备分。

| 设备 | 工具指针 | 相机 | 菜单 | 修饰键 | 还缺什么 |
|---|---|---|---|---|---|
| 鼠标 + 键盘 | 左键 | 中 / 右拖、滚轮 | 右键 | 键盘 | — |
| **笔**（iPad；现在） | 笔（悬停 = 吸附预告；点两下） | 手指（单指转、双指平移缩放、双指轻点撤销） | 笔长按 | **芯片**：选区两档、锁轴徽章、复制开关、（吸附反转没有——§3-3） | 吸附反转芯片 |
| **手指**（手机 / 笔丢了；以后） | 单指（「手指画」开关已有） | 双指 = 平移 + 缩放 + 转；单指平移 / 缩放走导航把手的手 / 放大镜 | 长按 | 芯片放大、常驻；软鼠标（user 10-25 脑洞） | 窗口变底部抽屉、左柱折叠、点按精度（探索）；**默认值先照笔** |
| VR | 手柄射线（`xr-pointer-frame.ts`） | 握把抓世界（没做）；摇杆 = 走路（`player/`） | 手腕面板 | 手柄按钮 | 握把相机、手腕面板吃放置表 |

### 2.7 「什么时候按 X 是什么意思」= 键表按上下文分层（user 10-28「不是说x代表什么，而是说，在什么时候，按x是什么意思」「不知道这个最好的架构是什么」「也许不一定是combo，我也不知道状态机是不是太臃肿」「状态机会组合爆炸吧。然后写条件容易错，行为树可能太复杂了专业也不对口」）

三个候选都不要：**状态机**要枚举状态 × 工具 × 阶段，组合爆炸，转移表养不起；**条件表**（VS Code 的 when 子句）每条绑定写一串谓词，容易写错、读不出全貌；**行为树**是给 NPC 决策的，对口不对。
要的是 **分层键表 + 上下文栈**（Emacs 的 minor-mode 键表叠加、Blender 的「窗口 → 区域 → 编辑模式 → 正在跑的 modal 算子」四层键表，同一个思路）：
- 每一层 = 一张小表：`键 → 动作`（十来行）。层有：**工作台层**（硬表面 / 自由建模 / 表面 / 验证）、**工具层**（移动 / 挤出 / 选择 …）、**手势层**（按下了 / 点了一下在等第二下 / 键盘起手的模态中）、**临时层**（连击：上一步刚挤出完、在等 G；镜像会话中回车 = 应用）。
- **栈不是状态机**：每次按键时，从编辑器现状**算出**现在压着哪几层（纯函数 `layersOf(state)`：工作台一层、当前工具一层、手势在不在、有没有临时层），**从顶往下找第一个绑了这个键的层**。没有转移、没有要枚举的状态——层是加法不是乘法；「什么时候」就是「现在栈里有什么」。
- 你拍的 X 在这里是三行：工作台层（自由建模）`X → 删除`；工具层（移动 / 旋转 / 缩放 / 挤出 / 插入 / 沿法线）`X → 锁 X 轴`（= 这把工具 = 自动按了 G）；手势层 `X → 锁 X 轴`。拿着选择工具 = 工具层没绑 X → 落到工作台层 = 删除。**不用写一个 if。**
- 连击（combo）= 工具做完一步时压一个**临时层**（带超时或下一下动作就弹掉）：「刚挤出完」层绑 `G → 挪同一批点`。连击系统你说要自己想——想好了就是往这类临时层里填表，架构不用变。
- 笔 / 手指没有键：同一层的表可以声明「在笔上显示成芯片」（锁轴徽章、复制开关就是工具层那几行的触屏渲染）。
- **肌肉记忆守卫**：比较两个工作台的工作台层 + 同名工具层，同一个键绑了不同动作 = 列出来给你拍（E 橡皮 vs 挤出、A 弧 vs 全选、G 建组件 vs 抓…）。层内不许一个键两行（表不许歧义）。
- **披露**：状态行 / 帮助页按栈顶往下列「现在 X = 锁 X 轴（移动工具）」，用户看得见为什么。
- 和立场表的分工：立场表管**手势**（按下 / 点一下 / 空处拖 = 什么）和修饰键（Shift / Ctrl / Alt 的意思）；键表管**单独的键**（X / G / E / 方向键 / 回车 / Esc）。手感表管数字。三张表都住 `src/controller/`。
- 今天的代码：`main.ts` keydown 里一长串 if（自由建模的 Blender 键、方向键锁、Esc 的四层、数值小窗抢键）= 这张栈写散了。落码 = 零行为变更先把它抄成层，再按你拍的 X 改一行。

### 2.6 控制器的窄接口（无头骑士：换成 Blender / SketchUp / ZBrush / Unity 的几何核，能插上吗）

三条缝，今天都在、都有漏：

| 缝 | 控制器看见什么 | 今天的代码 | 漏在哪 |
|---|---|---|---|
| **进**（设备 → 控制器） | 指针帧 + 按下 / 跟随 / 松手 + 修饰 + 点按族 + 相机通道 | `pointer-frame.ts`、`ToolPointer`、`gestures.ts`、`tap-train.ts`、`xr-pointer-frame.ts` | 基本干净；键盘快捷键散在 `main.ts` keydown |
| **读模型** | 世界视图（各池合成到世界坐标的点线面 + 变换 + 槽，`WorldView`）、内核显示契约（`KernelView`：面环 / 平面 / 显隐）、拾取和吸附服务、选区、上下文 | `scene/world-view.ts`、`scene/kernel-view.ts`、`pick.ts` / `solver.ts` | **工具直接拿 `Kernel` / `MeshKernel` 查几何**（`ctx.kernel()` / `ctx.mesh()`）——换核就要改每把工具 |

诚实的答案：**能插，但按工作台插**——自由建模的控制器插 Blender 的 BMesh（mesh 族 op 和 bmesh 算子基本一对一；`KernelView` 包一层 BMesh 就行）；硬表面的控制器插 SketchUp 的 API（画线 / 推拉 / 跟随）；一个控制器通吃四个核不成立，因为「拿到目标做什么」那半本来就是核的语义。ZBrush 是雕刻（笔刷 = 配置好的指令 × 一笔，注册表提案 §2.4 留了位）；Unity 不是几何核，是场景 + 组件——我们的物体层（定义 / 实例 / 变换 / 层）对得上。

folder（user「可以工程文件也单独隔离出一个folder」，我读作「控制器的代码单独一个文件夹」——读错了说一声）：样板就是 **`src/player/`**：零 kernel / three / DOM import、node 直测、窄的 `WorldQuery` 当模型接口、`InputFrame` 当输入接口。编辑控制器照它搬成 `src/controller/`（工具 / 立场表 / 放置表 / 选法 / 把手数学 / 参数会话 / 窗口模型），只许 import `src/controller/api/` 里的接口类型；守卫测试 = 文件夹里不许出现 `../kernel/`、`../mesh/`、`three`、`document`。今天 `editor.ts` 3800 行是 C 和 M 的胶水混在一起、`main.ts` 1460 行是适配器和窗口混在一起——**探索期不做大搬家**：先画线 + 守卫只管新文件，碰到哪个搬哪个。

- 草稿的数据怎么接（不是拍板，是给「到时候定」留的形状）：**一张「纸」= 一个坐标架（原点 + 两根轴，= 硬表面的绘图面 / 坐标架那套）+ 纸上的二维笔迹数组（每笔 = 点串 + 粗细 / 压感 + 不透明度）**；参考图 = 同一种纸，只是纸上贴的是像素而不是笔迹；纸可以「钉在屏幕上」（视口层，storyboard）或者「立在空间里」（3D 存，转过去看还在）。拿起笔立刻画 = 没有纸就按当前坐标架 / 正对视线过原点自动起一张，**不问大小**（纸无限大，边界按内容）。套索 + 变换 = 在纸的二维坐标里做（含透视变换 = 单应，矢量点精确变、像素要重采样）。所以**先矢量**（笔迹 = 折线），像素那一半等和 WeebPaint 结婚时再决定要不要铅笔质感的栅格——这就是你说的技术权衡，数据结构两种都接得住：纸的内容 = 笔迹数组 | 像素块，二选一或并存。

### 结论（10-28 下午，user「有自己摆放、有身份的 → 对象 借用这一层坐标架的脚手架 → 这一层定义的一个组件 哈哈哈就是unity里面要不要借this.transform。同意」「所以基本就是component逻辑了？话说gltf是不是也是component」「以及我天天骂unity，我这个算不算长大了变成自己最讨厌的人。这是一个需要认真回答的设计哲学问题」）

**判据定了：借不借这一层的 this.transform。** 借 = 这一层定义的一个**槽**（component）；不借、自己摆放、有身份 = 对象。按这个判据：
- 尺规：画在这一层的坐标架里、吸附这一层的几何 → **借** → 定义的一个槽（一个数组）。我上一条「挂工程层」**撤回**（它违反刚拍的判据）。「父子互相看得见」是显示 / 吸附规则（所有层的尺规都画、都能吸），不是归属；「不是交付物」= 导出不带、一键清；一个组件几份实例 = 几份尺规，脚手架随手擦，不是问题。网格体定义也就有尺规了（今天只有硬表面体有 = 要搬家）。
- 参考纸（参考图 + 草稿）：**不借**（跟工程不跟模型，你拍的）→ 工程层的一副牌（`CATSUP_references` 扩出来）；纸自己有坐标架。
- 猫娘卡 / 以后的验证实体：自己摆放 → 对象（另一种身体 / 实体）。
- 物体级属性（对称、默认平滑、锁、藏、层）：不是槽，是定义 / 实例上的字段。

**是不是 component 逻辑？是，但是 glTF 那种，不是 Unity 那种。** glTF 的 node = 一个 transform + 几个**有类型的固定槽**（mesh / camera / skin / 扩展各一个），不是「任意挂一串脚本」。CatsUp 的 `Definition = { name, instances, body, guides, … }` 已经是这个形状：加一种槽 = 加一个有名字的字段 + 它自己的窗口 / 工具 / 格式拍子 / 迁移（和「加一种身体 = 五处各登记一行」同一条纪律），**没有「添加组件」按钮**。

**会不会变成自己最讨厌的人（认真答）。** 你骂 Unity 骂的不是「节点 + 面向」这个数据形状——那是 glTF、USD、Maya 的 DAG、SketchUp 的组（变换 + 实体）都在用的范式，本质就是数据库的范式化：一张节点表 + 每种面向一张表按节点 id 挂（你给网格内核拍的列式数组也是这个）。你骂的是 Unity 拿这个形状**卖的产品**：① Inspector = 选中谁就把它所有组件堆给你看（你今天拒掉的那个）；② 组件 = 行为（MonoBehaviour），东西是靠用户把零件拼出来的——「什么都可能，你自己配」= 直乘 = 元编程；③ prefab / variant 那套配置当内容。这三条我们一条都没借：窗口按类型一个指针；行为全在工具和立场表里（C），槽只是数据；槽有类型、有限、由我们定立场（坦克就是一个身体，尺规就在那儿，不用「添加尺规组件」）。把一个想法和卖这个想法的商店分开看，不是变成它，是长大了能分清——你自己的话：「天下所有的飞行员都是用cessna飞的」「一屋子乐器，贝多芬没等到合成器，但是也没被乐器锁死」。
真正会让你变成它的地方在**验证纪元**：猫娘 = 碰撞体 + 寻路 + 相机 + 枪…，那时候「开放的组件列表」最诱人。现在立一条规矩挡住它：**槽永远有类型、有限、每个槽自带窗口和立场；要「任意组合」的需求先回到「这是哪一种实体」**，不开通用组件列表。

### 主体互斥（user 10-28「然后brep和mesh互斥，你可以想一下。也许是辅助的随便挂，但是主体，这个物体是什么。得互斥？」）

对，互斥。定义 = { 名字, 实例, **身体（硬表面体 | 网格体 | 以后的种类，有且只有一个）**, 尺规?, … }。glTF 同款（一个节点最多一个 mesh，schema 禁止两个）；也是你 10-24「每个物体有一个 kind，可以换，换了要 explicit cast」——换种类 = 把那一个槽整个换掉。为什么必须互斥：「这个物体是什么」只能回答一次，工作台 / 工具 / 指令 / 拾取 / 导出全按身体种类派发，两个身体 = 两个工作台抢一个物体、点中的是谁说不清、导出成什么说不清。要「硬表面体上贴一块网格装饰」= 子物体（自己摆放、自己的身份），不是第二个身体；以后真要「内部同时含两种」= 一种新身体（自己内部管两份），对外还是一个槽。辅助槽（尺规、草稿牌…）各自可选、互不知道、和身体是什么无关，各有自己的窗口页 / 工具 / 格式拍子。

### GameObject / Component 体系的本质、解放与代价、选不选（user 10-28「我骂unity是gdtf里面的骂，骂的是gameobject component体系，我当时是想数据驱动。不过后来我好像想明白了是我幼稚了，也拍板决定了可能realhome就是需要gameobject component体系，而不是所有的都得像全面战争 环世界一样都是数组。嗯其实我就是当时想要裸数组」「现在的关键不是我为什么要骂unity，而是gameobject component体系的本质是什么，他的liberation和代价是什么，我们该不该选它」「gdtf可以考古一下」「①…②…③… 这三个确实是我想避免的」「猫娘…对，所以就是老游戏的一个struct字段，反正到时候再头疼吧，geometry node和shader都是同样的关键决策点」）

**考古（GDTF，2026-08-14，你的日记 `20260716 GDTF/20260814 meta/journals/20260814 复活initiative.md` + 当天会话）**。你当时骂的原话：「Unity最让我疼恨的（其实godot, unreal也没法免俗）就是每一个gameobject都必须有一个scenegraph的户口。可能我一直做不了走格子的游戏比如dungeon crawl, 战棋，环世界…I cannot cope with the idea that goblin belongs to the pirate ship and being life-cycle managed」「modern oo scripting lures metaprogramming and over abstracting. but those abstract gameobject/component/physics engine do lure people to make the most general, compatible, abstract descriptions. and make concrete content shameful…[SerializeField]TriggerABC.onTrigger += [SerializeField]UnityEvent…the actual plot is buried into a bloated scenegraph that have 10000 props, and the guid soup」「actually data driven is good, and is my goal. but what changes in 2025 is for LLM the best data is code, not manifest and guid」「要不要上ecs？还是ecs是毒，任何引擎强制的scripting协议都是毒？我们需要的是spec层次的约定，而不是编译器检查的协议」。你当时的解法：「MVC彻底分离。游戏是headless world model」「强plugin化…even hierarchy, transform are not inherent to an entity. an entity is just an entity」。当天会话的结论（AI 写、你没推回）：「scenegraph 的罪不是每个对象要户口，是假装存在一个万能且唯一的层级…真实结构是约束图，按 system 分成多张图」「E 是外键，C 是列，全是关系模型的水管；S 才是游戏本体…争的只是存储布局」。

**本质**：GameObject / Component = **一个开放的关系模型** —— 实体只是一个 id（外键），每种面向是一张表（一列），任何人随时能加新的列类型（写一个脚本 = 一种新组件），运行时按名字查（`GetComponent<T>`），外加**一列强制的**：Transform（场景图户口）。它和三样东西是同一个模型的三种姿势：
- **老游戏的 struct**：同一个关系模型，但**模式封闭**——怪物有哪些字段编译时就定了，加字段 = 改结构、改存档版本。
- **ECS**：同一个关系模型，列式存储 + 系统按原型批量跑；模式每个构建封闭、可组合。
- **GameObject / Component**：模式**开放**（谁都能加列）、对象是口袋、行为住在列里（MonoBehaviour）、一列强制（Transform）。

**它解放的**：① 组合代替继承树（一扇门同时是武器：挂两个组件就行，不用设计类层次）；② 晚绑定——工具、插件、第三方不碰引擎核心就能给任何对象加面向（Asset Store 生态全靠这个）；③ 引擎不用知道你的游戏：一个 Inspector 画所有对象、一个序列化器存所有对象、一个场景文件装一切；④ 原型快：往上糊组件就能试；⑤ prefab = 组合的复用。
**它的代价**（每一条都是从「开放」直接推出来的，不是 Unity 做差了）：① 强制户口——万物必须是空间节点，走格子 / 回合制 / 视觉小说的认知失调（你 8-14 骂的）；② 模式开放 = 没有封闭词汇 = 「这个东西是什么」没有答案，只有「它组件的总和」→ 每个系统都得去探（`GetComponent`）、哪些组件必须共存的协议写在哪里都不是 → spiral；③ 行为住在列里 → 剧情埋进场景图和 guid 汤、配置当内容（你 8-14 的陷阱门例子）；④ **Inspector 不是 UX 失误，是开放模式唯一可能的 UX**——你没法给「任意对象」设计一个窗口，只能把它所有的列堆出来（= 你今天拒掉的那个）；⑤ 每种组件 = 自己的存档格式，meta 文件一动雪崩；⑥ 指针追逐（ECS 修的是这一条，修不了②③④）。

**该不该选**：选**关系模型 + 每个纪元封闭的模式** = 你刚说的「老游戏的一个 struct 字段」。具体到 CatsUp：定义 = struct { 名字, 实例, 身体（恰好一个）, 尺规?, … }，实例 = struct { 变换, 锁, 藏, 层 }；模式按发布版封闭（格式拍子 + 迁移），每个字段自带窗口页 / 工具 / 立场。这样得到：封闭词汇（「是什么」只答一次）、按类型开窗口（因为我们知道有哪些字段，Inspector 的堆法就不必要了）、没有 guid 汤、格式有版本。放弃的：晚绑定的开放性（第三方组件——我们本来就不要，那正是喂 spiral 的那条解放）和运行时随手组合（门 + 武器——建模 app 里用「新的一种身体」或子物体接；验证纪元里用有类型的实体种类接）。
三个要避开的（你确认了）在这个选择下是**结构上**避开的：窗口按类型 → 没有 Inspector 堆；行为在工具 / 指令 / 立场表（C）里、槽只是数据 → 没有「组件 = 行为」；预制 = 定义 + 实例（glTF 的东西）、不是配置层 → 没有 prefab / variant。
**RealHome 那句「可能需要 GameObject Component 体系」**：按 8-14 的你自己的话，RealHome 要的是「每种实体有类型的面向（可抓 / 门 / 碰撞体…）+ transform 不是实体固有的」——那还是封闭模式的关系模型，不是开放口袋。真要开放口袋的只有一种场景：让别人往你的引擎里塞你没想到的东西（生态）。你不卖生态。
**同一个决策点还会再来三次**：验证实体（猫娘 = struct 字段，你拍了）、几何节点（修改器 / 预制 vs 语义工具——10-28 凌晨你拍了「镜像是 unnegotiable 的编辑工具…细分更像预制」）、shader（语义材质 vs shader graph——10-27「shader graph 可以有但只是用来产出 shader 的，shader 是原子」）。三次的答案形状一样：**封闭词汇 + 可以按版本加词，不开放图**。
