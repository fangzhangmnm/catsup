# 颜色空间的约定

> created 2026-11-11 by Claude Fable 5.2 · as-of v0.19.35
> 一页约定：颜色在哪里是什么空间、哪一步可以换算。改渲染、改贴图、改画的显示之前先读。拍板的出处在 `ai-docs/talks/20261030-materials-color.md`（三轮）和本页末尾 user 11-11 的话。

## 一、user 定的

- 10-30：「（其实我比较喜欢srgb）」「文件边界换算 同意」「我做retro game是要调srgb的」「每个画风在哪个空间里算 对，渲染里面可以调……颜色因为我们的语义是颜色，html css也是srgb对吧，weebpaint也是……可以和weebpaint对齐。但是我们的写实引擎可以走linear，复古走srgb，可以吗」。
- 11-11：「我们的画画软件是比较忠实的在 sRGB 上面对吧？……我是比较倾向于内容创作的时候还是用 sRGB，但是渲染的时候是线性……关键是说，我想兼容就是 N 六四这种老设备的图，因为我很多时候做游戏都是画的，直接 shadiness 没有明暗，或者乘以一个非常简单的明暗直接端上来，而不是我希望我画的时候和显示的地方插一个色彩空间的变换，然后就会显得偏白。」

## 二、约定

1. **颜色的意思是 sRGB。** app 里的材质色、调色板、取色、画上去的像素，存的都是 sRGB 的数（8 位）。
2. **画的时候在 sRGB 里混。** 笔的累积、图层的混合照画画内核（它在 sRGB 的 8 位数上算）。
3. **复古的画风（线稿 / 白模、像素描边、1 bit、剪纸）从画到显示全程 sRGB，中间不许插换算：**
   - 贴图取样拿到的就是存着的数；
   - 放大、缩小时的过滤，缩小图的取平均，都在 sRGB 的数上做；
   - 明暗 = 这些数直接乘一个系数；
   - 写到屏幕上的就是算出来的数。
   判据（探针 `probe-texture-srgb`）：不打光时，256 级灰阶每一级读回来都是它自己。
4. **写实的画风（写实、铸铜）在线性里算光：** 取样之后换成线性，算完压回来。它的缩小图在线性里取平均。
5. **只有文件边界换算材质色：** glTF 规定 `baseColorFactor` 是线性值，写出去换、读进来换回（`src/format/color-space.ts`）；贴图的图片 glTF 规定就是 sRGB，不换。
6. **「在哪个空间混」是画风的一项**（10-30 定的方向）：现在两档（sRGB、线性）；以后照画画软件加 oklab、spectral。

## 三、现在和约定差在哪（11-11）

- 第 3 条里「过滤和缩小图在 sRGB 的数上做」**现在没做到**：给渲染器的贴图建成了会自动解码的格式（`SRGB8_ALPHA8`），所有画风的过滤和缩小图都在线性里做。这是 W-14（v0.19.17）时 Fable 裁定的（「过滤和缩小图在线性里做，对的」），对写实成立，对复古不成立，和 10-30 的拍板矛盾。后果：放大（最近邻）不受影响，逐级相等；缩小时，细碎、对比强的地方比在 sRGB 里平均的结果亮（黑白相间：线性平均 = 188，sRGB 平均 = 128）。
- 改法（交小弟）：
  - 给渲染器的贴图（画的显示图、导入的图）改成不自动解码的格式（`RGBA8`），取样拿到的就是存着的数；
  - 复古画风的着色器直接用这些数（W-14 加的那一步「编码回 sRGB」去掉）；写实画风取样之后自己解成线性；
  - 缩小图已经是自己做的（v0.19.35 起）：取平均的着色器加一项「在哪个空间平均」，跟着画风走；换画风时缩小图按新画风整套重做一次；
  - 探针：256 级逐级相等照旧；新加一条「缩小着看一张黑白相间的图」——复古画风读到 128 左右，写实读到 188 左右；截图基线里带贴图又缩小着看的场景会变，照规矩写一行为什么再重冻。
