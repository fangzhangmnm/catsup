## 一、制度

**叫法**（user 11-13 夜：「其实我比较想叫 property，就一个叫 attribute，一个叫 property。」「正好两个中文名字都叫属姓，你可以想下分别怎么分」；「元素容易让人想到魔法，我还是想争取一下图元」。中文的这一对是统筹照 user 的意思配的，user 还没最后点头）：

| 英文（代码、文档） | 中文全称 | 是什么 | 量词 | 界面上的短名 |
|---|---|---|---|---|
| attribute | 图元属性 | 点、边、面、角的属性，每个图元一个值 | 一列 | 物体窗口的「图元」页（现在叫「元素」页） |
| property | 物体属性 | 物体的属性，自成一体的一块 | 一项 | 物体窗口的「物体」页 |

- **图元** = 几何的一个部分：点、边、面、角、面边、面的一侧；以后的格点、体素。图 = 图形，不是显示——藏着的面、不画出来的角也是图元。整个的东西叫物体，不叫图元（SketchUp 把组和组件也叫图元，我们不）。
- 按「是谁的属性」分。只管某一份摆放的那种也叫物体属性，行尾标「只管这一份」。
- 改过的叫法：这一页第一稿的「数据块」= 物体属性；第二稿和属性规程里的「元素」「元素属性」= 图元、图元属性（user 11-13 早些说过「物体元素行吧」，同一晚改口）。

### 物体上只有三样东西

| | 是什么 | 挂在哪 | 换种类时 |
|---|---|---|---|
| 几何本身 | 点、边、面，以及它们怎么连 | 内核里 | 真的换算；只有这里可能丢东西，丢什么在转换那一步报 |
| 图元属性（属性列） | 每个图元一个值的一列数：面的材质号、接缝、贴图坐标 | 点 / 边 / 面 / 角 / 面边 / 面的一侧 | 跟着几何走（切开、并掉、新长照属性规程的规矩表）；内核不懂它的意思 |
| 物体属性 | 一项自成一体的数据：坐标架、对称设置、材质槽表 | 物体（定义）上，或者一份摆放上 | 原样留着；新种类用不上的变灰、不起作用，转回来还在 |

种类只决定一件事：几何由哪个内核来管。

### 规矩

1. **没有第三个地方**（user 的硬要求）。物体上的数据不是属性列就是物体属性。场景上另开一张按物体记的表、内核上挂一个设置字段、身体上放一张种类自己的表，都不许。
2. **不懂它意思的那一层，也必须把它带着。** 物体属性的带着 = 原样留；属性列的带着 = 跟着图元走。「不认识就原样保留」只对物体属性成立：属性列是按图元排的，几何一换算图元就变了，原样留着会挂到错的图元上。
3. **物体属性不许按序号指着图元。** 凡是每个图元一个值的，做成属性列；物体属性只按名字引用那一列，引用别的条目只用 GUID。有了这一条，第 2 条里的「原样留」才安全。
4. **代号列和它的对照表是一个整体。** 一列里存的是小编号时（材质槽号、在哪套排法上），编号只是某个物体属性里一张对照表的代号（家规：没有对照表的编号不合法）。这样的列和那个物体属性一起生、一起删。
5. **生死按引用，动作不顺手删别的东西。** 普通的列没有任何物体属性在用 = 孤儿列，面板上标出来，人自己删。拿掉画、关掉对称、换种类都不删列、不删别的物体属性。
6. **变灰不等于删。** 当前种类用不上的物体属性留着、不起作用、能手动删。起不起作用只看「这种物体属性 × 这个种类」那张登记表，物体属性自己身上没有开关。
7. **缺 = 现行的默认。** 物体上没有某种物体属性 = 那一样按现在的默认算。物体属性里写的是值本身，不写「相对默认差多少」。恒等的、等于默认的不另存一种写法（坐标架已照这条做：恒等一律存成缺）。
8. **全部登记在册。** 第二节的表就是册子；程序里有一张对应的登记表和一个守卫（第五节）。
9. **一样东西只有一个家**（user 11-13 夜：「这个是硬规矩，进设计文档」）。整个物体一个值的，一律是物体属性；图元属性严格是每个图元一个值。不做「挂在整体上的图元属性」。
10. **同一样东西只做一份**（user 11-13 夜：「我绝对无法接受的是……同一个东西做两份，有 ECS 版本的 Transform 和 Component 版本的 Transform」）。一个意思在登记表里只许有一份声明；以后换存法是改这份声明，不是另起一个。
11. **算法只经物体属性和图元属性读写数据**（user 11-13 夜：「以后所有的算法访问就都得访问这些 component 或者 attribute……但是也要保证性能」）。工具、渲染、导出、以后的脚本都走同一个入口；性能的办法 = 热路径先把那一列（或那一项）拿在手里再循环，不每次按名字查。
12. **没有隐藏数据**（user 11-13 夜，筑基阶段就做到：「我们这里读到的数据就是我们写到文件里的，我们写到文件里的就是我们这里读到的数据」「把不认识的东西都交给用户来折腾」「几何里所有上盘的数据都能看到……至少是有哪些东西都能看到」）。做法见第六¾节第 6 条起。

### D. 硬表面里的组

组 = 几何的分区（user：「组不是物体只是管理sticky geometry用的」；09-06：「group 不是 object，是同一个 mesh……所以 group 其实是一个编辑时语义」），现在各有自己的内核、名字、坐标架、参考线，转成网格体时并成一池（转换清单里的「组分区」）。

**在制度下它是什么**（user 11-13 夜：「存组的容器是一个property，而不是一个组是一个定长的Property」）：装着所有组的那个容器是一项物体属性（不定长的那种，一张对照表：每个组的名字、坐标架、参考线）；每个图元属于哪个组是一列代号（这一半是统筹的读法）——又是「一列代号 + 一张表」。内核里各组各用一个池子是存法，对外是一份几何。这样落的话，转成网格体时组那一列可以照带，不再是损失。

### E. 不属于某个物体的（只被引用）

材质表、贴图表、排法表、层表、素材架、文档设置。它们是文件里的条目，按 GUID 被引用，生死按引用，在资源页管。不归这套制度；物体属性和属性列引用它们时只用 GUID。

## 三、现状和制度差在哪（施工的输入）

1. **住在第三个地方的**：对称设置在场景的表上；默认平滑在内核的字段上；材质槽表、贴图坐标的表、参考线住在种类自己的身体上，所以换种类就没地方放。
2. **硬表面内核没有属性表**：层是写死的两种，没有角、没有点；内核有四处认得层的意思。贴图坐标、接缝、用户的列带不过去，根子在这里。
3. **文件里列有三种写法**：网格体是专门打包的（面的材质、面的开关位、边的开关位、贴图坐标各一种）；硬表面是层；用户自己加的列不写。要收成一种。
4. **自由建模内核缺三类**：点、面边、面的一侧。硬表面的正反面材质搬过来要「面的一侧」。
5. **裸线的记号不是列。**
6. **物体属性没有容器、没有登记表、没有面板。**
7. **「两张面能不能并成一张」不看属性列**：转硬表面时共面的面自动并，两边的列对不上也并。

## 四、换种类时几何本身真丢的

接上属性表、物体属性搬完家之后，转换前的询问只剩这些：

- 硬表面 → 网格体：组的分区、曲线、折线、带洞的面（切成不带洞的）、只有背面有材质的面。
- 网格体 → 硬表面：不平的面（折成几块平的）、裸线、一藏一露背靠背的面、对不上的藏边。
- → 空物体：只在没有几何时能转。

对称设置、默认平滑、坐标架、材质槽表、贴图坐标、接缝、参考线、用户的列都不在这张单子上。

## 五、物体属性（property）的形状（user 11-13 夜定了方向；细则是统筹的）

1. **是什么**：一个类型名 + 一份纯数据（一份字典、JSON）。一个物体上每种类型最多一项。
2. **一项只管一件事**（user）。材质槽表一项、贴图坐标的表一项、对称设置一项、默认平滑一项、坐标架一项；以后方块表一项。判断法：能单独缺省、单独删、单独被引用的，单独成一项；必须一起变、分开没有意义的字段留在同一项里（对称的方式和轴是一项）。
3. **没有「必备」**（user：「主要是靠引用，就是没有的话就是 default」）。种类只登记「用得上哪几项」；物体上没有那一项 = 按现行的默认。唯一的硬约束来自引用：有一列代号，就得有它的那张表。
4. **对照表是物体属性的一种固定形状**：一张表一项，形状都一样——第几行 = 代号几，每行是一个身份（GUID）或者一小份数据。于是三件事全仓只写一份：跨物体粘贴时两张表合并、删一行时那一列重新对号、清理没人用的行。现状是材质槽和贴图坐标的表各写了一套（`mergeUvSlots` 和材质槽那一处）。
5. **复杂的聚合可以有**（user：游戏引擎 Inspector 那种）。三个条件：是一份字典、JSON；不按序号指着图元；引用别的东西只用身份。守住这三条，程序不认识的也能原样带着，面板按通用的样子把键和值列出来。
6. **住在哪**：定义上（所有摆出来的份共用），或者某一份摆放上（只管这一份）。几何之外，身体上不再放别的。
7. **登记表**（程序里一张表，每种类型一行）：类型名；给人看的名字；挂在定义上还是摆放上；哪几个种类用得上；是不是对照表、它的代号列是哪一列；它引用哪几列；能不能手动删；面板上怎么显示（不写 = 通用的键值样子）。
8. **不认识的类型**（登记表里没有）：原样留着，存盘原样写回，面板上按通用的样子列出来、灰、能删。
9. **换种类不碰物体属性。** 转换只换算几何和它的图元属性。新种类需要、物体上又没有的，按第 3 条就是默认；只有默认和「从那个种类转过来该有的样子」不一样时，转换明着写一项（例：硬表面转网格体，默认平滑写成「按角度 30°」，因为新建网格体的默认是全是棱）。
10. **守卫**：定义、摆放、身体、内核上每一个字段都要落到这张登记表或者图元属性的声明上，多一个没登记的字段 = 测试红。
11. **第一版不做**：一个物体挂好几项同一类型的；物体属性之间的先后；物体属性自己带开关。
12. **面板变长怎么办**：显示时按用途分组；分组只是显示，不改数据怎么存。

## 五¼、物体属性以后怎么存：两种形状，今天留的口子（user 11-13 夜提的方向；四条口子是统筹的提案）

user 的想法：有些物体属性是不定长的大块（比如图元属性的容器），各放各的；有些是小而整齐的，做成一个跨物体的大数组（ECS）。真正的排布细节等做超大场景再弄；但同一样东西绝不做两份，所以第一天要设计好。

统筹：可以。办法是让「怎么存」只是声明里的一栏，读写它的代码看不见。今天留四个口子（user 11-13 夜：「可以，不过其实这个就是c struct like，嗯你叫定长也对」——定长的记录就是 C 的 struct）：

1. **声明里多一栏「形状」**：定长的一条记录（只有数、长度固定：坐标架、对称设置、默认平滑），以后可以搬进跨物体的大数组；不定长的一块（对照表、字典、几何本身），各放各的。
2. **定长的记录第一天起只许放数。** 不放字符串、不放嵌套的东西；要指别的东西用代号或 GUID。文件里也这样写，以后换存法不动文件。
3. **只有一个入口读写**：「这个物体的这一项」和「所有带这一项的物体」（成批）。不许直接伸手拿字段（第五节第 10 条的守卫管）。
4. **一个意思只许登记一次**（规矩第 10 条）。

今天不做：大数组本身、内存里怎么排、对齐、成批调度。物体少的时候入口背后用最简单的存法。

一个观察：定长的物体属性排成大数组之后，是「每个物体一个值、按名字分列」，和图元属性是同一种表，只是一行是一个物体还是一个图元。所以两边的声明用同一个形状（名字、类型、缺省值），面板、存盘、登记表这些通用的代码写一份。这不改规矩第 9 条：它还是物体属性，只是存成了列。

## 五⅜、真相在表里，内核是编辑引擎（user 11-13 夜提的模式；下面的规矩和批判是统筹的提案，等 user 定）

user 的想法：物体属性和图元属性是唯一的真相；内核进去编辑时从里面读，干活期间可以有派生数据（越少越好），每一步提交回去——像画画软件里 CPU 的瓦片是真相、GPU 是派生，GPU 丢了从 CPU 重建。硬表面和自由网格各收成深模块、窄接口。

**规矩（提案）**：文档里的表是唯一的真相。内核手里多出来的任何东西都是派生的，丢了能从表重建。每一步结束时表和内核一致。

| 层 | 手里的东西 | 丢了怎么办 |
|---|---|---|
| 文档 | 物体属性、图元属性（含形状） | 这就是文件 |
| 编辑引擎（各种类的内核） | 为了改得快的索引 | 从文档重建 |
| 渲染引擎 | 合批、切片、LOD、显存里的东西 | 从文档重建 |

每一层的派生数据只归自己，别的层不许读。

现状（统筹读代码，没跑）：所有物体的内核常驻，内核自己的数据结构就是内存里的真相，文件是它的快照。硬表面内核里的派生数据：每条边挨着哪些面、面的环在平面上的二维坐标和包围盒、按平面找面的索引、按位置找点和边的格子、改动日志。渲染现在直接读内核和它的改动日志。

和画画不一样的三处：

1. **提交不是白来的。** 瓦片是固定的格子；图元会增、删、重排。提交要么只补这一步碰过的图元（要求表里的编号稳定、允许有空位；内核本来就记着碰过谁），要么整份重写（Blender 退出编辑、记撤销时就是整份写回，大模型上慢）。统筹建议前一种。
2. **派生数据里可能混进表里没有的东西** = 内存里的隐藏数据。守卫：任何时候把内核扔掉、从表重建，接着做同一串操作，结果必须一样。硬表面现在过不过得了没核过（平面登记处、编号的计数器这些要查）。
3. **「只有正在编辑的物体才有引擎」有代价**：进一个大物体要等重建；吸附和拾取别的物体不能靠它们的内核，归拾取那一层自己的派生数据。办法：最近编辑过的几个保着。

它不违反规矩第 10 条：那条防的是两份都算数；这里只有表算数，引擎那一份外面没人能读。

**种类模块对外的窄接口（提案）**：从表建出引擎；跑一条命令、交出这一步碰了哪些图元（预演和落定同一条）；提交（把改动写回表）；丢掉；转换（表进、表出，外加丢了什么）。种类之间不许互相引用。

**今天做多少（提案）**：定规矩、加「扔掉重建」的守卫、种类之间不互相引用。「不在编辑的物体只剩表、没有内核」真拆是大场景才需要的，先不拆。

## 五½、几何：每个物体必带的那一个（user 11-13 夜；说法是 user 的，细则是统筹的）

**三个词**：几何 = 物体的形状本身 + 它有哪几类图元；图元属性（attribute）= 挂在几何的图元上的一列一列的值，它不是几何、它长在几何上；种类 = 这个物体的几何是哪一种。

**几何是基类**（user 的说法）：图元属性那一套挂在基类上，基类派生出空物体、硬表面、自由网格，以后还有曲线、曲面、高度图地形、体素。像 Unity 的 transform，每个物体必带、只有一个。种类 = 派生类是哪一个；空物体 = 没有图元的那一个派生类。

### 挂在哪（user 11-13 夜问的；统筹的回答）

```
物体
├─ 几何（必带，只有一个；是哪一种 = 种类）
│   └─ 图元（按类分：点、边、面、角……）
│       └─ 图元属性：名字 → 每个图元一个值
└─ 物体属性：名字 → 一项（一份字典）
```

图元属性的那本字典是几何的一部分，不直接挂在物体上：它长什么样由几何定（有哪几类图元、每类多少个、怎么存）；换种类时它跟着几何一起换算；空物体没有图元，所以没有它，但照样有物体属性。物体上直接挂的只有物体属性。（统筹早先把几何说成「特殊的一项物体属性」，不对：几何不是物体属性，是必带的那一个。）

### 挂在哪，再想一遍（user 11-13 夜第二问；统筹的提案，等 user 定）

| 挂法 | 意思 | 问题 |
|---|---|---|
| 几何是一项能挂图元属性的物体属性 | 物体 = 一包物体属性，其中一项特殊 | 「只能有一项」要靠规矩守；换种类时别的物体属性原样留着，偏偏这一项要换算 |
| 物体下面有一个「几何」，图元属性挂在它里面，形状另放（上面那张图） | — | 形状成了第三种数据，既不是图元属性也不是物体属性，和「物体属性和图元属性就是文档的数据结构」对不上 |
| **图元属性直接挂在物体下面，形状也是其中几列** | 物体 = 种类 + 图元表 + 物体属性 | 见下 |

统筹建议第三种：

```
物体
├─ 种类（一个词）
├─ 图元表：每类图元一张，表里是列
│   ├─ 形状的列（点的位置、哪圈点围成面……保留名，不能删，只有这个种类的内核能写）
│   └─ 普通的列（材质号、接缝、贴图坐标、自己加的）
└─ 物体属性
```

- 「几何」不再是另外的容器，只是「种类 + 形状那几列」的叫法。
- 「一个物体只有一份几何」是结构上就这样：物体只有一套图元表。
- 文件和面板只有两种东西；「一个物体就是一本名字对应数组的字典」字面成立。
- 和第五⅜节合上：这套表就是真相，内核是读它、写它的引擎。
- 代价：硬表面多出几类图元（平面、曲线、面上的环），面板里归到「形状」那一块；形状的列不走通用的规矩表，怎么变由内核定，通用代码只管列出来和存盘；位置要双精度，列的类型加一种。
- 内存里它是「不定长、各放各的」那一类，但不进物体属性的登记表：它必带、唯一、换种类时要换算，这三样物体属性都没有。

### 几何的契约（基类向上面承诺的）

1. 我有哪几类图元（名单由几何的种类给，不许在属性表里写死）。
2. 每一类有多少个，图元怎么编号（网格用编号，格子用坐标）。
3. 我变的时候，新图元是从哪些旧图元来的（属性规程的七种来历）。
4. 我的图元属性怎么存是我自己的事（见下面两种存法）。**通用的那一层**（面板、存盘、清理、登记表）只许问「有哪些列、挂在哪类图元上、什么类型、多少个」和「读 / 写一片」，不许假设底下是一整个数组；**专门伺候某一种几何的代码**（网格的贴图坐标、交给显卡）可以直接用数组。
5. 形状是我自己懂的那一部分（点的位置、格点的高度、体素的密度）；别的列我不懂，只照规矩表带着。

图元属性表只靠这五条干活，不知道底下是哪种几何。属性规程已经这么写了（「类别的名单由几何的种类给」），硬表面内核还没照做。

### 几何和物体属性不一样的地方（所以它不是普通的一项）

- 一个物体必有、只有一个。
- 换种类 = 把它换算成另一种，不留旧的（留着 = 两份真相）；图元属性跟着走。
- 强类型的规矩（user 11-13）照旧：新建时定、不自动变、只有明着的动作才换。删光了面不会变成空物体。
- 面板上排第一行，带「切换种类」。守卫：不许给几何「灰着留着」那条路。
- 不走到 Unity 那一步：一个物体不挂好几份几何。

### 两种存法（同一个概念）

「名字对应数组的字典」说得太具体。准确的说法：图元属性 = 从图元到值的对应，按名字分列；怎么存是几何的事。

| | 列表型 | 格子型 |
|---|---|---|
| 图元怎么指 | 编号 | 坐标 |
| 图元会不会变 | 会新长、删掉、切开、并掉 | 格子固定，不会 |
| 怎么存 | 每类图元一本「名字 → 数组」 | 分块存，没有的块 = 默认值 |
| 有没有边界 | 有 | 可以没有 |
| 来历的规矩表 | 重头戏 | 几乎用不上（改大小、改精度 = 「之间」） |
| 有谁 | 硬表面、自由网格、曲线曲面、点云、成批的实例 | 高度图、方块世界、光滑体素、volume |

人眼里是同一个东西（面板上一行一列：名字、挂在哪类图元上、类型）；内核里是两种存法。格子型一做出来就是按块存的、没有边界，不先做一个定大小的版本（user 11-13 夜：「格子型就是默认支持chunk/tile based，第一天就支持，相当于我们做的东西都默认支持无穷大的」）。现在还没有格子型的种类，不提前写（统筹的读法：「第一天」指格子型的第一天）。

### 以后的几何种类（都不急着做；设计时放得进来）

| 种类 | 存法 | 图元 | 形状 | 图元属性 / 物体属性的例子 |
|---|---|---|---|---|
| 硬表面、自由网格 | 列表 | 点、边、面、角 | 点的位置 | 材质号、接缝、贴图坐标 / 材质槽表 |
| 曲线、曲面 | 列表 | 控制点、段或面片 | 控制点的位置 | 粗细 / 是否闭合、阶数 |
| 点云 | 列表 | 点 | 点的位置 | 颜色、大小 |
| 成批的实例（撒一万根草） | 列表 | 每一份 | 每一份的变换 | 原型的代号 / 原型的对照表 |
| 高度图地形 | 格子 | 格点 | 高度 | 地表材质的权重 / 地表材质的表 |
| 方块世界 | 格子 | 体素 | 是不是实的 | 方块的代号 / 方块表 |
| 光滑体素地形、volume | 格子 | 体素 | 密度 | 材质的代号 |

- **粒子系统不是几何**：人写的只有发射器的设置（一项物体属性）；粒子是运行时算出来的，不存。把某一刻烤下来才是一个点云。
- 「一列代号 + 一张对照表」反复出现：材质槽、贴图坐标的表、方块表、原型的表——同一个共用模块（第五节第 4 条）。
- 显示用的三角面是从格子算出来的，只在设备上记着，不进文件。
- 种类之间换算照旧是「几何真的换算」，丢什么在那一步报。

### 有没有各自的身份（物体还是图元的判断法）

- 人一个一个摆的、各有各的身份（名字、单独选、单独锁、出现在层级窗口里）= 子物体。
- 成批铺出来的、没有各自的身份 = 一个物体里的图元。层级窗口里一行。
- user 的说法：「杂兵没有名字，英雄有名字，所以total war warhammer里面一个unit是物体，unit里面的兵是图元」。
- chunk 不是物体、撒的一万根草不是一万个子物体，是这同一条。两边可以互转（收成一个撒布物体 / 炸开成子物体）。
- 推论：要长期指着某几个图元的东西（顶点组、存下来的选区）做成一列图元属性，不做成物体属性里的一串序号。

### 三条要守（第一稿叫「三处要防」；第 1 条统筹说错了，user 11-13 夜纠正）

1. **同一样东西只做一份。**（规矩第 10 条。）第一稿这里写的是「别做成游戏引擎」，错了。user：这个软件一开始的目标就是游戏引擎，只是专做数据驱动的场景编辑器；引擎长成那样是为了图形和物理的性能，游戏逻辑反而是最上面最随意的一块。以前定过的边界（09-06 的远景、10-30 四轮「游戏引擎的边界」）划在**规则**上：规则不写死进核心，是数据、进文件但不进层级树。数据这一层本来就照引擎做（09-06：「一个关卡文件里只有 Geometry 和 ECS 式的元数据」）。统筹把两件事混成了一句。
2. **一个物体只有一份几何。** 好处和代价见下一小节。（第一稿这里说「Blender 允许一个物体同时带网格、曲线、实例、volume」，不准：Blender 的物体本身就是一份数据、类型建的时候定，混着带的是几何节点算出来的结果。）
3. **一样东西只有一个家。**（规矩第 9 条，user 定为硬规矩。）Houdini 有挂在「整体」上的属性，等于把物体属性也塞进属性那一套；我们不这么做。

### 一个物体只有一份几何：好处和代价（user 11-13 夜要统筹想；下面是统筹的回答，user 还没表态）

别人怎么做：Blender 的物体、USD 的节点都是一个物体一份、一种类型——我们是把这个做法做得更严（种类不自动变、硬表面和自由网格算两个种类）。相反的是 Unity（一个物体一包部件）和 Houdini（一份几何里混着各种图元）；Blender 几何节点算出来的结果也是一包。

好处：

- 「我现在在改什么」只有一个答案：工具、键位、吸附都跟着种类走。
- 内核的规矩对整份几何成立（硬表面的面都是平的），不用到处问「这一块归不归我管」。
- 图元属性只有一本，面板是一张表；换种类丢什么只在一处算。
- 组合只有父子这一种办法，名字、锁、隐藏、摆放、复用都跟着白得。
- 文件好懂：一个物体就是一份某个种类的几何。
- 和「有名字的是物体」是同一条规矩。

代价：

| 代价 | 具体是什么 | 有没有办法 |
|---|---|---|
| 不同种类之间不能共用点和边 | 硬表面的盒子上长出一块雕塑，接缝焊不到一起 | 没有。只能两个物体叠着，或者整个转成一种；「来回切」就是在付这个 |
| 提出来和并回去必须随手、不丢东西 | 创作时把帽子提出来单独做、再拷回去；一棵树做到最后并成一个物体（user 11-13 夜纠正：第一稿这一行写的是「物体变多：一棵树至少是空物体、树干、叶子」，问错了问题） | 这两个动作带着图元属性走（按名字对上）、对照表合并、一步撤销；跨种类时经转换，丢什么当场说。是筑基的验收 |
| 跨物体的关系要明着写 | 「叶子撒在树干上」变成一个物体指着另一个 | 用 GUID 指，断了看得见 |
| 一样东西要好几份**人做的**几何 | 手做的碰撞体、手做的简化版 | 子物体加一项「用途」（USD 的 purpose 就是这样）。自动算出来的不算，见下 |
| 程序生成的结果常常是一包 | 生成器一次出网格的树干和成批的叶子 | 出成一棵子树 |
| 种类之间两两转换按平方涨 | 每加一种要和所有种类对一遍 | 定几个枢纽，都经它转 |
| 种类自己悄悄长成一包 | 硬表面里已经有面、裸线、曲线、参考线、组 | 一条判断：共用同一套点和同一套规矩的才算一份几何 |

统筹的看法：守住。第一行是这条路的本质，别的都有办法。

**内容创作是第一公民：打散和重组**（user 11-13 夜，原话在第零节）：

- 带着几何的父物体是常态（树干自己带几何，根物体自己是路网）。空物体只是当容器用的一个种类，设计时不许假设容器是空的。
- 结构是做的过程中流动的：把一部分提出来单独处理、拷回去、再提出来；最后常常并成一个物体。不是先定好有哪几个零件。
- 所以「一个物体只有一份几何」成立的条件，是**提出来和并回去随手、不丢东西**：同一个种类里提出来再并回去，没改过的话每一列原样回来；跨种类（提出来转成另一种做一下再并回去）走转换，带不过去的当场说。这是筑基的验收（现在这几个动作各带着什么走，统筹没核过）。

**自动算出来的 LOD、合批、切片归渲染引擎，不进文档、用户看不见**（user 11-13 夜倾向这样：「渲染引擎会进行静态batching然后重新分组切片」；统筹同意）。判断法和粒子一样：人写的进文档，算出来的归引擎；要缓存也只是设备上可以重新生成的缓存，和规矩第 12 条不冲突。进文档的只有人写的两种：手做的简化版或碰撞体（子物体 + 用途），和人给的意图（真要有，是一项物体属性）。

### chunk 不是物体（统筹的结论）

chunk 是几何内部的储存单位，物体是「这一整片地形」——像画画内核的画布按瓦片存、一张画是一个东西。

每个 chunk 一个物体的毛病：一笔跨四个 chunk、光滑体素要读隔壁的值，操作和撤销全成了跨物体的；层级窗口里几千个物体；方块表、材质表这种整片共用的物体属性没处放；chunk 多大本来是实现细节，做成物体就成了身份、进了文件，以后改不动。

user 说 chunk 不能走图元属性：容器那一半是对的（无边界的世界不可能是一整个数组），道理上它还是图元属性（每个体素一个值）。要改的只是容器：名字 → 分块存的数组，没有的块 = 空。所以有契约第 4 条。

**无边界、不用先定大小**（user 11-13 夜）：
- 图元属性是对外的那一面（按坐标、按一片来读写）；chunk 是它里面怎么存，对外不透明——外面不知道有几块、每块多大。
- 没有的块 = 默认值（没摸过的地方不存，读出来是空的或者平的）。和「物体上没有那一项物体属性 = 默认」是同一条规矩。
- 摸到哪、长到哪：第一次在某个地方刷，那一块才出现。地形多大 = 摸过多大；文件大小跟着摸过的地方走。不让人在动手之前填一个尺寸。
- 可以给一句不拦人的反馈（已经铺了多少块、多大）；不设上限（家规：app 不许硬拦）。
- 躲不开会漏出来的两处，都留在几何内部、不变成物体：撤销记这一步摸过的那几块；存盘一块一块存、改了哪几块重写哪几块。
- 和画不一样：画布现在要先定大小，地形不走那条路。

「块 = 物体」只在一种情况下对：人自己摆的模块（一间做好的房间，复制、旋转、到处摆）。那是物体的复用，和储存的分块是两回事。

## 六½、清理窗口（user 11-13 夜的设计；共用的深模块）

**规矩**：没人用的东西不自动删。「清理」是人点的动作：自动的只有「找出来」，删不删由人勾。

**窗口**（user 定的样子）：模态。一行一样东西：图标、名字、一个勾。最下面确认和取消。统筹补的：每行可以带一句小字（为什么算没人用、多大）；按来源分组；连着的行一起勾、一起取消；勾着的在同一步里清掉，撤销一下全回来；默认全勾，来源可以声明某样默认不勾（提案：带着人画的像素的画默认不勾）。

**接口**（窄；窗口不认识它列的是什么）：

```ts
/** 一样可以清的东西。 */
interface CleanupItem {
  id: string;                 // 这一次窗口里的身份
  icon: string;               // 共享图标库里的名字
  name: string;               // 给人看的名字
  note?: string;              // 小字：为什么算没人用、多大
  group: string;              // 分组的标题（属性列 / 物体属性 / 贴图 / 材质 / 物体……）
  checked: boolean;           // 默认勾不勾
  needs?: readonly string[];  // 这些行也勾着，这一行才能清（连带关系）
  ops: readonly Op[];         // 勾着时要做的指令
}
/** 一个会报「我这里有哪些没人用的东西」的地方。范围 = 整个文件，或者一个物体。 */
interface CleanupSource { id: string; collect(scene: Scene, scope: { def: DefId } | "file"): CleanupItem[] }
/** 收集 → 弹窗 → 勾着的那些在同一步里做掉。没有可清的 = 说一句、不弹窗。 */
function openCleanup(scope: { def: DefId } | "file"): Promise<void>;
```

- 来源现在就有的：没人摆的物体定义、没人用的材质、没人用的贴图（现在资源页各有各的「清理」，收进这一个窗口）、没有画挂着的排法。筑基之后加：孤儿列、没人用的物体属性、对照表里没有图元在用的行。
- 加一种能清的东西 = 加一个来源；窗口不动。
- 两个入口同一个窗口：物体窗口里「清理这个物体…」（范围 = 这个物体），资源页「清理…」（范围 = 整个文件）。
- 连带关系由来源报全：清掉 A 之后才变成没人用的 B，也列出来，`needs` 指着 A。
- 锁着的文件：窗口能看、不能清（修改锁那一张表管）。

## 六¾、文件格式怎么走（user 11-13 夜定）

1. **筑基做完之前不做任何向后兼容。** 格式想改就改；不认中间版本的写法，不加迁移。在 user 说可以之前，不假设 user 用中间版本存过新文件。
2. **筑基做完之后，文件格式升一个大版本。** 新程序只读新格式；读文件那一段里不留「老写法怎么读」。
3. **老文件归一个专门的转换程序。** 统筹的做法（等 user 看方案时点头）：
   - 把筑基开工那一刻的整套读文件的代码原样冻一份，当转换程序的前半段；后半段用新格式写出去。到那一刻为止的所有文件（连同第 1 版的定义 8.0）都转得了，不另写老格式的读法。
   - user 在 iPad 上没有终端：转换做成软件里一个明着的动作——打开老文件时说「这是旧格式，要转换才能打开」，点了才转，转完列出转了哪些东西，老文件留着不动（家规硬规则 #9：非转换不可才弹对话框、说明白）。
   - 转换程序和平时运行的程序不沾边：平时的代码不许引用它里面的老读法（守卫）。
4. **中间版本不让人踩到**：筑基在分支上做完再合一次，默认不往开发版推中间版。中间要推给 user 试的那一版，存出来的文件不保证以后打得开，存盘时明着说一句。
5. 所以原来等 user 定的「老位置认不认」= 新程序不认，归转换程序。

**没有隐藏数据（规矩第 12 条）怎么落**（做法是统筹的提案）：

现状（统筹读代码，没跑）：文件是一个 .glb。标准的一半 = 烤出来的三角形和材质，给别的软件看的派生物；我们自己的一半 = `CATSUP_` 开头的扩展，真正的数据在这里，数组放在 glb 的二进制块里（借 glTF 放 blob 的办法，glTF 标准不认识它们）。隐藏数据有三类：① 「不认识的原样带着」的口袋（顶层、扩展、文档、定义、硬表面那一段、材质、桌面、素材架各一个；读进来不认识的键和二进制原样写回，界面上看不见）；② 认识但界面上不列的（硬表面的平面表、容差、曲线登记、组）；③ 文件里是另一副样子的（材质号、隐藏、边的标记挤在几个字节里，贴图坐标按通道重排，读写各有一段换算）。

6. **文件照登记表写。** 一个物体写进文件的只有三样：几何本身（种类 + 它自己的几张表）、图元属性（每列 = 声明 + 数组）、物体属性（每项 = 类型名 + 数据）。名字和程序里的一样，不重排。写文件的代码把登记表从头列到尾，不一个字段一个字段手写。守卫：写出去的键和登记表逐个对上，多一个少一个 = 红。
7. **面板照同一张登记表列。** 物体窗口三块：几何（点、边、面各多少；硬表面另有平面表、曲线、容差）、图元（每一列）、物体属性（每一项）。只显示有哪些、多少个、多大；不做逐个改的界面（user）。
8. **不认识的东西是看得见的条目，物体这一层的口袋退役。**
   - 不认识名字的列：声明跟着列存在文件里，它照样是一列，照规矩跟着几何走，图元页里列出来。
   - 不认识类型的物体属性：原样留着、灰、能删（第五节第 8 条）。
   - 完全读不懂的（列挂在这一版没有的图元类别上；物体是这一版没有的种类）：打开时摆出来说清是哪几样，人选——留着（那个物体的几何只能看不能改，改了它就对不上了），或者删掉再编辑。不悄悄带，不悄悄丢。
9. **压缩不算隐藏。** 一列开关在文件里按位压是编码；条件是名字和形状一一对应，解开就是程序里那一列。
10. **范围**：这一版做物体这一层（定义、摆放、几何、图元属性、物体属性）。文档层的（材质表、贴图、排法表、素材架、桌面状态）和图片、音频以后做（user：「图像和音频资源，我们可以之后做」），那几处的口袋这一版还在。user 11-13 夜：「同意，然后未来的进wishlist」——后一半（文档层和图片、音频也做到看得见有哪些、口袋退役）记进愿望单，不排期。
11. **烤出来的那一半**（标准 glTF 的三角形）是派生物，面板里列一行（多大、可以重新生成）。以后还带不带它、外面这层壳换不换 = 「慢慢抛弃 glTF」，等 user 定。
12. 转换老文件时，老文件口袋里的东西在转换的对话框里列出来。
13. 「不同文件版本」统筹的读法：照这样做，别的版本写的文件只是「里面有几样我不认识的东西」，不再需要按版本分路；老格式的文件还不是这个结构，仍然要第 3 条那一次转换。
