## 0. 先说结论

**没有发现会丢文件、会坏存盘的问题。** 撤销的底子是好的。

有实锤、值得修的，按要紧程度：

1. **强行对称会悄悄不对称**（镜像，§4.1，跑过）。「是不是已经对称」的判定漏看三样：挖掉一张面（边还在）、翻一张面的朝向、边上的标记。这三种改动在强行对称下都不会镜到另一边，界面还说着「每一步都会对称」。
2. **强行对称下删东西，分不清动的是哪边**（§4.2，跑过）。在左边删一张角上的面，如果上一次动的是右边（或者刚开镜像还没动过），这张面会被右边镜回来，等于删除没生效。
3. **裸线不镜像**（§4.3，跑过；就是账上的 T45）。另外查出它的第二个后果：只要留着的那边有一条裸线或一个孤点，模型就永远判成「不对称」，之后每一步都把另一半整个删掉重建。
4. **选中的参考线被擦掉后，选区里还留着它**（§1.1，读码）。之后界面以为「有选区」，但画面上什么都没选中。
5. **自由建模的吸附会吸到看不见的旧位置**（§3.2，读码）。开着软选择或镜像时，跟着动的那些点原来的位置还是吸附目标。

没找到问题的：撤销（§2）、「拖动时越拖越偏」那种自己吸自己的回路（§3）、提示文案里的组合键（§5，现在提到的 15 种组合键在键表里都有）。

## 1. 选中参考几何，和 10-24 那批改动（F-84）

user 10-24 深夜的原话：「我设计方案：编辑器单独维护一份「选中参考几何id」集合，不混入内核实体的选区类型，避免影响其他消费方」。

### 1.1 说的和做的不一致：现状和后果

**现状（读码）。** 选中的参考几何还是住在选区类型里：`src/editor/tools.ts` 的 `BrepSelection` 有一个 `guides: Set<number>`。10-27 选区拆成硬表面 / 网格体两种以后，它只在硬表面那一种上，读的人走 `guidesOf(选区)`。所以 user 说的「单独一份」没有做，只是收窄了。

**该守住的不变量：** 选区里的每个编号，都指着活动层里一个还活着的东西。边 / 面 / 点由 `Editor.pruneSelection` 守（每次场景变了都清一遍死编号）。

**违反处（读码）：`pruneSelection` 不清参考几何。** 它清边、面、点、组和组件，唯独没有参考几何。于是：

- 用橡皮擦掉一条**正选中着的**参考线（`tools/erase.ts` 提交 `eraseGuides`，不动选区），或者菜单里「清空参考几何」（`Editor.clearGuides`），选区里那个编号留下来成了死的。
- 之后 `hasSelection()` 一直是真（它把参考几何算进去）。读它的地方有四十来处：右键出的是「选区菜单」不是「空处菜单」；Esc 先当「取消选择」用掉一次；移动工具走「对选区做」那一支，但选区里没有能动的东西，这一下按下去什么都不发生；右下角的选区条、左柱的「删掉选中」脸都会亮。
- 这时按 Delete：提交一条 `eraseGuides`，里面全是死编号，什么都没删，但撤销栈里多了一步「删参考线」。代码里别处特地写了「什么都没删就不假装删过」，这条路绕过去了。

没在 app 里复现；链条每一环都是直接读到的代码。

**撤销那条路是干净的**：撤销 / 重做时选区从记录里整个换回来，记录里的参考几何编号和场景是同一时刻的。

### 1.2 评修法

user 的方案（单独一份集合）和现状（塞进选区）各有一个真实的理由：

- 塞进选区：清选区的十几处自动连带清，撤销的会话记录自动带上。这两条是现状白拿的。
- 单独一份：别的消费方不会被「有选区但没有几何」这种状态吓到。上面那串后果正是这个状态造成的。

**建议：不用搬家，补不变量。** 现在只有硬表面那一种选区带它，读口也只有 `guidesOf` 一个，「影响其他消费方」的面已经很窄。要做的是两件：

1. `pruneSelection` 里加一段：参考几何编号不在活动层的参考几何表里 = 删。一处改动，橡皮、清空、以后任何删参考几何的路都被它兜住。
2. 把问法分开：`hasSelection()` 现在同时回答「有东西选中」和「有能被工具动的东西」。移动 / 旋转 / 缩放问的是后者，应该问不含参考几何的那个（已经有 `hasGeometrySelection` / `hasPointSelection`，缺一个合起来的名字）。

如果 user 还是要「单独一份」，代价是：十几处清选区要各补一行、撤销的会话记录要加一栏。我不推荐，但这是 user 的设计，由 user 定。

**顺带一条和家规的出入（读码）：** 参考几何的身份是每层一个自增编号（`Guides.next`），存在文件里。家规 10-30 说文件里条目的身份用 GUID、自增编号也算序号。现在没人跨层、跨文件引用参考几何（只有选区和橡皮在用，都是临时的），所以今天不出事；等到「尺寸标注挂在参考线上」这类功能要引用它时，要先换。

### 2.1 这条的来龙去脉

F-93 是 10-26 记的：Opus 先重设计，Fable 之后审。之后发生了三件事，把这条的大半做掉了：

所以这次审的是：**规章本身站不站得住，加上 10-28 之后新进来的指令有没有绕开它。**

### 2.2 不变量，和我怎么查的

**核心不变量：** 一条指令的撤销记录，必须盖住这条指令改到的全部状态。

记录分四档（`history.ts opTier`）：硬表面一层的差量、网格体整表、只拷骨架、整份场景。危险只有一个方向：**一条指令被分到便宜的档，实际改到的东西比那一档记的多**。比如分到「只拷骨架」却原地改了某个内核，撤销之后内核回不去，而且不报错。反方向（分贵了）只是慢。没登记的指令默认走最贵的整份场景，这个默认是安全的。

我写了个脚本（仓外）把 `ops.ts` 里 77 条指令和四张分档表对了一遍，再看每条便宜档指令的代码里碰了什么：

- 登记了但没有实现的：0 条。
- 「只拷骨架」的 26 条里，代码里出现内核的只有 `shelfFolderRemove`，读了一下是只读（克隆出去）。
- 「硬表面差量」的 17 条里，碰到组 / 实例 / 定义的有 `mirror`（带实例时已经改走整份场景）、`setHidden`（对实例时改走骨架）、`paintFaces`（改槽表，槽表在骨架里，这一档本来就顺带记一份骨架）。都对得上。
- 10-28 之后新加的 `purgeMaterials`（清理没人用的材质，同一步重排所有槽表）：只动材质表和槽表，都在骨架里；面上存的是槽号，不动。对。
- 修复插件一律按「硬表面差量」记，只有「层级」那条按名字特判成整份场景。现有十条插件里只有它动别的层，读码没发现第二条。

**结论：没找到撤销记录盖不住的指令。** 加上规章里的差分测试（每步之后「从头重放」和「活着的场景」比指纹）和 26 种动作的随机测试，这一块我认为是可信的。

### 2.3 留下的三个薄处（都不是现在的 bug）

1. **修复插件的分档靠名字特判**（`op.name === "hierarchy"`）。下一条会动别的层的插件，作者得记得来 `history.ts` 加一个名字，忘了就是「撤销回不干净、不报错」。修法：让插件自己声明「我只动这一层 / 我动整个场景」，`opTier` 读声明；没声明 = 整份场景。和「没登记默认最贵」是同一个安全方向。
2. **「只拷骨架」那 26 条没有机械守卫**。现在靠读码 + 随机测试。可以加一条便宜的测试：每条骨架档指令跑一次，前后对每个内核算指纹，变了就红。
3. **随机测试的指纹不含对称设置**（规章自己写了）。和 §4 合起来看：对称设置不进撤销是 user 定的分类，没问题；但 §4.1 说的「悄悄不对称」随机测试抓不到，因为它比的是「撤销重做前后一样」，不是「强行对称下模型真的对称」。

## 3. 拖动时会不会吸到自己（F-89）

user 10-25：「复制和实例预览其实感觉坑蛮大的，特别是对齐引擎。会不会自己卡住自己」。

### 3.1 不变量，和现在是怎么守的

**不变量：** 吸附目标必须同时满足两条：(a) 这次拖动不会让它动；(b) 画面上看得见。破了 (a) 会越拖越偏（目标跟着手跑）；只破 (b) 不会跑偏，但会吸到一个「鬼影」。

Opus 10-26 记的是「四种做法」。读完代码，实际是**两台吸附引擎、各有一个必填的口**，比「四种」整齐：

**硬表面这一台（`editor/solver.ts`）。** 每次查询必须交一个「手里有什么」（`hand`，类型上必填，空手要显式写 `NO_HAND`；2026-09 那次自吸事故之后立的）。编辑器统一算这只手（`Editor.freshHand`），三条规则：

1. 正被整体搬的组 / 组件、复制的影子、同一组件的其他份：整个槽标成「在手里」。
2. 预演里新长出来的点：凡是提交过的内核里没有的编号，自动算在手里。**这一条是结构性的**，画线、矩形、弧、推拉长出来的东西不用工具自己报。
3. 挪已有的点：工具自己报一个集合（移动、变换箭头都报了）。

连着手里的点的边、面，和由它们派生的交点，引擎自己退赛。

另外有三处直接声明空手，我逐处看了理由：首点拾取（还没有手）、镜像面把手（特地用没改过的世界）、悬停。都成立。

**自由建模这一台（`tools/mesh-snap.ts`）。** 自己另写的一套（点 > 线 > 面），必填参数是「正在动的点」。它看的是提交过的网格，不是预演，所以目标不会跟着手动。

**结论：两台都没有找到会「越拖越偏」的回路。** 不变量 (a) 守住了。

### 3.2 破了 (b) 的地方：吸到自己原来的位置（读码）

1. **自由建模开着软选择。** 「正在动的点」只有选中的那些；软选择带着走的邻居不在里面。它们在画面上已经挪了，但原来的位置还是吸附目标。
2. **自由建模开着镜像。** 对面跟着动的孪生点同理，原来的位置还是目标。
3. **硬表面旋转的第三步。** 吸的是按下那一刻的世界，里面包括被转的东西自己没转之前的样子。转的时候会吸到自己原来的角点方向。

第 3 条有一半是好事（转回 0° 会咬住）。第 1、2 条是纯粹的鬼影，修法简单：把软选择权重大于 0 的点、镜像孪生点并进「正在动的点」再交给吸附。

### 3.3 评「要不要一个总开关」

不建议硬并成一台。两台的目标集合本来就不一样（硬表面有推断线、充能、面交线；自由建模只有点线面）。该统一的是**规矩**，不是代码：

- 把 (a)(b) 两条写进吸附模型那份文档（`ai-docs/20260901-snap-model.md`），两台都指过去。
- 加一条两台通用的测试：每把会吸附的工具做一次拖动，断言「吸到的点，离这次拖动改过的任何一个点（改之前、改之后的位置都算）都不在容差里」。这条测试一次把 (a) 和 (b) 都看住，以后加新工具也跑它。

侧门也看了：透视吸附点（选中组件的原点）在给引擎之前会剔掉在手里的那份（`selectedPoolFrames`）；充能过的点 / 边存的是充能那一刻的坐标，不跟手动。

## 4. 镜像（F-116）

user 10-28：「记账，让fable系统的看一下mirror之类的。然后等一下，mesh的mirror只对本mirror有用啊」。

网格体有两种镜像：**强行对称**（每一步之后删掉另一半、照这一半镜回来）和**镜像编辑**（只挪点，对面的点跟着）。代码在 `mesh/mirror.ts`，编辑器在 `editor.ts` 的 `mirrorRewrite / mirrorForceAfter`。

### 4.1 强行对称：「已经对称了吗」判得太松（跑过）

**该有的定理：** 强行对称开着时，每一步之后，模型关于镜像面严格对称：点、边、面、面的朝向、边的标记、面的材质，两边一一对应。界面的话是「以后每一步都会对称，动了哪边哪边为准」。

**实现：** 每一步之后先问 `isSymmetric`；是，就什么都不做（为了不让另一半的编号乱换）；不是，才对称化。所以**这个判定就是定理的守门人**。它查三样：每个点有对面的点；每条边的镜像是一条边；第三样本意是「每张面的镜像是一张面」，但写出来的是「把每张面的点换成对面的点之后，没有两张面撞到一起」。这只能查出重复，查不出**缺**。

我在仓外用临时脚本搭了一块 6×3 的对称网格，直接调模块：

| 只在左半边做的改动 | `isSymmetric` 说 | 该说 |
|---|---|---|
| 挖掉中间一张面（四条边都还被邻居用着） | 对称 | 不对称 |
| 把一张面的朝向翻过来 | 对称 | 不对称 |
| 给一张面换材质槽 | 对称 | 不对称 |
| 给一条边打标记 | 对称 | 不对称 |

对应到 app 里（这一段是读码）：强行对称下删一张里面的面、「翻转法线」、标锐边 / 标平滑边，都走「做完查一下，不对称才对称化」，而查出来是「对称」，于是只有这一边变了。标记那条还多一层：提交前补对面那条边的改写只在「镜像编辑」模式做，强行对称模式指望事后对称化，事后又被这个判定放过去了。

**评修法。** 两种：

- 小修：把第三样改对（每张面换成对面的点之后，那个点集必须真是一张面，而且朝向相反、材质相同），再加上「每条边的标记和对面那条一样」。
- 根上的修：不靠「事后看结果猜」，改成**按指令的种类决定**。分类表（`mesh/mirror-ops.ts`）已经把每条指令分好了类，现在只用来决定「镜像编辑下要不要先问」。强行对称可以直接用它：改拓扑、改标记的指令做完**一律**对称化，只有登记成「对称进、对称出」的整体指令（现在只有细分）才走「查一下」。这样守门人不再是一个容易写漏的几何判定。代价是另一半的编号会更常换；实测编号是回收复用的，这块网格上对称化前后另一半的点编号没变，但面和边没逐个比，所以这一条要先量再定。

我建议根上的修，同时把小修也做了（`isSymmetric` 还被「开镜像时提示已经对称」和右上角的橙色标记用着，它自己也该是对的）。

**该补的测试：** 现在没有任何一条测试断言「强行对称下，做完任意一步，模型是对称的」。随机测试比的是撤销重做前后一致，抓不到这类。加一条：强行对称开着，随机做 N 步，每步之后用一个**独立写的**对称检查（不调 `isSymmetric`）断言。

### 4.2 「动了哪边哪边为准」对删除不成立（跑过）

`sideOfChange` 靠两样投票：新长出来的点在哪边、挪过的点在哪边。**删掉的东西不投票。** 一步里只有删除时，它答「看不出来」，编辑器就用上一次的那一边，没有上一次就当右边。

脚本实测：删左边角上一张面 → 判「看不出来」→ 按右边为准对称化 → 面数 17 变回 18，**那张面被镜回来了**。删右边角上那张 → 面数 16，两边都删了，对。

所以在强行对称下，如果上一次动的是右边（或者刚开还没动过），去左边删东西是删不掉的，而且没有任何提示。这不丢文件，但属于「界面说做了、其实没做」。

**修法：** 让删掉的点 / 面也投票（按它们删之前在哪边）。更干净的是连同 §4.1 的根上修法一起：指令自己带着「我动的是哪些点」，编辑器按这些点在哪边定，不用前后两个网格去猜。

### 4.3 裸线和孤点（跑过；账上的 T45）

对称化只镜**面**。没有面的裸线、孤零零的点：

- 在留下的那一边：不镜过去。
- 在被删的那一边：跟着那一半一起删掉，不说。

第二个后果是这次新查出来的：留下的那边只要有一条裸线，`isSymmetric` 就永远答「不对称」（它的点找不到对面），于是**之后每一步都把另一半整个删掉重建一遍**。实测再对称化一次，报告是「删 9 张面、加 9 张面」。模型大了这是每一步的白工，而且另一半上的选区每步都悬着。

**修法：** 对称化把裸线和孤点也镜过去（点已经有镜像函数，边补一个循环）。这样 T45 和「永远重建」一起没。

### 4.4 user 列的其余几问

- **「网格体的镜像只对本镜像有用」**（Opus 读作：设置跟着这个网格体自己走）。现状是这样：设置按组件定义存（`Scene.meshMirrors`），v0.16.6 起进文件。我同意这个读法；但这半句是 user 说的，读得对不对由 user 定。
- **设置要不要存进文件**：已经存了（v0.16.6）。它不进撤销（开关镜像撤不回去），这是规章里明写的分类。
- **镜像面 = 物体原点**：设计上我认为对。镜像面跟着物体走，挪物体不会让对称坏掉；想换镜像面的位置 = 换原点，已经有「设为组件原点」。要小心的只有一处：换原点会把几何整体挪一下，挪完之后原来对称的模型对新原点不对称，强行对称下一步就会按新面重建。换原点时如果这个物体开着镜像，应该说一句。读码没看到这句提示（没核全）。
- **切开的公差和防碎**：中缝容差是 1 毫米，写死（`MIRROR_TOL`）。配对用的是同一个数。模型按米建、细节小于 1 毫米时（首饰、小零件），离中缝不到 1 毫米的两个点会被当成同一个中缝点钉到面上。现在的做法没有随模型大小变。建议记成已知限制，等有人做小东西再说。
- **撤销 / 重放逐字一致**：对称化是一条普通的网格体指令，整表记录，撤销没问题（§2）。「重放」这条有一处我没核：对称化的结果依赖点的遍历顺序，重放时编号一致才一致；现有的差分测试覆盖它，但测试是不是跑到了镜像那条路，我没看。
- **交叉（Alt 点边选环过中缝、环切 / 倒角 / 细分开着镜像）**：镜像编辑下改拓扑先问「关掉镜像再做」，这一层有分类表 + 守卫，漏登记会红。强行对称下这些指令靠事后对称化，就回到 §4.1。逐条的组合我没跑。
- **硬表面和网格体两套镜像要不要一套接口**：不建议。硬表面那条是「一次性指令」（选中 → 镜像面把手 → 做完就完了），网格体的是「一直开着的编辑方式」。它们共用的只有「镜像面」这个概念和反射变换，这两样已经是共用的小函数。硬并一个接口会把「会话」和「模式」两种寿命搅在一起。硬表面那条（`editor/mirror.ts`，241 行）这次没逐行审。

## 5. 提示里的手写键名（F-120）

user 10-28 晚：「tooltip你没有更新，这背后有什么架构问题和可以设计瑞士奶酪的修」。

### 5.1 不变量，和已经做了的

**不变量：** 界面上任何地方写出来的「按哪个键是什么意思」，都得和键表（`controller/keymap.ts`）说的一样，而且得是**当前工作台**下的意思。

v0.16.23 落了四层，管住了左柱提示、小三角、手腕面板、帮助页、键名芯片。这些现在都从键表算出来，改键位不用改它们。

### 5.2 还没管住的（跑过脚本 + 读码）

我用脚本扫了 `src` 里所有字符串：除键表自己以外，**含键名的字符串大约 110 行，散在 25 个文件**。最多的是 `editor.ts`（25 行）和 `main.ts`（22 行），其余是各工具的提示行、工具条选项的说明、立场表格子里的括号注。

把其中写成「修饰键 + 键」的组合键全抽出来（15 种，如 Ctrl+J、Shift+D、Alt+H、Ctrl+R、Ctrl+B），逐个去键表里找：**15 种现在都在键表里。** 所以今天没有「提示说的键根本不存在」这种错。

这个脚本查不了的：

- **是不是这个意思、是不是这个工作台。** F-120 当初的 bug 正是这一类（键存在，但在自由建模里不是那个意思）。
- **单个字母键**（X / Y / Z 锁轴、G G 沿边滑、O 软选择、方括号改半径）。
- **「按住 Shift = …」这类修饰键语义。** 它们的出处是立场表，不是键表。

### 5.3 评修法

这 110 行不是一种东西，分三类，修法不同：

1. **讲一个动作的快捷键**（「Ctrl+V 原位粘贴」「Ctrl+J 合并」「Alt+H 全部显示」）。这类应该从键表派生：文案里不写键名，写动作的 id，由一个小函数查出当前工作台下真的那个键再拼进去；查不到就整句不提键。和左柱提示是同一个做法，接口已经有了（`toolKeyText` 那一家）。
2. **讲这把工具按住修饰键是什么**（「Shift = 沿垂直方向」「按住 Ctrl = 压」）。出处是立场表那一格。v0.16.16 的「按住修饰键露出提示」已经是从立场表读的。工具提示行里手写的这些应该删掉、让那条机制去说，或者从同一格读。
3. **立场表格子里的括号注**（「（Ctrl+B / Ctrl+Shift+B 键盘 = 倒角 / 倒点）」）。这是立场表在手写键表的内容，一份事实两处。应该改成引用动作 id，显示时再查。

**先上一层便宜的守卫，再慢慢派生。** 派生是一行一行改文案的活，110 行，适合交给施工的会话慢慢做。守卫可以先落，一次挡住整类：

- 测试扫 `src` 里所有界面字符串，抽出组合键（就是这次脚本做的事），断言每一个都在键表里。今天是绿的，以后改键位漏改文案就红。
- 进一步：给每条带键名的文案登记「它说的是哪个动作」，守卫用键表的 `resolveKey` 在声明的工作台下反查，键和动作对不上就红。这一步才真正挡住 F-120 原来那种错。登记表本身也是第 1 类派生的半成品，不白做。

单字母键和修饰键语义，脚本扫不准（字母太容易误伤普通文字），只能靠派生消掉，不能靠扫描守。
